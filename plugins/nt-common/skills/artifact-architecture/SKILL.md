## いつ使うか

- 比較資料・台帳・一覧系は対象外だ（`nt-common:artifact-templates`を使え）
- デザイントークン（配色・`max-width: 1700px`・和文フォント・文字の太さ）は独自に定義せず、`nt-common:artifact-templates`の「共通デザイントークン」節をそのまま使え。値の正本は向こうにあるのでここでは再掲しない。**構成図が単発の図解であることを、`max-width: 1700px` を適用しない理由に絶対にするな**
- **既存の構成図を直すときの起動漏れに注意しろ。** どういう場面で漏れるか・別skillが先に起動していても起動しろという判断は `nt-common:artifact-templates` の「いつ使うか」節に書いてある。構成図でも同じだ

## 絶対にやるな

- **出力形式に draw.io / mermaid を選ぶな。HTML＋インラインSVGに固定しろ。** draw.io は mxGraph 独自の座標系を自前で当たり判定する必要があり、ブラウザのレイアウトエンジンにレンダリング結果を測らせられない。「機械的に検証するループ」が原理的に組みにくい
- **`deploy-on-aws:aws-architecture-diagram`のような自動生成系の公式プラグインに頼るな。** CDK/CFnからの自動生成はリソースを取りこぼし、グループ枠がAWS公式スタイルにならず、世代の古いアイコンが混入する
- **publish前の確認をスクリーンショットの目視だけで済ませるな。** 目視には網羅性が無い。スクリーンショットを何度撮り直しても解消しなかった「矢印の経路が交錯する」「文字と線が被る」が、実測値の機械判定では一発で見つかる

## 手順

### 1. 出典を明記しながら描く

図の全要素を、参照した一次情報（IaCコードのファイル・行、実際に確認した設定値）に紐づけながら描け。ページ冒頭に出典（例: `出典 infra/bin/cdk.ts と infra/lib/**`）を明記しろ。あとで、例えば「このymlの条件ならこのジョブは動かないよな？」と聞かれたとき、行番号で即答できる状態にしておく。

### 2. アイコンは公式配布から直接取得する（AWSの例）

- `https://aws.amazon.com/architecture/icons/` の**英語版ページ**から `Icon-package` を取得しろ（日本語版ページは古い世代の zip を指すことがある）
- ライセンスは思い込みで判断せず一次ソースで確認しろ。同梱の使用許諾・PPTXデッキの記載を見ろ（改変禁止・再配布不可・図への使用は許諾ありが一般的だが、都度確認しろ）
- 改変禁止の対象は path のデータと fill 色だ。**一切変更するな**
- Artifactの CSP 制約で外部ホストの画像は読み込めない。取得したSVGは `<symbol id="...">` としてページ内に1箇所まとめて置き、各図から `<use href="#...">` で参照しろ
- グループ枠（AWS Cloud / VPC / サブネット相当）の線色・破線種は自作せず、同梱の PPTX デッキの shape properties から実測しろ
- **自作の箱でサービスを表した構成図は publish の時点で hook が止める**（AWS のサービス名が SVG の中に2種類以上あるのに `<symbol id="...">` と `<use href="#...">` の組が1つも無い場合）。止められたら描き直せ。迂回するな

### 3. SVGのレイヤー順序を理解して描く

**SVGは後に書いた要素が上に重なる。** ラベルに縁取り（`paint-order: stroke`等）を付けても文字が線に負けるなら、原因は大抵「矢印がラベルより後に描かれて上から塗り潰している」ことだ。**ラベルは経路（矢印・線）より後に描け**、を全図で固定しろ。

### 4. 図を包む器を横方向で中央に寄せろ

**図を包む器には必ず `display: flex; justify-content: center;` を当てろ。** ページの器の `max-width` は図の実サイズより広いのが常態で、中央寄せが無いと図はそのまま左端に張り付く。`margin: 0 auto` ではなく flex を使え（器の中身が図1枚のときも、凡例と横並びのときも同じ指定で中央に来る）。

### 5. 矢印の網羅性をIaCから起こした一覧と照合しろ

「矢印が繋がっていない」「経路が抜けている」はスクリーンショットでは見つからない意味的な不備で、実際に指摘の最大カテゴリになっている。図を描く前に、参照したIaCコード（セキュリティグループ・ルートテーブル・IAMロール・ネットワークACL等）から「起点→終点」の接続関係を一覧化した表を作れ。図を描き終えたら、一覧の行1つずつが図中の矢印1本に対応しているかを照合しろ（一覧に無い矢印・一覧にあって図に無い矢印の両方を検出する）。この照合はIaCの記法がリポジトリごとに異なるため、コードでの自動判定ではなく一覧表と図を並べた目視で構わない。

### 6. publish前に機械的検証をしろ（最重要）

ヘッドレスブラウザで実際にレンダリングし、実測値で以下を全項目、全数検査しろ。目視のスクリーンショット確認で代替するな。

1. **文字と線の交差**: `text` 要素の実測 bounding box と `path` / `line` を突き合わせ、交差を全列挙する
2. **行き先のない矢印**: 経路の終端が、接続先のコンポーネントの箱に接しているか。**「何らかの `rect` の内側に着地しているか」で判定するな。** グループ枠のような器の内側の空白で止まった矢印がそのまま合格になる。器（面積が図全体の一定割合を超えるノード・塗りの無い枠）は着地先の候補から外して判定しろ
3. **SVGが参照しているのにCSSに定義が無いクラス**: `class="..."` の値と、スタイル定義側のセレクタを突き合わせる（不一致は SVG 既定値でレンダリングされ、意図しない黒塗りの原因になる）
4. **要素間の余白**: 隣り合うノード枠の間隔と、枠の内側から文字までの余白を実測し、閾値未満を全列挙する
5. **文字が載っている器からのはみ出し**: **器を `closest('g')` のような DOM の入れ子から引くな。** `<g>` でラップしていない文字が検査ごと飛ばされ、入れ子の箱では外側だけが相手になってピルからのはみ出しがすり抜ける。文字の bounding box と全ノードの bounding box を突き合わせ、幾何学的に器を選べ
6. **アイコン（`<use>`）と文字の接触・近接**: アイコンは文字を内包しないので器の判定には入れず、距離だけを見る
7. **グループ枠の線と文字の接触・近接**: 塗りが無く線だけの矩形を計算後のスタイルから判定しろ。`data-role` のような属性に頼ると、付け忘れた枠が検査から漏れる
8. **図が器の中央から左右にずれていないか**: `svg` の描画矩形と、それを包む器の内側の矩形を実測し、左右の余りが釣り合っていないものを全列挙する

**「要素間の余白」を飛ばすな。「重なり」の検知だけでは、重なっていないが窮屈なだけの図はすり抜ける。** 閾値は絶対値ではなくその図の文字サイズに対する比率で持て（`verify-svg.js` は文字サイズの中央値に対して、ノード枠の間隔を1.2倍、枠と文字の間を0.4倍を下限としている）。指摘が続くなら比率を上げて育てろ。

指摘されてから直すのではなく、指摘される前に自分で検査を通してから提示しろ。検査は「文字と線の重なり」→「行き先のない矢印」→「クラスの取り残し」のように、1件指摘が来るたびに検査項目を増やして育てていい。育てた検査は使い捨てにせず `${CLAUDE_SKILL_DIR}/references/verify-svg.js` へ書き戻せ。

**実行には orca のブラウザ操作を使え。**

1. プレビュー用の一時HTMLファイルをローカルに保存する
2. `orca tab create --url "file://<絶対パス>"` で開く（既にタブがあるなら `orca goto --url "file://<絶対パス>"`）
3. `orca eval --expression "<verify-svg.js の関数を即時実行する式>" --json` で検査を走らせる。`${CLAUDE_SKILL_DIR}/references/verify-svg.js` の中身を式として渡せ。戻り値のうち `severity: "error"` が0件になるまで直す。`severity: "warn"` は誤検知を含みうるので、1件ずつ実際のレンダリングを見て妥当性を判断してよい
4. 終わったら `orca tab close` で閉じろ

### 7. 複数図構成なら1図だけ先に作れ

図が複数枚になる構成（例: ネットワーク図・デプロイフロー図・監視経路図）では、いきなり全部作るな。**1枚だけ作って方向性の承認を得てから残りに同じ方式で展開しろ。** アイコン方式の変更は座標の全面組み直しを伴うことがあり、手戻りを1図分に抑えられる。

### 8. 裏付け表は図に無い情報だけに絞れ

図の下に補足の表を置くこと自体は良いが、**図で表現済みの情報（ノード名・条件・経路の合流先）を表でも繰り返すな。** 表に載せていいのは図に無い情報（欠測時の扱い、コスト額、正確なポート番号のような細かい一次情報）だけだ。迷ったら図の`figcaption`か各ノードの補足テキストに一言足すだけで済ませ、表を新設するな。

### 9. 同じファイルパスに再公開してURLを固定しろ

修正のたびに新しいArtifactを作るな。同じファイルパスに書き戻して再公開すれば、共有したURLは1本のまま更新できる。**公開が競合して失敗したときの扱いは `nt-common:artifact-templates` の「公開が競合したときの扱い」節に従え**（`force:true` で押し切るな）。

**publish 前のローカル確認と、Artifact ツールの deny の一時解除は `nt-common:artifact-templates` の「publish 前後の手順」節に従え。** 手順の正本は向こうにあるのでここでは再掲しない。

## 関連skill

- 組み込み `artifact-design` — favicon・title・テーマトークンの一般原則。**このskillより先に、または合わせて読め**
- `nt-common:artifact-templates` — 比較資料・台帳系はこちら。デザイントークンの正本もここにある
- 組み込み `artifact-diagramming` — 図解全般の描き方・inline SVGの基本メカニクス。このskillが扱うのはその上に乗るインフラ構成図固有の落とし穴と実績のある手順だ
- 組み込み `artifact-capabilities` — ライブデータ・共有状態等の高度な機能が要るときはこちらを使う（このskillの対象外）
