## いつ使うか

Artifactで以下のようなページを作る意図を感じたら、書き始める前に読め。**既存のArtifactを更新するときも同じく起動し、公開済みのHTMLをテンプレートと突き合わせろ。** 新規作成でなければ対象外、と判断するな。

- 2つの対象（システムA/B、旧仕様/新仕様等）の項目を突き合わせて見せる資料
- 多数の項目・カラム・データを、グループ単位で絞り込み・検索・並び替えして見せる台帳・一覧（週別・担当別のロードマップ／スケジュール表を含む）

表形式で多数の行を扱うなら、「ダッシュボード」と呼ばれていてもグループ化テーブル型を検討しろ。名称だけで対象外と判断するな。

**単発の説明ページ・図解のようにどちらの型にも当たらないものでも、対象外になるのは「型の選び分け」だけだ。** 共通デザイントークン（`max-width: 1700px` を含む）・ダーク分岐の禁止・表を持つ場合のテーブル規定（列区切り線・ヘッダクリックソート・列幅ドラッグリサイズ）は、Artifact 全般の既定として必ず適用しろ。**型に当たらないことを、これらを適用しない理由に絶対にするな。**

### 起動漏れが最も起きるのは既存Artifactの更新依頼だ

- 既存ArtifactのURLを貼られて「直せ」「更新しろ」「突き合わせろ」と短く指示されたとき。`plan` / `research` が先に反応し、このskillに一度も渡らないまま作業が終わる
- **別のskillが先に起動していることを、このskillを起動しない理由にするな。** Artifactを触るなら両方だ
- **`artifact-design` が起動していても、このskillの代わりにはならない。**
- **`/compact` の後もArtifactを触り続けるなら、もう一度起動しろ**

**1回の会話の中で同じArtifactを何度も直すなら、突き合わせは初回だけで終わらせるな。修正のたびに毎回やれ。** 最初はテンプレートに沿っていても、修正を重ねる過程で逸脱していく。

## 既存Artifactを更新するときの差分チェックリスト

既存Artifactへの追記・修正を行うときは、書き始める前に公開済みHTMLと対応する `references/*.html` を突き合わせ、以下を確認しろ。

- ダーク分岐（`@media (prefers-color-scheme: dark)` / `:root[data-theme="dark"]`）が入り込んでいないか
- 配色トークン（`--bg` / `--accent` 等）の値が全項目一致しているか。「近いが不一致」も見逃すな
- 判定バッジ相当のクラス（`k-v1` 等）が、更新対象の要素すべてに漏れなく付いているか
- `max-width: 1700px` が保たれているか

## 型の選び分け

| 状況 | 選ぶ型 |
|---|---|
| 比較対象が2つあり、各項目の説明が長い | **マスター/ディテール型**（`references/master-detail.html`） |
| 項目数が多く1行が短く、グルーピング可能（テーブル名等の単位がある） | **グループ化テーブル型**（`references/grouped-table.html`） |
| 一覧の各行についてユーザーの判断（採用/却下/選択）を集める用途 | **グループ化テーブル型** + `artifact-capabilities` の `publish()` で選択状態を保存する形にしろ。読み取り専用で出すと必ず作り直しになる |

### ユーザーの操作を保存する形にするとき、何を保存して何を保存しないか

**`publish()` で永続化していいのは、複数人で集約したい判定値（ランク・採否の選択等）だけだ。** 閲覧用のフィルタ・検索語・ソート状態・選択中のタブは、その人がその場で見たいものを絞っているだけの表示状態なので、`localStorage` に留めて `publish()` に混ぜるな。混ぜると、他の閲覧者が絞り込みを変えた瞬間に自分の絞り込みが外れる。

**変更監視（`watch`）を勝手に有効にするな。** ユーザーが「他の人の更新を検知したい」と明示したときだけ使え。

**取り違えるな。** 長い説明が伴う比較は、テーブルの1セルではなく `.compare-grid` の左右2カラムに分けて見せろ。

## 使い方

1. 型を選んだら、対応する `references/*.html` を作業用の一時HTMLファイルに `cp` でコピーしてから、そのファイルを直接編集して `{{...}}` プレースホルダとJSコメントで示した箇所を実データに置き換えろ。真っ白なファイルに手で書き写すな
2. CSS変数（配色トークン）・レイアウト・インタラクションのロジックはそのまま使え。**独自の配色・レイアウトに作り替えるな**
3. データは `DATA` という名前のJS配列に埋め込み、レンダリングはクライアント側JSで行う既存の書き方を踏襲しろ（サーバーサイドテンプレートエンジンは使わない）

## 共通デザイントークン（Artifact 全般に共通・変更するな）

```css
--bg: #f4f5f8;        /* ページ全体の下地。薄いグレー */
--surface: #ffffff;    /* カード・パネルの背景 */
--surface-alt: #eceef3;
--border: #d7dae3;
--text: #1a1d27;
--text-muted: #5b6072;
--text-faint: #8a8fa3;
--accent: #33459c;
--accent-soft: #e7eafb;
--shadow: 0 1px 2px rgba(20, 22, 30, 0.06), 0 8px 24px rgba(20, 22, 30, 0.05);
```

- `.page { max-width: 1700px; margin: 0 auto; }` — 議論せずこの値を使え
- フォント: `"Hiragino Sans", "Hiragino Kaku Gothic ProN", "Yu Gothic UI", "Meiryo", system-ui, sans-serif` + `font-feature-settings: "palt"` + `line-height: 1.6`
- 数値には必ず `font-variant-numeric: tabular-nums` を当てろ（桁がガタつくのを防ぐ）
- ヘッダー直下にサマリーカード（数字＋ラベル）を3〜4枚置け。クリックでフィルタトグルにできるなら、そのまま活用しろ
- **文字は`font-weight: 400`（既定値）のまま出すな。** 本文相当は500〜600、ラベル・見出し・数値相当は700を目安にしろ。`--text-muted` / `--text-faint` の薄い色に小さいフォントサイズを組み合わせると、既定の細さでは実機で読めない。両テンプレートの既存クラスに付けた値をそのまま倣え

**ユーザーの要望はテンプレートより常に優先だ。** テンプレート通りであることを、直さない理由にするな。「この行はテンプレートと一致しているので仕様通りです」という回答は、テンプレート自体に問題があるケースでは通用しない。テンプレート側が悪いと分かったら `/gripe` に回せ。

## 載せる情報は依頼された範囲に絞れ

**依頼されていない列・注記・他案件への言及・経緯の説明を自主的に足すな。** 要望にある情報だけを載せ、迷ったら削る方向で判断しろ。

**特に足しがちなのは、検討の経過・比較した他案件の名前・今回決めた方針のまとめだ。どれも資料の本題ではない。**

## 厳守事項（1つでも破るな）

- **ダーク分岐を作るな。ライト固定にしろ。** `@media (prefers-color-scheme: dark)` も `:root[data-theme="dark"]` も書くな。ページ冒頭に「このページは常時ライト固定（ダーク分岐は意図的に持たない）」という趣旨のコメントを残せ
- **`max-width: 1700px` を疑うな。**
- **ArtifactのHTMLの記述・修正・テンプレートとの突き合わせをサブエージェントに委任するな。自分でやれ。** 委任していいのは公開済みHTMLを読んで要点を抜く作業だけで、修正の適用は渡すな。
- **幅・フォントサイズ等の数値を直すとき、片側へ振り切るな。** (1) 現在値を実測してから変えろ。(2) 変更前後の値を会話で示せ。(3) 1回で決めきれない指示は段階的に動かせ。
- **表の1セルに長文を詰め込むな**。マスター/ディテール型なら `.compare-grid` の左右2カラム、グループ化テーブル型なら備考列を短く保て
- **列がある表には、可能な限り列区切り線（`border-right`）・ヘッダクリックソート・列幅ドラッグリサイズ（`grouped-table.html` の `.col-resizer` の実装）を付けろ**。無くても動くが、表の読みやすさを大きく左右する
  - **列幅リサイズを入れたら、公開前に実測で2点確認しろ。目視で済ませるな。** (1) リサイズのドラッグでソートが誤発動しないこと。`.col-resizer` の mousedown を `stopPropagation` しても、ドラッグ終了後にブラウザが生成する click は th へバブルするため、click 側の `stopPropagation` が無いと**必ず**ソートが走る（実測で確認した）。(2) 再読み込み後に幅が保持されること。保存が無いと再公開のたびに初期値へ戻る
  - **他の修正を入れて再公開するたびに、この2点を再確認しろ。** 無関係な作業の直後に壊れる

## publish 前後の手順（Artifact 全般に共通）

### publish 前に依頼者自身の目で見せろ

自分で撮ったスクリーンショットや機械的な検査で代替するな。

1. 公開する HTML のコピーをスクラッチパッドへ `verify.html` として置け。`<head>` の先頭に `<meta charset="utf-8">` を必ず付けろ（付けないと和文が文字化けする）
2. そのディレクトリで `python3 -m http.server 8931` をバックグラウンドで起動しろ
3. `http://localhost:8931/verify.html` を案内し、ブラウザで開いて確認してもらえ。**返事が返るまで publish するな**
4. publish が済んだらサーバーを止めろ

**ポートは 8931 に固定しろ。** 毎回同じ URL なら依頼者がブラウザの履歴から開き直せる。

### Artifact ツールの deny を publish の直前だけ外せ

`~/.claude/settings.json` の `permissions.deny` に `"Artifact"` が入っているなら、publish の直前に取り除き、publish が終わったら必ず戻せ。

- **外すときも戻すときも、`permissions.deny` の変更差分を会話に提示して確認を取ってから書き換えろ。** グローバル設定ファイルを黙って書き換えるな
- **publish が失敗したときも必ず戻せ。** 戻し忘れると封鎖が解けたままになる

## 公開が競合したときの扱い（`force:true` を使うな）

**`publish` が「このセッションは最新版を見ていない」「別の版が公開済み」の類のエラーで失敗したら、`force:true` で押し切るな。** その新しい版は、ユーザーがページ内で直接行った操作（ランクの選択等）の保存結果だ。`force:true` はそれを破棄するので、ユーザーの入力が消える。

- 競合したら、エラーが指す最新版を読み直し、自分の変更をそこへマージし直してから公開しろ
- `force:true` を使ってよいのは、ユーザーが「その版は破棄してよい」と明示したときだけだ
- **ユーザーがページ内で直接操作する機能を持つArtifactでは、デザインの微調整のたびに公開し直すな。** 公開のたびにユーザーの操作と競合する。直す点をまとめてから1回で公開しろ

公開前のWebFetch確認がhookでブロックされる場合、その確認自体は一次仕様の事実確認ではないため `/research` は不要だ。
