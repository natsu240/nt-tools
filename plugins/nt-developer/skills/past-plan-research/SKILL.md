# 過去の実装計画を検索する（書く前に読め）

実装計画の置き場所は2通りある。**どちらも検索対象にしろ**（片方だけ見て「無い」と言うな）。

- **`plans/*.md`**: コミットしないローカル専用ファイル。GitHub 上の検索や remote への grep では見つからない。ローカルディスク上を直接検索しろ
- **GitHub Issue の description**: GitHub Issue で課題管理しているリポジトリでは、実装計画が Issue 本文に書かれている（`nt-developer:plan` の経路）。ローカルには無いので `gh` で検索しろ

## 手順（plans/*.md 側）

1. **検索対象を洗い出す**: `find ~/pj -maxdepth 3 -type d -name plans 2>/dev/null` で、ローカルに clone 済みの全リポジトリの `plans/` ディレクトリを列挙しろ。`~/pj` 以外の場所にもリポジトリがありそうなら、ユーザーに置き場所を確認しろ
   - `plans/` の配下は「状態（`進行中/` `完了/`）→ 管理表（`github/` `other/` 等）」の2階層に分かれている。**どのディレクトリも検索対象にしろ**（`plans/` を起点にすれば全部入る）。規約を変える前に書かれた計画書が `plans/` 直下にフラットに残っているリポジトリもあるので、そこも対象に入れろ
2. **キーワードで絞り込む**: 受け取ったキーワード・関連語で `grep -rli`（大文字小文字を区別しない）をかけろ。ファイル名一致（`find <plans ディレクトリ> -type f -iname "*<キーワード>*.md"`）も併用しろ。**`find` に `-maxdepth` を付けるな**（状態・管理表のディレクトリ配下が丸ごと漏れる）。1つのキーワードで0件なら、類義語・関連する業務用語でも最低もう1パターン試せ
   - ファイル名は `<日本語タイトル>-<チケットID>.md`（例: `ログイン画面のUIリニューアル-104.md`）の形なので、タイトルの語・チケットIDのどちらでも当たる。チケットの採番元はファイル名ではなく管理表のディレクトリ（`github/` 等）で分かるので、採番元で絞りたいときは検索の起点をそのディレクトリにしろ
3. **ヒットしたファイルは全文 Read しろ**。grep のマッチ行だけを判断材料にするな。否定形・限定条件・時制が切れて意味を取り違えるリスクがある

## 手順（GitHub Issue 側）

1. **検索対象のリポジトリ・組織を決めろ**: カレントリポジトリは `gh repo view --json nameWithOwner,owner`、ローカルの他リポジトリは `git -C <パス> remote get-url origin` から owner/repo を集めろ。**組織名を推測で決め打ちするな**（集めた owner が複数あるなら、どこを見るかユーザーに確認しろ）
2. **キーワードで検索しろ**:
   - リポジトリを絞るなら `gh issue list --repo <owner>/<repo> --search "<キーワード>" --state all --limit 20 --json number,title,state,url`
   - 組織を横断するなら `gh search issues "<キーワード>" --owner <owner> --limit 20 --json number,title,state,url,repository`
   - `--state all` を付けろ（実装が終わった計画は closed 側にある）。1つのキーワードで0件なら類義語でも最低もう1パターン試せ
3. **ヒットした Issue は本文を全文取得しろ**: `gh issue view <番号> --repo <owner>/<repo> --json title,body,state,url --jq '.body'`。検索結果のタイトルだけで判断するな
   - 議論が本文ではなくコメント側に積まれていることがある。本文だけで経緯が読み取れないときは `--comments` も取れ
4. Issues が無効・`gh` が未認証のリポジトリはこの経路をスキップしろ（`plans/*.md` 側の結果だけで報告し、Issue 側は見ていないと明示しろ）

## まとめ方（経路共通）

- 複数ヒットした場合、リポジトリ名・状態・チケットID / Issue 番号・タイトルで一覧を先に示してから、関連度が高そうな順に中身を要約しろ
- **結論が出ていないものを、出ているものと同じ確度で紹介するな**。`plans/進行中/` のファイルと open の Issue は「まだ決まっていない前提」で扱え
- 要約は「背景」「変更後・対応内容」「採らなかった案」「この判断を覆す条件」「未解決事項」「今回やらないこと」を中心に、今回の相談内容とどう関係するかを一言添えろ。単なる見出しの書き写しにするな

## 出典の書き方

経路が分かる形で書き分けろ。

- `plans/*.md`: `(plans) <リポジトリ名>/plans/<状態>/<管理表>/<ファイル名>`（例: `(plans) sample-app/plans/完了/github/ログイン画面のUIリニューアル-104.md`）。**状態・管理表のディレクトリを省くな**。進行中のものか完了したものか、どこで採番されたチケットかが出典を見た時点で分かるようにするためだ。規約を変える前に書かれた `plans/` 直下のファイルは、そのまま `(plans) <リポジトリ名>/plans/<ファイル名>` と書け
- GitHub Issue: `(issue) <owner>/<repo>#<番号> <タイトル>（open / closed）`

`plans/*.md` はコミットされていないローカル専用ファイルなので、他の人と共有する文章（PR 本文等）にこのファイルパスをそのまま転記するな。**GitHub Issue にはこの制約は無い**（相手も開けるので、番号・URL をそのまま書いてよい）。

## 見つからなかった場合

0件でも「無い」と断言する前に、キーワードを変えて最低2パターン試したか・両方の経路（plans と GitHub Issue）を見たか確認しろ。それでも見つからなければ「過去の計画には見当たらなかった」と正直に報告しろ。どちらかの経路を見られなかった場合（`gh` 未認証等）は、その経路を見ていないことを明示しろ。
