# PRレビュー返信フローの自動化

PR番号を受け取り（省略時はカレントブランチの open PR）、**レビュー内容の取得 → 指摘の自律調査 → 一覧テーブル提示 → 会話文での進め方確認 → 修正 → commit/pr/pr-comment への連鎖**までを1つの入口で扱う薄いオーケストレータースキル。**指摘そのものを新規に探す作業はこのスキルの対象外**（すでに投稿されたレビュー内容の確認・対応に特化する。初回レビュー実施は `nt-developer:code-review` の担当）。文面生成・敬語チェックも実装しない（すべて `nt-developer:pr-comment` に委譲する）。

## 対象PRとモードの確定

- 引数が数字のみ → その PR 番号を対象にする
- 引数省略時 → `gh pr list --head "$(git symbolic-ref --short HEAD)" --state open --json number,title --jq '.[0]|select(.)|"\(.number)\t\(.title)"'` でカレントブランチの open PR を検出しろ。見つからなければ対象PR番号をユーザーに確認しろ
- 対象PR番号が確定したら `gh pr view <番号> --json author --jq '.author.login'` と `gh api user --jq '.login'` を突き合わせろ
  - **一致（自分のPR）→ Flow B**（対応の結果、修正が発生しうる）
  - **不一致（他人のPR）→ Flow A**（確認のみ。原則コード修正は発生しない）

## レビュー内容の取得（4種を必ず取る。取りこぼし対策として決定論的に固定している）

以下を毎回この順で全部取得しろ。1つでも省略するな（実測で行コメント・diff の取りこぼしが発生していたため固定した）:

1. `gh api repos/{owner}/{repo}/pulls/<番号>/reviews`（レビュー本体。approve / comment / changes_requested の状態と本文）
2. `gh api repos/{owner}/{repo}/pulls/<番号>/comments --paginate`（行コメント。ファイル・行番号付き）
3. `gh api repos/{owner}/{repo}/issues/<番号>/comments --paginate`（会話タブのコメント）
4. `gh pr diff <番号>`（差分本体。指摘対象のコードを確認するのに使う）

`{owner}/{repo}` は `gh repo view --json nameWithOwner --jq .nameWithOwner` で取得しろ。

**`reviews`／レビュー依頼が空でも「まだ誰も見ていない」と断定するな。** レビュアーが着手済みだがまだコメント・approve 等を投稿していない状態は、これらの API では検知できない。レビュー状況の確認が必要な場合は、直接連絡ではなく、PR 上のコメントで確認・共有しろ。

## スコープ・作業内容を聞かれたときの確認

- PR の作業内容・スコープについて質問されたら、回答前に必ず対象の実装計画書（`plans/` 配下、または GitHub Issue 経路では Issue の description）を(再)Read しろ。計画書を一度も Read していない状態でスコープに関する質問に答えるな
- 計画書だけでなく、対象 PR の本文（`gh pr view <番号> --json body`）も確認しろ。計画書と PR 本文の記載が食い違う場合は、より新しい確定情報である PR 本文を優先しろ

## 計画書の引き当てと照合

**一覧テーブルを出す前に必ず終わらせろ。** レビュー2周目では、1周目の指摘への回答が計画書に承認記録として残っている。計画書を読まないまま採否を決めると、一度合意した決定を覆す判定と、ユーザー自身が手で入れた変更を戻す判定が混ざる。

- 引き当て方は経路ごとに違う。どちらも試して見つからなければ照合を飛ばして先へ進め（計画書を持たない PR がある）
  - **`plans/` 経路**: `plans/` 配下から `<!-- PR: #<対象PR番号> -->` を含むファイルを探せ。`plans/` の起点は本体のチェックアウトだ（ワークツリーの中には無い）
  - **GitHub Issue 経路**: PR 本文（`gh pr view <番号> --json body`）の `Closes #<番号>` から Issue 番号を取り、`gh issue view <番号> --json body --jq .body` で description を取れ
- **引き当てた計画書は全文読め。** 節名を決め打ちして部分読みするな。承認記録は計画書へ後から足された見出しに入ることがある
- 照合で拾うのは次の2つだ。どちらかに当たった指摘は、「指摘の抽出と自律調査」節の判定基準に従って対応推奨を決めろ
  - **合意の蒸し返し**: 同じ論点が前のレビューで既に出ていて、ユーザー承認のうえ「対応しない」と決まっている
  - **ユーザー自身の手による変更**: 差分の一部をユーザーが手で入れたと計画書に記録されている
- **照合の結果は一覧テーブルの「調査結果」欄に、根拠にした計画書の記述とあわせて書け。** 列を増やすな（端末の幅に収まらず表が縦積みに崩れる）

## 指摘の抽出と自律調査（AskUserQuestionは使わない）

- 取得した4種から個々の指摘事項を抽出しろ。同じ内容を指す複数コメント（例: レビュー本体の要約 + 行コメントの詳細）は1件にまとめろ
- **Flow A（他人のPR）では、指摘元を自分（対象PRのモード確定で取得済みの自分のGitHub login）に絞り込め。** 他のレビュアーが投げた指摘は原則一覧に含めるな。例外は次の2種のみ: ①自分が投げた指摘と直接関係する指摘（同じファイル・同じ問題を別の角度から指摘している等）②コードをReadして自律調査した結果、見過ごすとバグ・セキュリティ問題・重大な仕様違反につながると判断した指摘。例外的に含める場合は一覧テーブルの指摘元欄に「(他レビュアー、含める理由: ...)」と明記しろ
- **Flow B（自分のPR）では絞り込みをしない。** 全レビュアーからの指摘が自分への対応依頼だからだ
- **各指摘についてClaudeが実際にコードをReadして妥当性を自律的に調査しろ**。指摘の主張をそのまま鵜呑みにするな。該当ファイルを読み、指摘が主張する挙動が本当に起きるか確認しろ
- **コードを読むだけで判定を決めるな。対象PRの計画書を引き当てて全文読み、各指摘と必ず照合しろ**（引き当て方は「計画書の引き当てと照合」節にある）。計画書を読まずに一覧テーブルを出すな
- 調査結果を踏まえ、各指摘に対応推奨（`対応する` / `対応しない` / `要確認`）を判定しろ:
  - 妥当性を確認できた指摘・規約違反・バグ → `対応する`
  - 誤り・的外れと確認できた指摘 → `対応しない`（根拠を明記しろ）
  - **同じ論点が前のレビューで既に出ていて、計画書にユーザー承認のうえ「対応しない」と記録されている指摘 → `対応しない`**（一度合意した決定を自分の判断で覆すな。計画書のどの記述を根拠にしたかを明記しろ）
  - **計画書に「ユーザー自身が手で入れた変更」と記録されている箇所への指摘 → `要確認`**（意図した変更をレビュー指摘のまま戻すと、ユーザーの手を消すことになる）
  - コードだけでは妥当性を判断できない指摘（仕様の解釈が絡む・相手の意図確認が必要 等） → `要確認`
- 調査が終わったら、**AskUserQuestionを使わず**、以下の形式の一覧テーブルを会話に提示しろ:

| # | 指摘元 | 指摘内容 | 調査結果 | 対応推奨 |
|---|---|---|---|---|
| 1 | \<reviewer login\> | \<要約\> | \<該当ファイル:行を読んで確認した内容\> | 対応する |
| 2 | ... | ... | ... | 要確認 |

- 提示直後、通常の会話文で「この一覧の対応方針で進めてよいか、変更したい番号があれば教えてください」と聞け。ユーザーの自由なテキスト返答（例:「全部いいよ」「2は対応しないで」）を受けて対応範囲を確定しろ
- **指摘の要否判断で AskUserQuestion を送る前に、関連調査（git blame / git log / grep / 仕様書照合）を全て終わらせてから1回にまとめて聞け。** 同一論点への再質問は原則1往復まで。2往復目に入りそうなら質問設計を見直せ

## 修正〜返信の連鎖

対応方針が確定したら:

- `対応する` と確定した指摘を通常のEdit/Writeで修正しろ（既存のcode-style系hookが自動で効くので、このスキル側は専用の修正手順を持たない）
- 修正内容をユーザーに提示し、承認を得ろ
- レビュー対応中に新たに判明した実装背景・経緯があれば、`nt-developer:pr`（既存 PR 編集モード）を呼んで PR 本文に反映しろ
- **Flow B（自分のPR）で1件以上修正した場合**:
  - `nt-developer:commit` を起動しろ（コミット前確認はcommit skill自身の仕様どおり毎回発生する）
  - `nt-developer:pr` を起動しろ（カレントブランチに対象PRが開いており未pushコミットがあるため「既存PRへの追加コミットpushモード」に自動で入る）
  - push後、`nt-developer:pr-comment` を明示的に起動し、レビュアーへの対応完了コメントを投稿しろ（`pr` skillの「検討する」判定に委ねず、このスキルが明示的に呼ぶことで確実に連鎖させる）
- **Flow B で修正対象が0件**（全指摘が `対応しない`）の場合: commit/pr をスキップし、`nt-developer:pr-comment` を起動して指摘への回答（対応しない理由の説明）を投稿しろ
- **Flow A（他人のPR）**: 修正は発生させるな。全指摘の対応方針が確定したら `nt-developer:pr-comment` を起動し、approve / comment / 変更依頼のいずれかを判断させろ
  - `要確認` が1件以上残っている場合は `--approve` を使わせるな（`pr-comment` 側の「approveしてよい状態かの判定」が既にこの制約を持っている）

## マージまで進んだ場合

approve をもらってこのセッションでそのままマージしたなら、**`gh pr merge` が成功した直後に `${CLAUDE_SKILL_DIR}/../../references/post-merge-handoff.md` を Read してその手順に従え。** デプロイ後にしかできない確認が残っているかを見て、残っていれば `deploy-watch` skill へ渡す判定だ。マージせずに終わるなら関係ない。

## `/pr` 自体の変更

このスキルは `nt-developer:pr` の既存挙動（既存PRへの追加コミットpushモード）をそのまま利用する。`/pr` 自体の改修は不要。

## ルール

- **指摘そのものを新規に探す作業はこのスキルの対象外**。すでにPRに投稿されたレビュー内容の確認・対応に特化しろ。初回レビュー実施は `nt-developer:code-review` に任せろ
- Flow A では指摘元を自分に絞り込め。他レビュアーの指摘は、直接関連する・見過ごせない重大な問題の場合のみ例外的に含めろ
- レビュー内容の取得は4種を必ず全部取れ。取得元を1つでも省略するな
- 指摘の採否確認にAskUserQuestionを使うな。一覧テーブル + 会話文での確認に固定しろ
- 各指摘の妥当性は必ずコードをReadして自律的に検証しろ。取得した本文をそのまま鵜呑みにするな
- **一覧テーブルを出す前に、対象PRの計画書を引き当てて全文読み、各指摘と照合しろ。** 計画書でユーザー承認のうえ決まった内容を、自分の判断で覆すな
- **一覧テーブルを出すまで、取得・調査の途中経過を報告するな。** 道具を呼ぶたびに一言挟むと、テーブルが画面のずっと下に押しやられて「テーブルで出てこない」と言われる（実測）。黙って進め、調査が終わってからテーブルを一度に出せ
- 修正はこのスキル自身が独断で行わず、対応方針確定後に通常のEdit/Writeで行え
- Flow B で1件以上修正した場合は commit → pr → pr-comment の順に必ず連鎖させろ。push だけで終わらせるな
- Flow A では修正を発生させるな。確認結果は pr-comment への連鎖で返信しろ
- 文面生成・敬語チェックは実装するな。すべて `nt-developer:pr-comment` に委譲しろ
