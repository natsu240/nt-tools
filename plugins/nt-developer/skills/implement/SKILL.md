# 実装セッションの手順

計画セッション（`plan` skill）で書かれ、承認された計画に沿って実装するためのセッションだ。同梱の hook が、`plan` / `implement` / `review` のいずれも未起動のままの編集・状態変更を block する。

| 詳細手順 | いつ読むか |
|---|---|
| `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` | Issue の description を書き換えるとき |
| `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` | plans 経路で作業中の計画書を記録するとき |
| `${CLAUDE_SKILL_DIR}/../../references/implement-handoff-prompt.md` | 本体で起動されてワークツリーへ引き継ぐとき |

**このセッションが実装するのは、Orca 管理のワークツリーの中で起動されたときだけだ。** 本体のチェックアウトで起動されたなら、自分で実装せず下の「ワークツリーへ引き継ぐ」に徹しろ（`git-rules` の「呼び出し元のセッションは自分で実装せず、引き継ぎ内容をプロンプトに書いて渡せ」に従う）。

## 呼ばれ間違いの検出

**この skill は計画が既にあることが前提だ。** 計画（Issue の description または `plans/*.md`）に「実装ステップ」の節が無い、あるいは計画そのものが無いなら、それは `plan` の担当だ。`/nt-developer:plan` を案内して止まれ。実装ステップの `- [ ]` が全部埋まっていて未コミットの変更がある状態なら `review` の担当だ。`/nt-developer:review` を案内して止まれ。

**計画に「決めたこと」節が無い、または「確認テスト: 合格」の記録が無いなら、決定フェーズを飛ばした古い計画だ。** `/nt-developer:plan` を案内して止まれ。実装ステップが揃っているように見えても、この2つが無ければ実装へ進むな（同梱 hook が `Edit` / `Write` / `MultiEdit` の時点で機械的に deny する）。

**計画に「計画書レビュー: 合格」の記録が無いなら、計画書レビューを飛ばした計画だ。** `/nt-developer:plan-review` を案内して止まれ。**この skill の中で代わりにレビューを回すな**（同じ hook が deny する）。

**実装着手の明示的な承認が返っていないなら実装するな。** 直前が計画セッションで承認をまだもらっていないなら、この skill が呼ばれたこと自体を承認と解釈せず、承認の確認へ戻れ。

## 入口でこれを全部やれ。飛ばすな

- **Issue 経路**: `gh issue view <番号> --json body --jq .body` で description を**全文読め**。要約で済ませるな
- **plans 経路**: 計画書を Read で**全文読め**。あわせて `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` のコマンドで記録を上書きしろ
- 実装ステップのチェックボックスを見て、どこから再開するかを決めろ
- `git rev-parse --git-dir --git-common-dir` で今いる場所を確かめろ。2つが一致すれば本体のチェックアウトだ（切り出した側は `--git-dir` が `.git/worktrees/<名前>` を指す）。一致したら下の「ワークツリーへ引き継ぐ」へ進み、自分では実装するな
- **plans 経路**: カレントブランチがその作業のブランチになっているか確認しろ。違っていれば切り替えろ
- `git status --porcelain` と `git diff` で、前のセッションが作業ツリーに残した変更を確認しろ。**「まだ何も実装されていない」と決めつけるな**（前のセッションが途中まで書いて閉じている）

**assignee / label / Type / フィールドの設定をやり直すな。** 計画セッションで埋めてある。`gh api /orgs/<org>/issue-fields` 等を毎セッション叩き直しても、すでに値が入っているので結果は変わらない。

## ワークツリーへ引き継ぐ（本体で起動されたとき）

**実行するのはこの実装セッションの入口だけだ。Issue 番号が確定しただけでは実行するな**（計画セッションのまま終わると、使われないワークツリーが残る）。

1. Skill ツールで `nt-developer:git-rules` を起動し、`orca worktree create` の書式とそのリポジトリに渡す値を確認しろ。**書式をここに書き写さない。手順の正本は `git-rules` だ**
2. 引き継ぎプロンプトを `${CLAUDE_SKILL_DIR}/../../references/implement-handoff-prompt.md` の雛形から組み立てろ。**必須項目は次の3つで、どれも落とすな**
   - 1行目に「`nt-developer:implement` を起動しろ」と、対象の Issue の URL
   - ワークツリーは既にあり、自分でブランチを切る必要が無いこと
   - 本体のセッションで既に決まっていて Issue の description に書かれていない判断（**原則として先に description へ書き戻し、プロンプト側には残すな**）
3. `--name issue-<番号>` と `--issue <番号>` を付けて `orca worktree create` を実行しろ。**ブランチ名は `issue-<番号>` に固定しろ**（日本語タイトルはそのままブランチ名に使うと扱いにくいため）
4. **作成したら自分は実装せず、ワークツリーの場所と Orca のカードで進捗を追えることだけを伝えて終われ。** 同じセッションで実装に入るな

**Orca が作るブランチは GitHub のリンク済みブランチではないため、Issue との紐付けは PR 本文の `Closes #<番号>` だけが担う**（`pr` skill が確認なしに付ける）。1つの Issue に PR を複数立てる例外での扱いは `plan` skill の `references/issue-route.md`「Issue と PR は 1 対 1 にする」にある。

## 実装中の運用

- 「実装ステップ」「触るファイル」のチェックボックスは、進捗が動くたびに `- [ ]` → `- [x]` に書き換えろ。計画側は人が読む永続記録であり、この計画だけが進捗管理の実体だ
- **GitHub Issue 経路でチェックボックスを更新するときも、`${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` に従え**（Write で一時ファイルに書き出してから `--body-file` で反映しろ。一括置換のワンライナーで直接 `--body` を組み立てるな）
- 実装中に判明した新事実・仕様変更は、その場で計画に追記しろ。後回しにするな
- **ただし次の2つは、ユーザーの確認を取ってからでないと計画に書くな。** 追記した時点で「決まったこと」として次のセッション・レビュー・PR 本文へ流れていくため、書いてしまえば誰にも止められない
  - 一部の対象にだけ与えられた根拠（特定のチケット・特定の画面についてのコメント・実測結果）を、根拠の及ばない他の対象へ広げて適用すること
  - よりどころにする資料（テストケース表・仕様書）に明記された期待値と違う挙動を採ること
  - 確認の手順と承認記録の書き方は `plan` skill の「よりどころにする資料から外れる判断・根拠の範囲外への適用」「承認記録の書き方」にある。**計画セッションで書かれていなかった判断を実装中に持ち込む場合も同じだ**
  - **承認が返ったら、計画の「検証・完了条件」を採用した挙動だけで書き換えるな。** 元の期待値を残したまま `plan` skill の「逸脱の記録は「検証・完了条件」に残せ」の表を更新しろ。完了条件を採用した挙動に合わせて書き直すと、実装がよりどころにする資料から外れている事実がレビューにも PR 本文にも一切現れなくなる
- **ユーザーから確認結果・判断根拠の発言（動作確認済み・検証済み等）を得たら、その場で計画に記録しろ。** 後回しにして同じ内容を再度説明させるな
- **PR の作業内容・スコープについて質問されたら、回答前に必ず対象の実装計画（Issue の description または `plans/` 配下）を(再)Read しろ。** 計画を一度も Read していない状態でスコープに関する質問に答えるな
- plans 経路では、実装中の計画書を `plans/進行中/<管理表>/` に置いたままにしろ（`plans/` の起点は本体のチェックアウトだ。詳細は `plan` skill の `references/plans-route.md`「配置・命名」を見ろ）。`plans/` 直下、`plans/レビュー中/` 配下、`plans/完了/` 配下のいずれにも置くな
- **今いるワークツリーの中で、`orca terminal create` / `orca terminal split` などで別の Claude セッションを起こして作業を分担するな。** 同じ作業ツリーを2つのセッションが同時に書くと、片方の編集がもう片方に上書きされる。並行させたいなら必ずワークツリーごと分けろ（`research` / `otel-analysis` の各 skill が自分の手順として起こす別タブは、ファイルを書かない委譲なので対象外だ）
- **実装ステップの先頭にリファクタのステップが置かれているなら、本命の実装より先に完了させろ**（`code-style` の「触る範囲の負債は本命の実装より先に直せ」節）。本命の変更が同じ関数・同じ行に入る見込みなら、そのステップが終わった時点で `/commit` を起動してリファクタだけをコミットしろ（**そのときは `/pr` へ連鎖するな**）。重ならないなら未コミットのまま残し、`commit` skill の分割判定に委ねろ
- **このセッションではコミットするな**（上のリファクタのステップだけが例外だ）。レビューは未コミットの差分に対して行う
- **実装ステップの `- [ ]` が全部埋まった、または一区切りついたら、レビューへ進む前に必ず下の「セッションを閉じる前にやること」へ進め。** ここで止まらずそのままレビューを起動すると、書き戻していない判断を持ったままレビューに入ることになる

## セッションを閉じる前にやること

セッションを閉じると会話が消える。**計画に書き戻していない判断は、次のセッションからは存在しないものになる。** 実装が一段落したら、必ずこの節をやってから終われ。

### 計画へ書き戻せ

- 実装ステップ・触るファイルのチェックボックスを、実際にどこまで終わったかに合わせろ
- 計画外で決めたこと・実装中に判明した事実・途中で捨てた案を計画に追記しろ。**次のレビューセッションでは、この計画が仕様として読まれる**（`code-review` が Issue の description / 計画書を仕様として読み込む）。古いままだと、意図して変えた実装をレビューが仕様違反として挙げてくる
- 更新のしかたは経路ごとに `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md`（Issue 経路）または計画書の直接編集（plans 経路）に従え
- **計画の「検証・完了条件」にマージ後でないと確認できない項目があると分かっているなら、その旨を実装ステップと同じ `- [ ]` のチェックボックス形式で書き足しておけ。** PR マージ時点でこの項目が残っていれば、`deploy-watch` skill へ自然につながる

### 終わり方

最後に、次に打つコマンドをそのままコピペできる形で1行出せ。

```
/nt-developer:review <Issue番号 または plans/進行中/<管理表>/<ファイル名>.md>
```

あわせて**作業ツリーに未コミットの変更が残っていること**を1行添えろ。別の作業を挟むなら、ブランチを切り替える前に気づける必要がある。

**サブ Issue の1本目が終わって次のサブ Issue へ渡すときも、必ずここで終われ**（`plan` skill の `references/issue-route.md`「Relationships / Sub-issues」節のとおり、サブ Issue は1つずつ別セッションで扱う）。同じセッションで次のサブ Issue に着手するな。
