# GitHub Issue の description に書く場合

書き込み先が Issue 経路に固定されたら、SKILL.md の「書き込み先の判定」から続けてこのファイルの手順を使え。

## Issue確定後の assignee/label 設定（新規作成・既存 Issue 選択の両方で行う）

Issue 番号が確定したら、`gh issue view <番号> --json labels,assignees` で現状を取得し、**空の項目だけ**埋めろ。すでに付いているものには触るな（assignee は他人が担当かもしれない、label は人が意図して選んだかもしれないため、上書き・付け替えを一切するな）。

- **assignee**: 取得結果が空なら埋めろ。新規作成時は `gh issue create --assignee @me` で作成と同時に、既存 Issue 選択時は `gh issue edit <番号> --add-assignee @me` で埋めろ。1人以上付いていれば何もするな
- **label**: 取得結果が空なら埋めろ。`nt-developer:pr` skill の「label の推定」節のルールをそのまま使え（変更ファイルの拡張子・パスから type を推定し、リポジトリの実在 label と AND を取って存在するものだけ付与する。対象ファイルは計画の「触るファイル」節に列挙したパス一覧とする）。新規作成時は `gh issue create --label <label>` で作成と同時に、既存 Issue 選択時は `gh issue edit <番号> --add-label <label>` で埋めろ。1つ以上付いていれば何もするな
- 推定結果が0件なら label は付けるな

## Issue確定後の Type とフィールド（Priority / Effort / Start date / Target date）の設定（新規作成・既存 Issue 選択の両方で行う。`gh` v2.94.0 以降が必要）

Type（Bug / Feature / Task の種別）と、組織で定義されたフィールド（Priority / Effort / Start date / Target date）も、assignee/label と同じ考え方で埋めろ。**すでに値が入っていれば触るな。空のものだけ埋めろ**（人が意図して入れた値を上書きしない）。

`gh` が v2.94.0 より古い、または `--type` の実行がフラグ未対応で失敗する環境では、Type 設定を諦めてスキップし、他の処理は止めずに続けろ。

**Type**:

- `gh api /orgs/<org>/issue-types` で組織に定義された Type 名の一覧を取得しろ。**名前を決め打ちするな**（組織ごとに定義が違う）
- `gh issue view <番号> --json issueType` で現状を確認し、既に設定されていれば触るな
- 空なら、計画の「背景」節を判定材料に以下の基準で選べ。**迷ったら Task にしろ**
  - Bug: 動いているはずの機能が期待通り動いていない。直すことが目的
  - Feature: 今まで無かった機能・仕組みを新しく足す
  - Task: それ以外すべて（既存構成の置き換え・削除・調査・ドキュメント更新・設定変更）
- 選んだ名前が取得した一覧に無ければ、Type 設定自体をスキップしろ
- `gh issue edit <番号> --type <name>` で設定しろ（新規作成時は `gh issue create --type <name>` でまとめてよい）

**フィールド（Priority / Effort / Start date / Target date）**:

まず定義と現在値の2つを取れ。**どちらも決め打ちするな**（フィールドの id・選択肢名は組織ごとに違う）。

- 定義: `gh api /orgs/<org>/issue-fields`。各フィールドの `name` / `id`（数値）/ `data_type`（`single_select` か `date`）/ 選択式なら `options` の名前が返る。目的のフィールドが定義されていなければ、そのフィールドだけスキップしろ
- 現在値: `gh api repos/<owner>/<repo>/issues/<番号>/issue-field-values`。**ここに出てくるフィールドは既に人が入れた値なので対象から外せ**

空だったフィールドだけを、以下の基準で埋めろ。

- **Priority**（選択式。Urgent / High / Medium / Low 相当）: 計画の「背景」節を判定材料にしろ
  - Urgent: **自動では付けるな**（本番障害は Issue を書く前に対応が動いているのが通常で、後から人が付ける）
  - High: 外部由来の期限がある（AWS の適用期限・証明書の期限・サポート終了）、または本番のユーザーに影響が出ている不具合
  - Medium: 期限は無いが実施が決まっている改善
  - Low: やるかどうか自体をこれから決める調査
- **Effort**（選択式。High / Medium / Low 相当）: 計画の「実装ステップ」「触るファイル」節の分量で決めろ
  - High: 複数のプラグイン・複数の領域にまたがる（触るファイルが5つ以上、または実装ステップが5つ以上）
  - Medium: 1つのまとまりの中で複数ファイルを触る（実装ステップが2〜4つ）
  - Low: 1ファイルの修正で終わる
- **Start date**（日付）: 着手日を入れろ。`TZ=Asia/Tokyo date '+%Y-%m-%d'` で当日を取れ
- **Target date**（日付）: 完了目標日を入れろ。**推測で埋めるな**
  - 外部由来の期限が計画に書かれているならその日付を使え
  - 対象リポジトリの運用（README 等）が一気通貫の自動進行を明記している場合は当日で埋めろ（その日のうちにマージまで終わる運用だ）
  - 期限の手がかりが無ければ AskUserQuestion で聞け（選択肢は「今日」「今週末」「来週末」「設定しない」を基本にし、実際の日付を括弧で添えろ）。「設定しない」が選ばれたらこのフィールドだけ空のままにしろ

設定は Write でファイルに書き出してから `gh api --method POST /repos/<owner>/<repo>/issues/<番号>/issue-field-values --input <ファイル>` で行え（ボディがネストした配列のため、フラグの直接指定では組み立てられない）。**空だったフィールドを1回の POST でまとめて送れ**。ファイルの中身:

```json
{"issue_field_values": [
  {"field_id": <Priority の id>, "value": "Medium"},
  {"field_id": <Effort の id>, "value": "High"},
  {"field_id": <Start date の id>, "value": "2026-08-13"},
  {"field_id": <Target date の id>, "value": "2026-08-20"}
]}
```

- 選択式は選択肢の **name をそのまま文字列で** 渡せ（id を渡すな）。日付は **`YYYY-MM-DD` の文字列**で渡せ
- **必ず POST を使え。PUT は既存の値を全部消して置き換える仕様のため、送らなかったフィールドの値まで消してしまう**

## Issue と PR は 1 対 1 にする

**1つの Issue に対して PR は1本だ。** 1つの Issue の中身を複数の PR に分けたくなったら、PR を分けるのではなく **Issue 自体をサブ Issue に切り分けて、それぞれに PR を1本ずつ立てろ**。

- 「実装ステップが独立した PR に分かれそうだ」と気付いた時点がサブ Issue を切るタイミングだ。計画を書き切ってから考えるな
- 逆に、複数の Issue の内容を1本の PR にまとめるな。どちらの Issue も PR から追跡できなくなる
- 例外にできるのは、ユーザーが「まとめて1本で出す」と明示したときだけだ

**例外: 実装ステップ自体は独立していないが、その前提となるブロッカー（hook の不具合等）だけを先に解消してマージする必要が生じた場合**、サブ Issue には切らずこの Issue のまま複数の PR を出してよい。この場合は以下を守れ。

- **2本目以降のワークツリーは `--name issue-<番号>-2`（3本目以降は `-3` と連番）で作れ**（作りかたは `git-rules` にある）
- **実装ステップが全部終わるまで、どの PR の本文にも `Closes #<番号>` を書くな。** 書いたぶんの PR がマージされた瞬間に Issue が close され、残りの実装ステップが未着手のまま閉じる。`pr` skill は GitHub Issue 経路で確認なしに `Closes` を付ける挙動なので、生成された本文からこの行を消してから PR を出せ
- 最後の PR にだけ `Closes #<番号>` を残せ
- それでも close されてしまったら `gh issue view <番号> --json state --jq .state` で確認し、`CLOSED` なら `gh issue reopen <番号>` で復旧しろ

## Relationships / Sub-issues（自動で張らない。`gh` v2.94.0 以降が必要）

Relationships（他の Issue との依存関係）と Sub-issues（親子関係）は自動で設定するな。誤って張ると相手側の Issue まで巻き込む。候補が見つかったら提示し、張ってよいか確認を取れ。判定材料は計画の本文（「背景」「実装ステップ」「未解決事項」「今回やらないこと」節）なので、それらを書き終えてから行え。

**サブ Issue を新しく作ること自体に確認が必要だ。**「事前確認はするな」が許しているのは親 Issue の本文を黙って書くことだけで、作業単位を分ける判断は含まない。サブ Issue に切ると以降その単位で PR・レビュー・マージが走り、後からまとめ直せない。**確認を取らずに複数のサブ Issue を作るな。**

**1つのサブ Issue は1セッションで扱え。** 対象リポジトリの `CLAUDE.md` が「計画・実装・レビューを1セッションで通せ」と明記していても、**次のサブ Issue へ進むときは必ずセッションを分けろ**。同じセッションで複数のサブ Issue を連続処理すると、前のサブ Issue の会話・判断・思い込みがそのまま次に引きずられ、この skill がセッションを分けている目的そのものが崩れる。1本目のサブ Issue が終わったら、次のサブ Issue の番号を引き継ぎとして出して終われ。

- **Sub-issues**: 上の「Issue と PR は 1 対 1 にする」に従い、実装ステップが独立した PR に分かれる見込みなら**サブ Issue に切る前提で**候補を出せ。1つの PR で終わる規模なら分けるな。承認されたら子 Issue を `gh issue create` で作り、親側で `gh issue edit <親番号> --add-sub-issue <子番号>,<子番号>` で紐付けろ
   - **`--add-sub-issue` を実行する前に、紐付け先の親候補が既に別の Issue の子（sub-issue）になっていないか `gh api graphql` で確認しろ。** 既に子になっている場合、その親の親（祖父）を新しい子の親にしろ（孫 issue 構造を作るな）
- **Relationships**: 計画の「未解決事項」節に「〜が終わってから」のように他の Issue への依存が書かれている場合だけ候補にしろ。同じ領域の話題というだけでは候補にするな。承認されたら `gh issue edit <番号> --add-blocked-by <相手番号>` / `--add-blocking <相手番号>` で張れ

## 書く前に既存の description を全文読め

- `gh issue view <番号> --json body --jq .body` で現在の description を取得し、**全文読め**
- 取得した内容を捨てるな。報告者が書いた再現手順・要望・判断材料はテンプレートの「背景」「現状」に取り込め
- 上書き前に元の description を退避しろ（`gh issue view <番号> --json body --jq .body > <スクラッチパッド>/issue-<番号>-body-before.md`）。全面上書きになるので、取り込み漏れに気づいたときに戻せるようにしておく

## テンプレート

`${CLAUDE_SKILL_DIR}/references/issue-body-template.md` の見出しの並びをそのまま使え。plans 用のテンプレートとは別物だ（Issue は他の人が読む場所なので、ローカルパス・個人メモを書かない前提になっている）。「AsIs」「ToBe」のような英語略語は使うな。「現状」「変更後」とプレーンな日本語で書け。

## 反映のしかた

`${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` を Read し、その手順に従え（`implement` / `review` skill と共有している）。

## 事前確認はするな

- **本文を会話に貼り出して承認を求めるな。黙って作成 / 更新し、結果（Issue の URL と何を書いたかの要点）だけ報告しろ。** Issue は後から編集できて履歴も残るため、書く前に全文を承認させる意味がない（長い本文を毎回貼られる方が読みにくい）
- 報告は数行に収めろ。description の全文を報告に再掲するな（Issue を開けば読める）
- ただし **既存の description を読まずに上書きするのは禁止だ**（このファイルの「書く前に既存の description を全文読め」節の手順）。確認を取らない代わりに、消していい内容かどうかは自分で確かめろ。取り込むか迷う記述があれば、消す前にその点だけ聞け
- 判断を仰ぐのは「既存の description に、計画のどのセクションにも収まらない記述があって、残すか消すか決められないとき」だけにしろ
