# 実装計画ワークフロー（書く前に読め）

実装計画は「まず計画を書く→それを元に実装する→まだコミットせずに計画をもとにレビューしてもらう」という一連の作業の起点になる。同梱の hook が、`plan` / `implement` / `review` のいずれも未起動のままの編集・状態変更を block する。

**この SKILL.md には計画セッションの手順だけを書いてある。** 実装は `implement` skill、レビュー以降は `review` skill が担当する。経路が決まってからの詳細手順は `references/` 配下に分けてあり、必要になった時点で Read する。読み取り調査だけで終わる依頼（下の「何を作るか判定しろ」で「何も作らない」に該当）では、どのファイルも読む必要が無い。

| 詳細手順 | いつ読むか |
|---|---|
| `${CLAUDE_SKILL_DIR}/references/issue-route.md` | 書き込み先が GitHub Issue に決まったとき |
| `${CLAUDE_SKILL_DIR}/references/plans-route.md` | 書き込み先が `plans/*.md` に決まったとき |
| `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` | Issue の description を書き換えるとき |
| `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` | plans 経路で作業中の計画書を記録するとき |
| `${CLAUDE_SKILL_DIR}/../../references/quality-axes.md` | 実装差が出る分岐の優劣を判断するとき |

## 呼ばれ間違いの検出

**この skill は計画を書くセッション専用だ。** 計画が既に書かれていて、実装ステップに `- [ ]`（未完）が残っている状態でここへ来ているなら、それは `implement` の担当だ。`/nt-developer:implement` を案内して止まれ。未完が残っておらず未コミットの変更があるなら `review` の担当だ。`/nt-developer:review` を案内して止まれ。

## この一連の作業は複数のセッションに分かれる

**計画・実装・レビューはそれぞれ別の Claude Code セッションで行え。** 実装した本人の会話に判断が引きずられた状態でレビューしても、同じ思い込みを見逃す。**この skill 自身は「対象リポジトリの運用次第で一気通貫にしてよいか」を判定する手続きを持たない。** 対象リポジトリの `CLAUDE.md` に別の運用が明記されているなら、その指示はこの skill の既定動作より優先される（`CLAUDE.md` はプロジェクト固有の指示として常に優先されるため、この skill 側で「明記されているかどうか」を毎回確認する必要は無い）。明記が無いリポジトリでは、この既定動作（別セッションで行う）がそのまま適用される。

| セッション | 起動する skill | やること | 終わり方 |
|---|---|---|---|
| **計画セッション** | `plan`（この skill） | 計画を Issue の description（または `plans/*.md`）に書く | 実装の承認をもらって終わる。実装はしない |
| **実装セッション** | `implement` | 計画に沿って実装する。**コミットはしない** | 計画へ書き戻して終わる |
| **レビューセッション** | `review` | レビューを起動する → 指摘の採否を決める → 修正する → コミット → PR | PR を出して終わる（マージ後の動作確認が要らない計画はここで完結） |
| **マージ後確認セッション**（計画の「検証・完了条件」にマージ後の動作確認が必要と書かれている場合のみ） | `deploy-watch` | デプロイの完了を待ってから実際の環境で動作確認する | 確認結果を計画に追記して終わる |

- **セッションを跨いで引き継がれるのは計画だけだ。** 会話の進捗はセッションを閉じた時点で消える。だから各セッションの入口で計画を読み直し、出口で計画へ書き戻す
- 実装セッションは、context が尽きて途中で閉じることがあるため複数回に分かれてよい。何回目でも入口・出口の手順は同じだ
- **サブ Issue に切った場合は、サブ Issue 1つごとに上の表を1周回せ。** 対象リポジトリが一気通貫の運用でも、**次のサブ Issue へ進むときは必ずセッションを分けろ**。そもそもサブ Issue に切ること自体にユーザーの承諾が必要だ（`${CLAUDE_SKILL_DIR}/references/issue-route.md` の「Relationships / Sub-issues」節）
- **セッションの終わりに確認を取るときは、そのセッション自身の成果物を確定していいかを聞け。次のセッション・次の工程へ進んでいいかを聞く形にするな。** 「進めていい？」のような言い方は、承認が返った瞬間に自分がそのまま次の工程へ入るような含みを持たせてしまう。計画セッションなら「この計画の内容で確定していいか」、実装セッションなら「この実装で確定していいか」、レビューセッションなら「このレビュー結果で確定していいか」と聞け。これは表の4セッションすべてに共通する

**この skill は計画書を作るためだけのものではない。作らないという判定もここで行う。** まず下の「何を作るか判定しろ」で3つのどれかを選べ。

書く場合の書き込み先は2通りある。

- **GitHub Issue の description**: そのリポジトリを GitHub Issue で課題管理している場合。計画がチームから見え、チケットと計画が1箇所に集まる
- **`plans/<状態>/<管理表>/*.md`**: GitHub Issue で課題管理していない場合。個人の Git 設定で除外されたローカル専用ファイル

## 何を作るか判定しろ（起動したら最初にこれをやる）

| 判定 | どういう依頼か | やること |
|---|---|---|
| **何も作らない** | 読み取り調査・質問への回答だけで終わる。コードもファイルも設定も変えない | この skill の残りは読まなくていい。`references/` も開くな。そのまま答えろ |
| **会話の出力画面に提示するだけ** | 単一ファイル・数十行程度の変更、設定ファイルの追記・修正、リポジトリ外の作業（`~/.claude` 配下 等） | 下の「会話の出力画面に提示するときの書き方」に従え。ファイルは作るな |
| **Issue か plans に書く** | 複数ファイルにまたがる実装、機能追加、チケットのある作業、実装中に判断を積み上げる作業 | 下の「書き込み先の判定」へ進め |

**判定の軸を「触るファイルの数」だけにするな。** ファイルを1つも触らない調査タスクでも、判断を積み上げるものは書く側に入れろ。実際に、移行データの欠損項目を洗い出す調査タスクでは、プロダクトコードを一切変更しないにもかかわらず、判定軸の設計・優先度のランク定義・採らなかった案の記録が必要で、実装ステップ7つの計画書になった。**「何を判断したかを後から辿る必要があるか」で決めろ。**

迷ったら書く側に倒せ。書きすぎて無駄になるコストより、判断の経緯が残らないコストのほうが大きい。

### 会話の出力画面に提示するときの書き方

ファイルを作らない場合も、見出しの構成は `${CLAUDE_SKILL_DIR}/references/plan-template.md` と同じものを使え（冒頭の要約→実装ステップ→確認テスト→計画書レビュー→決めたこと→参照→背景→現状→変更後・対応内容→検証・完了条件→採らなかった案→この判断を覆す条件→触るファイル→未解決事項→今回やらないこと）。埋まらない見出しは省いてよい。

作業を進めるうちに規模が大きいと分かったら、その時点でファイルに落とし直せ。最初の判定に縛られるな。

**実装の承認を得たあとは、確認を挟まず `/commit` を起動しろ。** 「この内容でコミットしていいですか」を `/commit` の起動前に聞くな。コミットの確認は `/commit` の中の「コミット実行前の最終確認」で1回だけ取る。`/commit` 後の `/pr` 起動まで含め、対象リポジトリの `CLAUDE.md` に一気通貫の運用が明記されていればそれに従え。

### 実装に着手する前に承認を取れ

計画を書くこと自体に承認は要らない（Issue は `${CLAUDE_SKILL_DIR}/references/issue-route.md` の「事前確認はするな」節のとおり黙って作れ）。**承認が要るのは実装・設定変更・副作用のある実行に着手する瞬間だ。**

- 計画を書き終えたら「この計画の内容で確定していいか」を聞き、**明示的な承認が返るまで着手するな**
- 「良さそう」「見た」「なるほど」を承認と解釈するな
- 承認の範囲は提示した内容だけだ。途中で計画外の変更が必要になったら、その分を提示して改めて承認をもらえ
- **「これ以外は全部それでいい」のような部分的な承認発言を、その後の全工程（設定変更・マージ・タグ作成まで）の許可と拡大解釈するな**。承認は明示された内容の範囲だけだ
- **疑問形の発言（「〜で良くね？」「〜ですか？」）を実行指示と誤解するな**。疑問文はまず確認を求めているだけで、実行の承認ではない
- **作業の分け方を変える判断（サブ Issue への分割・PR を複数に分ける・スコープの拡大）も承認の対象だ。** 計画の中身への承認をもらっただけで、作業単位まで自由に決めていいと解釈するな
- 例外は1つだけだ: ユーザーが「計画はいいから直接やって」と明示したとき

### 着手を止めろ（承認をもらっていても、これに当たったら止まって確認しろ）

次のいずれかに当たったら、実装に入る前に止めてユーザーへ確認しろ。**確認せずに自分の判断で進むな。**

- **チケットに対象範囲（対象ページ名・URL・画面）の記載が無い。** 「たぶんこの画面だろう」で対象を決めるな。どの画面・どの機能までを含むかを確認しろ
- **既存構成と違う置き方をする**（新規ディレクトリ・新規 Controller・新しい層の追加）。既存の置き場所に収まらないと判断したなら、その判断自体を確認しろ
- **一般的なベストプラクティスと既存実装が食い違っており、どちらに寄せるかで実装が変わる。** 既存に合わせるか理想に寄せるかを勝手に決めるな

止まって確認した結果は、決めた理由を1行添えて計画の「決めたこと」表に書け。

書く場合は、以降の手順を順番に守れ。

## 書き込み先の判定

- **対象リポジトリの `CLAUDE.md` / `README.md` に運用が明記されているか確認しろ**。「plans は使わない」「実装計画は GitHub Issue の description で管理する」のような明記があれば Issue 経路に、「plans を使う」のような明記があれば plans 経路に、確認を取らず固定しろ。曖昧な記述で判断するな、明記されているときだけ適用しろ
- **明記が無ければ無条件で plans 経路に固定しろ**。`gh repo view` で Issues の有効性を確認する処理・`gh issue list` で運用実態を推測する処理・AskUserQuestion での確認は一切行うな。**Issue が何件か存在すること自体は「そのリポジトリが実装計画をGitHub Issueで管理している」証拠にならない**（バグ報告用に数件 Issue が立っているだけのリポジトリを「運用中」と誤判定し、計画とは無関係な新規 Issue を黙って作ろうとした事故が実際に起きた）。他のチケット管理と併用しているリポジトリでも同様だ（Issue の description 更新は手間が大きく、更新を追従させ続けるコストに見合わないため plans 経路で構わない）。GitHub Issue 経路を使わせたい場合は、ユーザーが CLAUDE.md / README に明記するか、その場で明示的に指示しろ
- Issue 経路に固定された場合のみ、以下へ進め:
  - **Issue 番号を検出しろ**: 引数・カレントブランチ名（`git symbolic-ref --short HEAD`）・直近のユーザー発言から `#123` / `123-xxx` / Issue の URL を探せ
  - 検出できた場合、`gh issue view <番号> --json state` が `CLOSED` なら別の新しい作業だ。その番号を捨てて Issue を作り直せ（カレントブランチが前の作業の `issue-<番号>` のまま残っていることがあり、ブランチ名だけで番号を採ると閉じた Issue の description を上書きする事故になる）
  - 検出できなければ `gh issue list --state open --limit 10 --json number,title` を取得し、AskUserQuestion で「既存の open Issue から選ぶ／新しい Issue を作る」を確認しろ。**「既存の open Issue から選ぶ」が選ばれた場合のみ**、一覧を新規の AskUserQuestion で提示しろ（依頼内容と明らかに無関係な Issue を関連性の判定なしにそのまま選択肢へ混ぜるな。関連しそうな Issue が無ければその旨を伝え、「新しい Issue を作る」への切り替えを促せ）
  - 「新しい Issue を作る」なら `gh issue create` で作れ（assignee・label・Type・Priority は作成直後に `${CLAUDE_SKILL_DIR}/references/issue-route.md` の各設定節で埋める）。**タイトルと本文を先に提示して承認を求めるな**（同ファイルの「事前確認はするな」）。作ったら URL を報告しろ

## 計画セッションの入口手順

- **Issue 経路のみ**: `${CLAUDE_SKILL_DIR}/references/issue-route.md` を Read し、「Issue確定後の assignee/label 設定」「Issue確定後の Type とフィールドの設定」を実行しろ。Relationships / Sub-issues の候補提示は、計画の本文を書き終えたあとで構わない
- **plans 経路のみ**: `${CLAUDE_SKILL_DIR}/references/plans-route.md` を Read し、配置・命名に従え。あわせて `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` の手順で作業中の計画書を記録しろ
- **作業ブランチもワークツリーも作るな。** 計画セッションは実装しないセッションなので、使われないまま残る。どちらも `implement` skill の入口で作る
- そのあと下の「書く前の聞き取り」へ進め
- **このセッションでは実装するな。** 計画を書き終えたら「実装に着手する前に承認を取れ」に従って承認を取り、承認が返ったら下の「終わり方」の形で次に打つコマンドを案内して終われ
- 例外は「実装に着手する前に承認を取れ」の例外と同じだ（ユーザーが「計画はいいから直接やって」と明示したとき）。その場合は同じセッションで `implement` skill を起動して続けろ

## 書く前の聞き取り（経路共通）

**書く前に質問するな。まず調べろ。** 次の4段階を順番に守れ。

1. **先に調べろ。調べる前に質問するな。** 対象のコード・よりどころにする資料・関連ドキュメントを読み終えるまで、次の「分岐を全部列挙しろ」に入るな
2. **実装差が出る分岐を全部列挙しろ。** 方式・配置・命名・エラー処理・テストの書き方など、実装の結果に差が出るものは小さく見えても落とすな
3. **1問ずつ `AskUserQuestion` で確定しろ。** 複数の分岐を1回にまとめるな。確定したものを計画の「決めたこと」表に書け
4. **計画本文を書き終えたら確認テストを必ず行え。** 下の「確認テスト」の観点のうち該当するものだけを断定文にして、1件ずつ `AskUserQuestion` で提示しろ。**計画へ書くだけで提示を省くことは絶対にするな**
5. **確認テストに合格したら、Skill ツールで `nt-developer:plan-review` を起動しろ。** 書いた計画そのものを読み直して抜けを探す手順だ。**承認を求めるのはこれが終わってからだ**

確定した内容は次の3つのどれかに必ず分類して書き分けろ。**分類する前に、その判断の根拠が「誰が・いつ・どの対象について」出したものかを必ず確認しろ**

- **よりどころにする資料に明記されている**: そのまま書け
- **よりどころにする資料には無く、この場でユーザーと決めた**: 見出しに `(よりどころにする資料に無いため今回決定)` と明示しろ
- **よりどころにする資料に明記された期待値と違うことをやる／根拠の及ばない対象へ広げる**: 下の「よりどころにする資料から外れる判断・根拠の範囲外への適用」に従え。**この分類を上の2つに丸めるな**

### 一次ソースの原文を引用しろ（引用が無い行は実装に進めない）

**仕様解釈を書く行には、必ず引用元の原文をそのまま貼れ。** 要約・言い換えで書くな。「仕様書にこう書いてある」と書いた行に原文が無いなら、それはお前の解釈であって仕様ではない。

- 引用の形は「<どのシート／チケット／画面>の<どこ（行・列・見出し・コメントの日付）>に、こう書いてある: <原文>」だ。**出所と原文の両方を書け**
- 一次ソースは Google Sheets の仕様書・テストケース表・GitHub Issue / PR の本文とそのコメントだ。**他の人の要約・会話の記憶・過去の実装を一次ソースとして引くな**
- 原文が見つからない項目は「よりどころにする資料に無いため今回決定」に分類しろ。見つからないまま解釈として書くな
- **引用が1行も無い仕様解釈を持ったまま実装へ進むな。** 承認を求める前に引用を埋めろ

そのうえで、引用元が名指ししている対象と、今回その解釈を適用する対象が一致するかを**対象ごとに1問ずつ確認テストで提示しろ**（下の「確認テスト」の観点に含まれる）。一致しない対象があるなら、次の節に従ってユーザーの承認を取れ。

**チケットの期待結果と今回採る実装が食い違うなら、チケット側の期待結果の更新依頼を「検証・完了条件」のチェックボックスに入れろ。** 実装だけ変えてチケットを放置すると、次に読む人が古い期待結果を正としてまた差し戻す。

### よりどころにする資料から外れる判断・根拠の範囲外への適用（確認なしに計画へ書くな）

**根拠の適用範囲は、その根拠を出した人が名指しした対象までだ。** 特定のチケット・特定の画面について依頼者が出した判断（コメント・実測結果・口頭での確認）を、「同じ種類の問題だから」という類推だけで他のチケット・他の画面へ広げるな。**範囲を広げること自体が独立した判断であり、ユーザーの承認が要る。**

同じく、よりどころにする資料（テストケース表・仕様書）に明記された期待値と違う挙動を採る判断にも、ユーザーの承認が要る。「実機で確かめた」「新しい判断だから当初の期待値より優先する」は、お前が単独で決めてよい理由にならない。

どちらかに当たったら、計画に書き込む前に必ずこの順でやれ。

1. 根拠の出所（誰が・いつ・どの対象について言ったか）と、今それを適用しようとしている対象の一覧を並べて、**根拠が及んでいない対象を特定しろ**
2. その対象について、AskUserQuestion で「この根拠は<出所の対象>に限定されているが、<及んでいない対象>にも同じ方式を採用してよいか」を明示して確認しろ。**対象をまとめて1回で聞くな。** 承認の範囲は対象ごとに分かれるので、まとめて聞くと承認されなかった対象が後から分からなくなる
3. 承認が返った対象だけを、下の「承認記録の書き方」の形で計画に書け。**承認が返らなかった対象はよりどころにする資料の期待値どおりに実装しろ**

### 承認記録の書き方

**「ユーザー承認済み」「合意済み」「決定」と書けるのは、この会話の中でユーザー本人が明示的に承認を返した項目だけだ。** チケットのコメント・仕様書の記述・他の人の発言を根拠にした判断へこの表現を使うな（それらは「よりどころにする資料に明記」または「<出所>のコメントによる」と書け）。

承認を得た項目は、対象範囲ごとに次の形で1行ずつ残せ。**複数の対象を1行にまとめるな。**

```
- <対象（チケットID・画面名）>: <何を承認したか> — ユーザー承認済み（<YYYY-MM-DD>）
```

### 逸脱の記録は「検証・完了条件」に残せ

**逸脱がある対象について、「検証・完了条件」を採用した挙動だけで書き換えるな。** 完了条件は後工程（実装・レビュー・PR 本文）が「何をもって正しいとするか」を読む唯一の場所であり、そこから元の期待値が消えると、逸脱していること自体が誰にも見えなくなる。

逸脱を承認された対象は、「検証・完了条件」に次の表を必ず置け。**元の期待値の行を消すな、書き換えるな。**

```
### よりどころにする資料からの逸脱

| 対象 | よりどころにする資料の期待値（出所） | 採用した挙動 | 根拠の出所と適用範囲 | 承認 |
|---|---|---|---|---|
```

- **よりどころにする資料の期待値**は、よりどころにする資料に書かれている文言のまま写せ。要約するな
- **根拠の出所と適用範囲**には「誰が・いつ・どの対象について出した根拠か」と「その根拠が及ぶ対象はどこまでか」の両方を書け。根拠の対象を書かずに「実測済み」「確認済み」だけを書くな
- **承認**は上の「承認記録の書き方」の形式で、対象ごとに1行ずつ書け
- 逸脱が1件も無いなら、この見出しと表ごと書くな

## 決めることを並べて選ばせる（1問ずつ AskUserQuestion）

上の4段階の2番目・3番目にあたる手順の詳細だ。調査が終わったら、実装の結果に差が出る分岐を全部書き出せ。方式・配置・命名・エラー処理・テストの書き方のように小さく見えるものも対象に含めろ。書き出した分岐は、複数をまとめて1回に聞かず、1問ずつ `AskUserQuestion` で確定しろ。確定した案は計画の「決めたこと」表（`| 何を決めるか | 選べた案 | 決めた案 |`）へ1行ずつ追記しろ。未確定のまま残す行を作るな。

- **どの案が優れているかは `${CLAUDE_SKILL_DIR}/../../references/quality-axes.md` の判断軸で決めろ。** 動くかどうかだけで方式を選ぶな
- **既存の書き方・置き場所に前例があり、それに合わせれば決まる分岐は聞くな。** 既存に合わせて計画へ書け。前例と違う置き方をするときだけ「着手を止めろ」節に従って確認しろ
- **質問文と選択肢には、その案を採ると実装がどう変わるかを必ず添えろ。** 案の名前・専門用語だけを並べるな。伝わらずに聞き返される回数がそのまま確認の回数に乗る

## 確認テスト（計画本文を書き終えたら行う）

Claude が計画を読み、下の観点のうち該当するものだけを、具体的な中身を埋めた断定文にして提示しろ。設問の形にするな。

- **提示は1件ずつ `AskUserQuestion` で必ず行え。** 複数件をまとめて1回の出力に並べるな。**計画へ書くだけで提示を省くことは絶対にするな**
- **`AskUserQuestion` の質問文には、計画へ書く断定文をそのまま使え。** 言い換えるな、短くするな。同梱 hook が計画の断定文と実際に投げた質問文を突き合わせ、対応する質問が無い断定文が1件でもあれば「確認テスト: 合格」の書き込みを deny する
- **「確認テスト: 合格」を書き込むときは、「該当した観点」の一覧を必ず同じ書き込みに含めろ。** 合格の1行だけを後から足す書き込みは deny される
- **同じセッションの分岐確定でユーザー本人が選んだ内容を言い直しただけの観点は、必ず該当なしへ回せ。** 判定理由に「同一セッションで確定済み」と書いて残せ。確認テストは Claude が独断で置いた前提を見せるためのものだ。ユーザー自身が選んだ内容を断定文にして「その通り／違う」で聞き直すな
- **該当なしと判定した観点は、判定理由を1行ずつ添えて一覧で出せ。** 都合の悪い観点を握りつぶしていないかを読み手が確認できるようにするため
- 提示した内容が計画と食い違うと分かったら計画を直せ。**食い違いがゼロになるまで「確認テスト: 合格」と絶対に書くな**

観点（この中から該当するものだけを選ぶ）:

| # | 観点 |
|---|---|
| 1 | よりどころにする資料に書かれた期待値と違う実装を採っている |
| 2 | 判断の根拠が、その根拠を出した人が名指しした対象を越えて適用されている |
| 3 | マージした時点で本番に副作用が出る |
| 4 | マージの前後に人が手でやる作業があり、順序を間違えると壊れる |
| 5 | 同じ原因を抱えているのに今回の対象から外した箇所がある |
| 6 | 仕様解釈の行に一次ソースの原文引用が無い |
| 7 | 引用元が名指ししている対象と、その解釈を適用する対象が一致していない |

引用に関する2観点（原文引用が無い／適用する対象が一致していない）は**対象ごとに1問ずつ提示しろ**。複数の対象・複数の引用をまとめて1回で聞くな。

## 計画書レビュー（確認テストに合格したら行う）

**確認テストに合格したら、実装の承認を求める前に Skill ツールで `nt-developer:plan-review` を起動しろ。** 手順はその skill が持つ。ここでやることは起動だけだ。

- **確認テストの前に回すな。** 確認テストでユーザーが計画を変えることがあり、先にレビューすると変わった後の計画を誰も読み直さない
- **別セッションに分けるな。** 計画を書いた会話を持ったまま回せ
- レビューが終わって `計画書レビュー: 合格` を計画へ書いてから、下の「実装に着手する前に承認を取れ」へ進め（同梱 hook が、この記録が無い計画での実装の編集を deny する）

## 実装ステップの粒度

**実装ステップは意味のある対応の単位で書け。ファイル1つにつき1ステップへ機械的に分割するな。** 関連する複数ファイルの変更は1つのステップにまとめ、全体を人が一目で確認できる分量（目安5ステップ以内）に収めろ。どのファイルを触るかは「触るファイル」節が持つので、ステップ側でファイルを列挙するな。まとめても5ステップに収まらないなら、1つの作業単位に収まらない規模を疑い、サブ Issue に切る候補として提示しろ（分ける判断には承認が要る）。

**触る範囲に規約違反の既存コードがあるなら、それを直すリファクタを実装ステップの先頭に独立した1ステップとして置け**（判定基準は `code-style` の「触る範囲の負債は本命の実装より先に直せ」節が持つ）。直す範囲をステップに明記して承認の対象に含めろ。違反が1件も見つからなかったならステップを置くな。

聞き取り・分岐の確定・確認テストが済んだら、経路に応じて `${CLAUDE_SKILL_DIR}/references/issue-route.md` または `${CLAUDE_SKILL_DIR}/references/plans-route.md` を Read し、テンプレートに沿って計画を書け。

## 終わり方

承認が返ったら、次に打つコマンドをそのままコピペできる形で1行出して終われ。

```
/nt-developer:implement <Issue の URL または計画書のパス>
```

**サブ Issue に切った場合、1本目のサブ Issue が終わるまで次のサブ Issue へ進むな**（`${CLAUDE_SKILL_DIR}/references/issue-route.md` の「Relationships / Sub-issues」節）。
