# レビューセッションの手順

実装セッション（`implement` skill）が残した未コミットの差分をレビューし、コミット・PR まで進めるためのセッションだ。同梱の hook が、`plan` / `implement` / `review` / `deploy-watch` のいずれも未起動のままの編集・状態変更を block する。

**この skill は `code-review` そのものではない。** それを呼び出す側の、セッションの入口と前後の手順だ。

| 詳細手順 | いつ読むか |
|---|---|
| `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` | Issue の description を書き換えるとき |
| `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` | plans 経路で作業中の計画書を記録するとき |
| `${CLAUDE_SKILL_DIR}/../../references/post-merge-handoff.md` | `gh pr merge` が成功した直後 |
| `${CLAUDE_SKILL_DIR}/../../references/quality-axes.md` | レビュー skill を使わない運用のリポジトリで差分を自分で読むとき |

## 呼ばれ間違いの検出

**この skill はレビュー対象の差分があることが前提だ。** 計画の実装ステップに `- [ ]`（未完）が残っていて、未コミットの変更も無いなら、それは `implement` の担当だ。`/nt-developer:implement` を案内して止まれ。計画そのものが無いなら `plan` の担当だ。`/nt-developer:plan` を案内して止まれ。

## 入口でこれを全部やれ

**このセッションでは自分は実装していない。** 差分の中身を知らない状態から始まることを自覚しろ。

- **Issue 経路**: `gh issue view <番号> --json body --jq .body` で description を**全文読め**
- **plans 経路**: 計画書を Read で**全文読め**。あわせて `${CLAUDE_SKILL_DIR}/../../references/plan-record.md` のコマンドで記録を上書きしろ
- `git diff` で変更内容を読め。**レビューを起動する前にやれ**（レビュー結果の採否を判断するのに差分の把握が必要で、あとから読むと指摘に引きずられる）
- **計画に書かれた判断の根拠と、それを適用している対象がずれていないか照合しろ。** 一部のチケット・一部の画面についてのコメント・実測結果を根拠に、他の対象まで同じ方式で実装していないかを見ろ。ずれていて、そのずれについての承認記録が計画に無ければ、**レビューを起動する前にユーザーへ確認しろ**（`plan` skill の「よりどころにする資料から外れる判断・根拠の範囲外への適用」）。コードの正しさだけを見ていると、この種の逸脱は最後まで誰にも止められずマージまで進む
- **よりどころにする資料が挙動として明記している期待値（発火タイミング・表示位置・表示文言・順序・遷移先）と、実装した挙動を1つずつ突き合わせろ。** 計画の「検証・完了条件」に「よりどころにする資料からの逸脱」の表があるなら、その表に載っている対象だけが逸脱していい範囲だ。**表に無いのに期待値と違う挙動になっている対象が1つでもあれば、レビューを起動する前にユーザーへ確認しろ**（`plan` skill の「逸脱の記録は「検証・完了条件」に残せ」）。完了条件が採用した挙動を基準に書かれていると、完了条件を満たしているだけでよりどころにする資料と食い違ったまま通る
- **レビュー中に実装差が出る新しい判断が必要になったら、レビューを進める前に計画の「決めたこと」表へ追記し、確認テストをやり直せ。** 追記しないままレビューを進めると、新しい判断が誰にも確認されずマージまで進む

PR が既にマージ済みで、計画の「検証・完了条件」に未完のチェックボックス（`- [ ]`）が残っている場合、この skill の担当ではない。`/nt-developer:deploy-watch` を案内して止まれ。

**ここで読むのは前提の把握と計画との突き合わせのためだけだ。コードの正誤検証をこの節でやるな。** 差分そのものが正しく動くかの裏取り（依存ライブラリ・`vendor` 配下・フレームワーク内部を読んで挙動を確かめる、実装の代替案を検討する）を始めたら逸脱している。正誤検証は下の「レビュー起動」を経て、返ってきた指摘の採否を一件ずつ決める段でやれ。**上の項目を終えたら、それ以上調べるな。次の節へ進め。**

## レビュー起動

**上の入口手順が終わったら、他に何をする前でも `/code-review <対象>` を必ず起動しろ。** 自分でもう少し調べてから起動する、という判断をするな。差分が小さい・自分で読んで問題無さそうだった・依存関係が気になる、はどれも起動を後ろへずらす理由にならない。レビュー対象は base ブランチとのマージベース以降の差分全体で、コミット済みの変更も未コミットの変更も両方含まれる。対象リポジトリが `/code-review` を使わない運用のときだけ、下の「レビュー skill を使わない運用のリポジトリの場合」に従え。

**ただし起動する前に、実装セッションから続けてそのまま来ていないか確認しろ。** `implement` skill の「セッションを閉じる前にやること」（計画への書き戻し・次のセッションへの引き継ぎ）を経ずにここへ来ているなら、まずそこへ戻れ。実装した本人の会話のままレビューへ進むのは、この一連の skill が避けようとしている事故そのものだ。

`<対象>` に渡す値は経路ごとに違う。

- plans 経路では `plans/<状態>/<管理表>/<ファイル名>.md` をそのまま渡せ
- **GitHub Issue 経路では、Issue 番号をそのまま渡せ**（例: `/code-review 306`）。`code-review` 側が渡された数字をまず PR 番号として存在確認し、無ければ Issue 番号として存在確認する（GitHub は PR と Issue で番号を共有するため、どちらか一方にしか当たらない）。Issue として解決されると description が自動で仕様として読み込まれ、レビュー対象は base ブランチとの差分になる。手元でファイルに書き出して渡す必要は無い

### レビュー skill を使わない運用のリポジトリの場合

対象リポジトリの `CLAUDE.md` / `README` に「`/code-review` は使うな」と明記されているなら、**レビュー段階を飛ばすな。** 起動するコマンドが無いだけだ。代わりに自分で以下をやれ。

- `git diff` の全体を自分で読んでレビューしろ
- **`${CLAUDE_SKILL_DIR}/../../references/quality-axes.md` の判断軸で、差分の読みやすさとコメントの分量を見ろ。** 動いているかどうかだけで通すな
- **変更した skill / hook / agent / 設定を参照している側が置き去りになっていないか確認しろ。** 参照が壊れても大半は黙って無視され、エラーも警告も出ない。見る先が対象リポジトリの `CLAUDE.md` に書かれていればそれに従え
- **名前で grep して0件だったことを完了の根拠にするな。** README のプラグイン一覧・マーケットプレイスのカタログ・plugin.json の description のように、機能を言い換えた文（「仕様横断調査」等）で書いてある箇所は名前検索に一切かからない。消した機能が何をするものだったかを言い換えた語でも検索しろ
- 触った範囲だけでなくリポジトリ全体を通しで軽く見ろ。**ユーザーに聞かれてから動くな**

## レビュー結果の反映とコミット

### レビュー結果を計画へ反映しろ

- 指摘が見つかったら計画を更新しろ。**GitHub Issue 経路では Issue の description がその計画そのものなので、更新先は1箇所だけだ**（別のチケット管理へ転記する必要は無い）。更新は `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` に従え
- **レビュー中に実装差が出る新しい判断が出たら、計画の「決めたこと」表へその場で追記し、確認テストをやり直せ。** 表に追記したまま確認テストを飛ばすと、「確認テスト: 合格」の記録が新しい判断を反映していない状態のまま残る
- plans 経路では、計画書を更新しろ
- **PR を出した後のレビューで差し戻された場合、plans 経路の計画書は `plans/レビュー中/<管理表>/` から `plans/進行中/<管理表>/` へ戻せ**（`mv plans/レビュー中/<管理表>/<ファイル名>.md plans/進行中/<管理表>/<ファイル名>.md`）。修正して PR を出し直したら下の「PR 作成後」の手順で再度 `レビュー中` に移る。GitHub Issue 経路では状態ディレクトリの概念が無いため何もしなくてよい

### 修正が終わったらコミットへ進め

指摘の採否が決まって修正が終わったら、**確認を挟まず** `/commit` を起動しろ。

- **「この内容でコミットしていいですか」を `/commit` の起動前に聞くな。** コミットの確認は `/commit` の中の「コミット実行前の最終確認」で1回だけ取る。起動前と起動後で2回聞くのは実際に苦情が出ている
- 起動したら `/commit` が自身の手順（base の取り込み・無関係な変更の検出・コミット分割の判定・コミット実行前の最終確認）を行い、コミット後は `/pr` まで連鎖する。**先回りして判定するな**
- **実装を別のセッションで行っている場合、`/commit` の「無関係な変更の検出」は計画の記載と照合して判定する。** そのため、このセッションで計画を読んでいることが前提になる（この skill の入口で読んでいるはずだ）
- 例外: ユーザーが「コミットはまだ」「レビューだけ」等で範囲を絞っている場合は、コミットへ進まず終われ

## PR 作成後

`/pr` で PR を作成すると、そのブランチに紐づく `plans/*.md` が `plans/進行中/<管理表>/` にあれば `pr` skill 自身が `plans/レビュー中/<管理表>/` へ自動で `mv` する（詳細は `pr` skill の「実装計画の参照」節）。GitHub Issue 経路では状態ディレクトリの概念が無いため何もしない。

- 自動で移らなかった場合（`pr` skill が計画書を見つけられなかった等）は手動で移せ:
  - 移動先が無ければ先に作れ: `mkdir -p plans/レビュー中/<管理表>`
  - `mv plans/進行中/<管理表>/<ファイル名>.md plans/レビュー中/<管理表>/<ファイル名>.md`
- **変わるのは状態のディレクトリだけだ。管理表のディレクトリとファイル名は変えるな**

## 完了後

計画の各節は `pr` skill の「反映のしかた（経路共通）」の対応表に従って PR 本文生成にそのまま参照される。書きっぱなしにせず、実際の差分と食い違っていないか最後に見直せ。

### GitHub Issue 経路

- PR がマージされたら、description の計画部分を実際の差分と突き合わせて最終更新しろ（実装しなかったステップ・スコープから外した項目をそのまま残すな）。更新は `${CLAUDE_SKILL_DIR}/../../references/issue-body-update.md` に従え
- **Issue を自分で close するな。** `pr` が付けた `Closes #<番号>` によって、マージ時に GitHub が自動で閉じる
- **子 Issue（Sub-issue）が閉じても、GitHub は親 Issue を自動で close しない。** マージで Issue が閉じたら、その Issue に親 Issue が付いているか確認しろ:
  - `gh issue view <番号> --json parent --jq .parent.number` で親 Issue 番号を取得しろ。親が無ければここで終わり
  - 親 Issue が取得できたら `gh issue view <親 Issue 番号> --json subIssuesSummary --jq '.subIssuesSummary'` で `completed` と `total` を確認しろ
  - `completed == total`（かつ `total > 0`）なら `gh issue close <親 Issue 番号>` で親 Issue も close しろ。**コメントは付けず無言で close しろ**
  - `completed < total` なら何もするな（他の子 Issue がまだ残っている）
  - **`completed == total` でも、親 Issue の本文に未着手の作業が残っていないか読んでから閉じろ。** サブ Issue を全部作り切っていない段階では、数だけ揃って中身が残る

### plans 経路

**`gh pr merge` が成功すると、hook が自動で `plans/レビュー中/<管理表>/` から `plans/完了/<管理表>/` へ計画書を移す。** 紐付けは計画書1行目の `<!-- PR: #<番号> -->` コメント（`pr` skill が「レビュー中」への移動時に付与する）で行う。移動結果（または見送った理由）は systemMessage で通知されるので確認しろ。

自動で移らなかった場合（PR番号のコメントが無い・同じ番号のコメントを持つ計画書が複数見つかった等）は、手動で移せ:

- **変わるのは状態のディレクトリだけだ。管理表のディレクトリとファイル名は変えるな**
- **`plans/` の起点は本体のチェックアウトだ**（詳細は `plan` skill の `references/plans-route.md`「配置・命名」を見ろ）。ワークツリーの中から `mv` するときは本体側の絶対パスを書け
- 移動先が無ければ先に作れ: `mkdir -p plans/完了/<管理表>`
- 移動は `mv plans/レビュー中/<管理表>/<ファイル名>.md plans/完了/<管理表>/<ファイル名>.md` の形で書け
- `plans/` は git 管理外なので `git mv` は使えない（`fatal: not under version control` になる）。`mv` を使え
- PR がまだマージされていない段階で移すな（レビューで差し戻されたら `レビュー中` から `進行中` に戻すことになる。上の「レビュー結果の反映とコミット」節を見ろ）

## マージした直後

`gh pr merge` が成功したら、**`${CLAUDE_SKILL_DIR}/../../references/post-merge-handoff.md` を Read してその手順に従え。** デプロイ後にしかできない確認が残っているかを見て残っていれば `deploy-watch` skill へ渡す判定と、ワークツリーのセッションを閉じる手順だ。**マージしたまま同じセッションで別の作業に入るな。**
