`gh pr review` で PR にコメント・approve・変更依頼を投稿するスキル。**指摘内容が固まった後、どう文章にしてどう投稿するかだけを担当する。指摘そのものを探す・作る作業はこのスキルの対象外**（`/code-review` 等に任せろ）。

## 手順

- 対象 PR 番号を確定しろ
- **著者確認を必ず先に行え**（「`--approve` 前の著者確認」参照）
- **既に投稿されている PR 本文・レビューコメント・会話コメントを全部読んでから書け**（`gh pr view <番号> --comments`）。他のレビュアーが既に出した指摘を重ねて出す・回答済みの論点を蒸し返すのを防ぐためだ。指摘を探すのはこのスキルの対象外だが、既存のやり取りを踏まえるのは文章を書くために必須だ
- 投稿する指摘・コメントがあれば、それぞれを「指摘の重み分類」の2種のどちらかに仕分けてから文章を組み立てろ
- **自分の修正について「修正しました」「反映しました」と書けるのは、その修正が対象 PR のブランチに push 済みでリモート上から確認できるときだけだ。** ローカルで直しただけ・コミットしただけの段階でそう書くな。投稿前に `git status -sb` で未 push のコミットが残っていないことを確認しろ
- **投稿種別（approve / comment / request-changes）は「投稿種別の判定」に従って確認なしで決めろ**
- **投稿前に本文をそのまま提示し、実行してよいという明示的な返事を得てから初めて投稿しろ。「そのまま提示」とは、本文の全文をこの会話の普通の文章として直接書くことだ。** `Write` でファイルに書いて `Read` で確認しただけの状態を「上のファイルの通り」「先ほど作成した内容で」のように参照するだけでは、ユーザーには本文が見えていない。ツール呼び出しの結果（Write/Read の出力）はユーザーの画面に表示されず、会話の文章として直接書いたものだけが見える。「インラインコメントにして」「approveして」のような指示だけでは、下書きを作ってほしいのか今すぐ投稿してほしいのかを言葉だけで区別できない。区別できないときは実行側に倒すな
- **提示する下書きは必ず1案に絞れ。「案A / 案B」のように複数案を並べてユーザーに選ばせるな。** 迷う点があればこのスキルの規約に照らして自分で1つに決め、その1案だけを出せ。指摘を受けたら直して出し直せばよい
- **下書きを押し戻されたら「押し戻されたときの直し方」に従え。** 指摘を消して出し直すな。**下書きの中身を咎める返信は投稿の許可ではない**（同節の冒頭を見ろ）
- 「実行」セクションのコマンドで投稿しろ

## `--approve` 前の著者確認

**`gh pr review --approve` を打つ前に必ず PR の著者を確認しろ。** GitHub の GraphQL API には「自分の PR は絶対に承認できない」という恒久的な仕様制限があり（`GraphQL: Review Can not approve your own pull request (addPullRequestReview)`）、これはリトライしても・書き方を変えても直らない。著者確認を省略して `--approve` を試みて失敗する、を毎回繰り返すな。

- `gh pr view <番号> --json author --jq '.author.login'` で PR 著者の login を取得しろ
- `gh api user --jq '.login'` で自分の login を取得しろ
- **`--jq` に raw 出力フラグ（`-r`）を付けるな**。`gh` では `unknown command` で失敗する。`gh` の `--jq` は文字列をクォート無しでそのまま出力するので、この指定はそもそも不要だ
- 両者が一致したら（自分の PR）:
   - `--approve` を一切試みるな
   - コメントだけの投稿（`--comment`）は可能なのでそのまま進めてよい
   - **マージ自体はこのスキルの対象外だ**（このスキルが担当するのは指摘の文章化・投稿だけだ）。承認を経由できないという事実だけをユーザーに伝え、マージするかどうか・どう進めるかは会話の他の文脈やプロジェクトの運用ルールに委ねろ。`gh pr merge` を生成・実行する手順をこのスキルに書くな
- 一致しなければ（他人の PR）: 「投稿種別の判定」に進め

## 投稿種別（approve / comment / request-changes）の判定

**著者確認・指摘の重み分類が終わったら、投稿種別は以下の基準で確認なしに機械的に決めろ。AskUserQuestion で選ばせるな。**

- 自分の PR（著者確認で一致）: `--comment` に固定しろ（`--approve` は使えない。マージ自体はこのスキルの対象外だ）
- 他人の PR で、🔴 必須対応 に分類した指摘が1件でも残っている: `--request-changes` にしろ。`--comment` は選ぶな（マージを止める効果が無く、見落とされて先にマージされるリスクがある）
- 他人の PR で、🔴 必須対応 は無いが、相手・他のレビュアーの回答待ちになっている確認事項が残っている: `--comment` にしろ。回答が返ってきてから改めて承認を検討しろ。「確認事項はありますが approve します」のように、確認待ちと承認を同じ本文に同居させるな
- 他人の PR で、残っているのが 🟢 任意対応 だけ、または指摘が無い: `--approve` してよい（🟢 任意対応 が残っている場合の締めの一文は「文章の書き方」の該当項目を見ろ）

**この4分岐は指摘の重み分類と著者確認さえ終われば機械的に決まる。「comment か request-changes か」のような、分類済みなら一意に決まる選択を AskUserQuestion で聞くな。** 分類自体が曖昧・確認事項の有無の判定に迷う等、分岐の前提そのものが不確かなときだけ会話文で確認しろ。

## 指摘の重み分類（文章を書く前に必ず1つ選べ）

指摘ごとに以下の2種のどちらかを先に決めてから文章を組み立てろ。分類の軸は**「この PR の中で直してほしいかどうか」の1本**だ。

| 分類 | 意味 | 見出し | ラベル形 | 見出し・ラベルで分類を示さないときに、その指摘の文章が満たすべき条件 |
|---|---|---|---|---|
| 🔴 必須対応 | バグ・仕様違反・規約違反等、この PR の中で直してほしい | `## 🔴 必須対応` | `**[必須対応]**` | マージ前に直す必要があることが読み取れる |
| 🟢 任意対応 | この PR の中で直さなくてよい。余裕があれば対応してほしい程度のもの | `## 🟢 任意対応` | `**[任意対応]**` | 今回の対応が必須ではないことが読み取れる |

**右列は満たすべき条件であって、そのまま貼り付ける文章ではない。** 条件を満たす言い回しは、その指摘の内容に合わせて毎回書き下ろせ。

- **同じ一文を複数の投稿で使い回すな。** 「この文を付けておけば分類が伝わる」という発想で決まり文句を差し込むな。書いた一文が、以前の投稿でも使えそうな汎用的な文になっていたら、その時点で書き直せ
- **見出しもラベルも使っていないとき（指摘が1件だけ・1分類だけのとき）は、分類を伝える一文を指摘の内容と切り離して独立に置くな。** 指摘そのものの文の中で、対応の要否まで含めて書き切れ。見出しかラベルで分類を示している場合は逆に本文で繰り返すな（「分類を伝える場所は1箇所に絞れ」参照）

### 🟢 任意対応 に落としてよいかの関門

**🟢 任意対応 は「余裕があればご対応いただけると幸いです」の位置づけだ。** 相手がこの PR の中で直さない判断をしても、こちらが困らないものだけを入れろ。

**マージ前に直らないと困るものを 🟢 に落とすな。** バグ・仕様違反・規約違反は、指摘した本人が直してほしいと思っている以上 🔴 必須対応 だ。分類を1段下げれば読み手の負担が減る・角が立たずに済む、という発想で選ぶな。**書いた本人が直してほしいと思っている指摘を任意の扱いで出すと、読み手は最初から読み飛ばしてよいものとして扱う。指摘を書いた意味がなくなる。**

逆に、**🟢 に入れた指摘を後から「やはり直してほしい」と言い直すな。** 🟢 に入れるのは、直らないまま終わることを受け入れたという意味だ。迷ったら 🔴 に入れて、相手に判断してもらえ。

### 規範を根拠にする指摘の裏取り

「このリポジトリの規約では」「〜という規約違反です」等、規範を根拠にして指摘するときは、その指摘を 🔴 必須対応 に入れる前に必ず次を確認しろ:

- 根拠として引用するファイルを実際に `Read` し、実在すること・引用した記載内容が本文と一致することを確認しろ。確認せずに記憶や推測で引用するな
- 根拠が「対象リポジトリ自身の規約・レビュールール」か「`~/.claude/review-rules/` 配下等の個人のレビュー方針」かを区別しろ。**個人のレビュー方針は対象リポジトリの規約ではない**。個人方針由来の指摘を「このリポジトリの規約では」と書くな
- 根拠ファイルが実在しない、または個人のレビュー方針由来だと判明した指摘は 🔴 必須対応 に入れるな。🟢 任意対応 に分類しろ
- **出典を本文に書くな。** ここで出典を区別するのは、規約でないものを規約と偽って書かないためだ。本文で出典を断らせるためではない。**「私個人のレビュー方針としての見解ですが」「リポジトリの規約ではありませんが」のような前置きを書くな。** 個人方針由来の指摘は、出典に触れず指摘の内容そのものだけを書け
- 確認が取れない指摘（根拠ファイルを開けない・記載内容が曖昧）は、規範を根拠にした断定をやめ、確認自体を相手に委ねる書き方（「〜という認識で合っていますでしょうか。」）にしろ

### 禁止語（読み飛ばしを誘う言い回し・決まり文句）

以下はいずれも実際に投稿を差し戻された表現だ。使うな:

| 使うな | 差し戻された理由 |
|---|---|
| 「〜程度で」で結ぶ言い回し（例:「気付いたら直す程度で」） | 指摘している時点で気づいているのは自明で、意味を成さない |
| 「今すぐの対応は不要です」 | 「今は不要だがいずれ必要」という緊急度の話にすり替わり、この PR の中で直さなくてよいという分類そのものが伝わらない |
| 「ご対応いただかなくても問題ございません」「対応しなくても大丈夫です」 | 読み手が見出しを見た時点で配下を読み飛ばしてよいと判断する |
| 「認識が間違っていましたらスルーしていただけますと幸いです」 | 4 回差し戻されている。仕様に関する免責を投稿の末尾に貼り付ける決まり文句になっていた。免責が要るなら該当する指摘の直後に、その指摘だけを指す形で毎回書き下ろせ |
| 「優先度は高くありませんが、対応自体は必要だと考えています」 | 毎回同じ文が入る決まり文句になっていた。分類は見出し（またはラベル）が伝えるので、本文で言い直すな |
| 「お手数おかけし恐縮ですが、よろしくお願いいたします。」「お手数ですがご確認の程よろしくお願いいたします。」等、対象を書かず〜だけで結ぶ締め | 3 回差し戻されている。「何を？」と聞き返される。締めには相手にしてほしい行為の対象を名指しで書け（「文章の書き方」参照） |
| 「〜いただければ十分です」「〜で構いません」 | こちらが相手の対応量を裁定しているように読める。任意対応の依頼は「〜いただけますと幸いです」で結べ |
| 「今回のPRには影響ありません」 | コードへの指摘である以上、影響が無いと断定するのは事実誤認になり得る。必須対応ではないことは「今回のPRの必須対応ではありません」のように分類の話として書け |

**分類そのものは、緊急度（今すぐ／後で）の言葉を経由して伝えるな。** 🟢 任意対応 なら、この PR の中で直さなくてよいということ自体を、その指摘の内容に即した言葉で直接書け。

### 複数の指摘をまとめるときの見出し構成

指摘が複数あり、かつ2種類の分類が混ざる場合、分類と1対1で対応する以下の見出しで分けろ。**実際に指摘が存在する分類の見出しだけを立てろ**（該当0件の見出しを空で置くな）:

| 分類 | 見出し |
|---|---|
| この PR の中で直してほしい | `## 🔴 必須対応` |
| この PR の中で直さなくてよい | `## 🟢 任意対応` |

**見出しの文言と絵文字を変えるな。** 「対応しなくても大丈夫です」のように読み手が見出しの時点で配下を読み飛ばせると判断できる文言に言い換えるのも、絵文字を落とすのも禁止だ。優先度が低いことと、読まなくてよいことは別だ。

指摘が1種類の分類しかない、または指摘が1件だけのときは見出しを付けず、文章の分量に応じて素直に書け。**異なる重み分類の指摘を同じ扱いの一文（例:「時間があるときに対応します」のように分類を無視して一括りにする言い方）で流すな。** 分類ごとに扱いを分けて書け。

- **1つの見出しの下に指摘が2件以上あるときは番号を振れ**（`1.` `2.` …）。番号が無いとどこからどこまでが1つの指摘なのか読み手が切り分けられない。指摘が1件だけのときは番号を振るな

### 各指摘は結論の太字1行タイトルから始めろ

**指摘の本文を説明文のベタ書きから始めるな。先頭に結論を示す太字の1行タイトルを置け**（例: `1. **同一ユーザーの二重登録が通ります**`）。タイトルが無いと、読み手は段落を読み切るまで何の話なのか分からない。**初回の下書きの時点でこの形にしろ**（押し戻されてから付け直すな）。

- **指摘が1件だけで番号を振らないときも、太字のタイトルは付けろ**
- **タイトルには結論（何が起きるか・何が誤っているか）を書け。** 「〇〇について」「〇〇の扱い」のように話題だけを示す体言止めにするな。読み手がタイトルだけで対応の見当を付けられる形にしろ
- **見出し（`##`）や小見出し（`###`）にするな。** `## 🔴 必須対応` の配下に見出しを足すと、提案であることを見出しで示す規約（「文章の書き方」の該当項目）と階層が競合する
- タイトルで分類（必須対応／任意対応）を言い直すな。分類は見出しかラベルが伝える（「分類を伝える場所は1箇所に絞れ」参照）
- **下書きを提示する直前に、各指摘の先頭行を1件ずつ上から照合しろ。** 太字タイトルになっていない指摘、結論ではなく話題だけのタイトル、結論を説明文の途中に埋め込んでいる指摘が1件も無いことを確認してから提示しろ。**規約を知っているかどうかではなく、書き終えた本文に対して実際に照合する工程を挟んでいるかどうかで抜け漏れが決まる**（書いている最中は指摘の中身に集中していて、先頭行の形が抜ける）

### 分類を伝える場所は1箇所に絞れ

分類を伝える手段は「見出し」「項目冒頭のラベル」「項目本文の文」の3つがあるが、**1つの投稿で使ってよいのは1つだけだ。** 2箇所以上で同じ分類を伝えると、指摘の数だけ同じことを繰り返すことになる。

- **見出しで分けたなら**、各項目にラベルを付けるな。各項目の文末に「この PR で対応する必要はありません」「対応は任意です」等の、分類を言い直すだけの一文を書くな
- **ラベルで示したなら**、同じ分類の見出しを重ねるな。文末にも書くな
- **見出しもラベルも無いとき**（指摘が1件だけ・1分類だけのとき）だけ、指摘本文の中で対応の要否まで書き切れ
- **見出しに使う文言を、個別の指摘の本文にそのまま流用するな。** 見出しで分類は既に伝わっているので、本文で同じ文言を繰り返すと決まり文句の貼り付けに見える

投稿前に、各項目の文末を上から順に読み返せ。**分類を言い直しているだけの一文が2項目以上に並んでいたら、見出しかラベルに一本化して全部削れ。**

## 押し戻されたときの直し方

**下書きの中身を咎める返信は、投稿の許可ではない。** 下書きを提示したあとに返ってきた発言が、書き方・結論の付け方・分類・分量のどれかを咎める内容だったなら、それは「直してもう一度提示しろ」という指示だ。**「もう聞かずに投稿しろ」の意味に取るな。** 直した本文を会話の文章として提示し直し、改めて明示的な投稿許可を得てから初めて投稿しろ。

- 咎める発言の例: 「結論をつけろ」「ポイントをつけて話せ」「長い」「何が言いたいのか分からない」「言葉遣いがおかしい」。**いずれも投稿許可ではない**
- **咎める発言に苛立ちが混じっていることを、催促＝実行の許可と読むな。** 苛立ちの原因は下書きが規約を満たしていないことであって、投稿が遅いことではない
- **投稿済みの本文を書き換える場合も同じだ。** 書き換えの必要を指摘されたら、書き換え後の本文を先に下書きとして提示しろ（「投稿後の訂正」参照）

そのうえで、指摘の分量・強度・書き方について押し戻されたときは、**指摘そのものを削除する方向へ倒すな。まず表現・分類・見出しの側を直せ。**

- **削除してよいのは、ユーザーが「その指摘は不要」「それは誤りだ」と明示的に言ったときだけだ。** 「多すぎる」「書き方がおかしい」「対応しなくていいなら書くな」は、どれも削除の指示ではない
- 押し戻しの原因が見出しの文言・分類の付け方にあるなら、直すのは見出しと分類だ。**中身を消すと「ではなぜ書いたのか」が説明できなくなり、押し戻しの意図とも食い違う**
- **この原則は指摘だけでなく褒め言葉・謝意の表現にも及ぶ。** 表現（採点調・ラフすぎる等）を咎められたら、その表現だけを直せ。褒め言葉・謝意をまるごと削って無難な短文にするな
- **押し戻された箇所だけを直せ。** 咎められていない部分まで巻き込んで作り替えるな
- 件数を自分の判断で減らすな。減らすべきだと思うなら、消した案を先に出すのではなく「この N 件は分類を下げますか」と聞け
- 押し戻しを受けて出し直す下書きでは、**前の下書きから消えた指摘が無いことを投稿前に自分で照合しろ**

## 文章の分量

**固定テンプレートで型にはめるな。** PR の複雑さに応じて分量を調整してよい。「確認しました、approveします。」の一言で済ませるのが適切な回もあれば、業者との調整事項を含む長文が適切な回もある。分量を無理に統一しようとするな。

### 短くする側の判断基準

- **自分または他のレビュアーが出した指摘への対応を確認しただけの承認では、確認した項目を列挙して再掲するな。** 何をどう直したかは相手が一番よく知っている。「冒頭の謝意 →（あれば相手の判断が必要な論点だけ）」の数文で終えろ（謝意を締めでもう一度書くな）
- 本文に書いてよいのは、相手がまだ知らない情報だけだ（新たに見つけた指摘、他のレビュアーの指摘のうち未対応のもの、こちらで追加で確認した結果 等）。これに当たらない確認済み項目の列挙は削れ
- これは分量の目安であって、書く内容を固定するものではない。上の「固定テンプレートで型にはめるな」と矛盾しない

## 文章の書き方

- **本文の先頭に `# PR番号 レビュー` のような見出しを置くな**。GitHub 上で本文の先頭に `@ユーザー名` のメンションを置くだけでよい
- **メンションの直後に置く1文は、投稿種別（承認／コメント／変更依頼）で機械的に決めるな。「相手の行為を受けての返信か、こちらから新規に確認を依頼するのか」で決めろ**
  - **直前に相手がレビュー・修正・回答をしてくれたことへの返信**: 冒頭は謝意の1文にしろ（指摘への対応を受けての返信なら「迅速なご対応ありがとうございます。」等）。**相手が今まさに対応してくれた直後に「お手隙の際にご確認いただけますと幸いです。」と書くな**（既に確認・対応してもらった後なので噛み合わない）
  - **こちらから新規に指摘・確認を投げる場合**（相手の対応を受けていないコメント・変更依頼）: 「お手隙の際にご確認いただけますと幸いです。」のような、どの PR にもそのまま貼れる決まり文句を添えるな。**その PR で相手が実際に何を実装・変更したかに触れた1文にしろ**（例:「実装ありがとうございます。SPでのTOPページ・ログイン導線まで通していただいた内容だったので、一つずつ確認させていただきました。」）
    - **変更点を列挙して「確認させていただきました」で結ぶだけで終わるな。** 「〇〇と△△と□□の3件、確認させていただきました。」は、どの PR にもそのまま貼れる決まり文句と変わらない。下の「冒頭の謝意には、その PR の具体的な良い点を必ず含めろ」に従って書き足せ
  - **承認**（`--approve`）: 既に確認済みなので「お手隙の際に〜」は付けるな。冒頭へ謝意を1文置け。指摘対応を挟まない初回レビューでの承認なら「ご対応ありがとうございます。」を使え。承認で冒頭を謝意なしにいきなり本題から始めるな
  - **承認の本文には、承認する旨を明示する一文を必ず入れろ**（例:「問題ございませんでしたので、承認いたします。」）。GitHub の UI 上に承認済みの表示が出ても、本文だけを読んで承認かどうか判断できない状態を作るな
- **誰の作業・誰の指摘・誰の判断かを一次情報で確定できていないなら、人物名を書くな**。コミット・コメント・レビュー履歴で本人だと確認できていない推測を本文に混ぜるな。確定できないなら、人物に触れずに事象だけを書け
- **誰の提案を誰が採用したか、といった経緯・帰属を書くな**。相手が既に知っている情報であるうえ、手柄の主張に読める。本文に書いてよいのは相手がまだ知らない情報だけだ（「短くする側の判断基準」参照）
- **相手の仕事ぶりを採点するような言い回し（「大変丁寧に実装いただきました」「完璧でした！」「参考になりました」「いいと思いました」「きれいな実装ですね」等）を書くな**。レビューする側が相手を評価しているように読め、失礼になる。
- **一方で、感謝を「実装ありがとうございます。」「ご対応ありがとうございます。」の1文だけに切り詰めるな。無愛想に読める。** 相手の対応によって自分がどう助かったかという目線（「大変助かりました。表示も崩れておらず、確認もスムーズにできました。」等）で書け。判断基準は「相手を評価しているか」か「自分が受けた助けを述べているか」であって、褒め言葉の有無そのものではない
- **冒頭の謝意には、その PR の具体的な良い点を必ず1つ以上含めろ。初回の下書きの時点で含めろ**（押し戻されてから足すな）。差分を読んでいれば見つかる。見つからないと思ったら差分の読み方が足りていない
  - 触れる対象の例: 追加されたテストの厚さ（境界値・競合の再現ケースまで押さえている 等）、残っているリスク・未対応箇所を PR 本文で正直に開示していること、修正の意図がコミットの分け方から追えること、こちらの過去の指摘を先回りして直していること
  - **良い点も「自分がどう助かったか」の目線で書け**（例:「境界値のテスト（10件・11件双方向）や競合の再現テストまで追加していただいていたので、修正の意図を追いやすく大変助かりました。」）。**上の項目の禁止（相手の仕事ぶりを採点する言い回し）はここにも掛かる。** 「丁寧なテストですね」「良い実装だと思いました」は採点だ
  - 同じ言い回しを毎回使い回すな。良い点は PR ごとに違うので、その差分を見て毎回書き下ろせ
- **指摘の存在・重要度を伝える見出し語に「お気づきの点」のような曖昧な婉曲表現を使うな**。「指摘の重み分類」で決めた見出しをそのまま使い、何についてのどの重み分類の指摘かが直接わかるようにしろ
- **🟢 任意対応 だけの指摘を切り出すとき、「気になった点がありました」のような重い言い回しを使うな**。「気になった点」は 🔴 必須対応 が混在する文脈を想起させ、任意対応だけの場面では実態より重く読める。「余裕があれば、以下の〇点についてもご対応いただけますと幸いです（今回のPRの必須対応ではありません）。」のように、指摘の重さに合った軽い言い回しで切り出せ。**「今回のPRには影響ありません」とは書くな**（コードへの指摘である以上、影響が無いと断定するのは事実誤認になり得る。必須対応ではないというだけで、影響そのものを否定するな。「禁止語」参照）
- **手戻りの原因がこちら側（仕様書とデザインの不整合等）にあるときは、指摘より先に「実装自体は〇〇通りに正しく作られており、原因はこちら側にある」旨を明示しろ**。書かないと相手の実装ミスとして読める
- **原因がこちら側にあり相手に手戻りを強いる変更依頼では、詫びを原因説明の冒頭と締めの一文の両方に入れろ。強度は「申し訳ございません」ではなく「大変申し訳ございません」を使え**（締めの側の具体的な書き方は下の「締めの一文は」の項目を参照）
- **本文が長くなるときは、話題ごとに空行で段落を分けろ。1段落に複数の話題を詰め込むな**
- **「①〜④」等の番号で他の項目を参照するときは、所属見出しを添えろ**（例:「🔴 必須対応 の①〜④」）。必須対応・任意対応の両方に番号列があるとき、見出しを省くとどちらを指すか読み手が判別できない
- **レビュー対象者や他のレビュアーが対応方針をまだ確認待ちのまま結論を出していない論点は、Claude が独自に結論を決め打ちして書くな**。原因が特定できている場合の断定（「〜が原因です」）はそのまま書いてよいが、複数の対応案から「どちらを採るか」は相手の判断に委ねる書き方（「〇〇さんの確認結果に沿って対応をお願いします」等）にしろ
- **相手の方針に同意している点があるなら、指摘より先にそれを書け**。同意を示さずに改善案だけを並べると、方針そのものを否定しているように読める
- **提案として書くものは、見出しの時点で提案だと分かる形にしろ**（`### ダミーデータの管理方法` ではなく `### ダミーデータの管理方法についてのご提案`）。断定的な見出しだけを置くと、こちらの私案を決定事項として押し付けているように読める
- **仕様と実装が食い違っている疑いを指摘するとき、「〜と書かれているように見えるのですが」のような書き方をするな**（読み手に「本当にそう見えているのか」と疑っているように読め、皮肉に受け取られる）。**仕様に関する指摘は Claude 側の理解が誤っている可能性の方が高いという前提に立て。「実装と仕様書どちらが正しいか」のような対等な問い方もするな。「〜と記載されているのを確認していますが、この認識で合っていますでしょうか。」の形にしろ**
- **仕様に関する指摘には、こちらの認識違いなら対応不要という趣旨を添えろ。ただし本文の末尾にまとめて置くな。** 該当する指摘の直後に、その指摘だけを指す形で書け。末尾に置くと、どの指摘に掛かっているのか読み手が分からず、とりあえず付けた免責文に見える
  - 仕様に関する指摘が複数あるときは、指摘ごとに書き方を変えろ。同じ一文を並べるな（「禁止語」参照）
  - 仕様に関する指摘が1件も無いときは添えるな
- **原因が既に特定できている場合は「〜が原因だと思うので」のような推測の言い回しにせず、「〜が原因です」と断定しろ**
- **対応が本当に必要かどうか自分で判断できない指摘は directive（「〜してください」「〜いただけますと幸いです」等、相手に行動を指示する言い方）にするな**。「〜が必要かご確認いただけますと幸いです」のように、判断自体を相手に委ねる言い方にしろ
- **締めの一文は「本文中に相手への対応依頼が残っているか」で使い分けろ（投稿種別〈承認／コメント／変更依頼〉だけで機械的に決めるな）**。「以上です、よろしくお願いします 🙇‍♂️」（絵文字あり）、および文頭に「以上、」を付ける言い方は、どちらの場合でも使うな
  - **本文中に対応依頼が残っている**（コメント・変更依頼の全部、および承認でも他のレビュアーの指摘への対応待ちに触れている場合）: **相手にしてほしい行為の対象を名指しで含めろ**（例:「お手数ですが、上記の対応内容についてあらためてご確認いただけますでしょうか。」）。「お手数おかけし恐縮ですが、よろしくお願いいたします。」のように何を頼んでいるか書かない「よろしくお願いいたします」だけの締めは禁止語だ（「禁止語」参照）。「何を？」と聞き返される。同じ一文を毎回使い回すな
    - **手戻りの原因がこちら側にある変更依頼では、対象を名指しした依頼文の直後に詫びを続ける2文構成にしろ**（例:「上記🔴必須対応の◯点について修正していただけますでしょうか。お手数をおかけして大変申し訳ございませんが、ご確認のほどよろしくお願いいたします。」）。「よろしくお願いいたします」は対象を名指しした依頼文に続ける形なら使ってよい。禁止語表が禁じているのは対象を書かず単独で置く場合だけだ
    - **承認で 🟢 任意対応 の指摘が1件以上残っている場合、対象を名指しした依頼文の直後に、次の2つの許可を両方とも読み取れる一文を、その回の指摘内容に即して書き下ろせ**
      - **見送ってそのままマージしてよいこと**
      - **指摘に対応して追加でコミットした場合も、あらためてのレビューを待たずにマージしてよいこと**
      - **「このままマージしていただいて問題ございません」だけで済ませるな。**「このまま」は今の差分を指すと読めるため、追加コミットを積んだ場合に再レビューが要るのかどうかが伝わらない（例:「上記🟢任意対応の◯点について、余裕があればご確認いただけますと幸いです。見送っていただいても、ご対応いただいて追加でコミットしていただいても、あらためてのレビューはお待ちいただかずマージしていただいて問題ございません。」）。これは「禁止語」に挙げた「対応しなくても大丈夫です」等（指摘の重みを軽んじる文言）とは別物で、マージ運用上の許可を書くものだ。同じ一文を毎回使い回すな（「決まり文句を使い回すな」参照）
  - **本文中に対応依頼が一切残っていない**（承認かつ全指摘が解消済み）: 「ご確認よろしくお願いいたします」を使うな。承認しているのにまだ確認してほしいことが残っているように読め、承認の意味と噛み合わない。**冒頭に謝意を置いている以上、締めの一文自体を省いて本題で終えろ**
- **同じ用件に対する謝意を本文中に2回書くな。** 冒頭に謝意を置いたなら、締めで謝意を繰り返すな（「迅速なご対応ありがとうございます。」で始めて「ご対応ありがとうございました。」で締めるのは同じ用件の二重掲載だ）。個別の指摘の直後に書いた謝意・対応依頼と締めの一文が重複するのも同じく禁止だ。投稿前に読み返し、同じ用件に対する同趣旨の表現が2箇所以上に出ていないか確認しろ

## 実行

**本文の渡し方は「シングルクォートで囲んだ複数行リテラルを `--body` に直接渡す」に固定しろ。** シングルクォート内はシェル展開が起きないので、改行・バッククォート・パイプ記号をそのまま通せる。ヒアドキュメント（`<<EOF`）は使うな（`nt-common:bash-rules` が禁止している）。一時ファイルを作って `--body-file` に食わせるのも通常はするな。

- コメントのみ: `gh pr review <番号> --comment --body '<本文>'`
- 承認: `gh pr review <番号> --approve --body '<本文>'`（自分の PR では絶対に実行するな。「`--approve` 前の著者確認」を参照）
- 変更依頼: `gh pr review <番号> --request-changes --body '<本文>'`

例外は、本文に ASCII のシングルクォート `'` が含まれてインラインが破綻するときだけだ。その場合に限り scratchpad ディレクトリ（システムプロンプトで指定されている一時ファイル置き場）配下の絶対パスに Write して `--body-file` で渡し、投稿後に自分で削除しろ。`$TMPDIR` 直下のような場当たりのパスに置くな。

投稿後は URL と投稿種別（approve / comment / request-changes）を簡潔に報告しろ。

## 投稿後の訂正

投稿済みのレビュー本文に誤りが見つかった場合、承認そのものの取り消しではなく本文の書き換えで対応できる。**許可を得ないまま投稿してしまったと気づいたときも、この節の手順で対応しろ。** 承認は取り消せないが本文は書き換えられるので、まず書き換え後の本文を下書きとして提示しろ。何をどうするかをユーザーに問い返す前に、下書きを出せ。

- `gh api repos/<owner>/<repo>/pulls/<PR番号>/reviews --jq '.[] | select(.user.login=="'"$(gh api user --jq .login)"'") | .id'` で自分が投稿したレビューの review_id を取得しろ
- `gh api -X PUT repos/<owner>/<repo>/pulls/<PR番号>/reviews/<review_id> -f body="<修正後の本文>"` で書き換えろ
- 書き換え後の本文も、新規投稿と同じく事前にユーザーへ提示し、実行してよいという返事を得てから実行しろ

## ルール

- `--approve` を打つ前の著者確認は省略するな（自分の PR での失敗を繰り返さないため）
- **マージ自体はこのスキルの対象外だ。`gh pr merge` を生成・実行する手順をここに書くな**（このスキルが担当するのは指摘の文章化・投稿だけだ）
- **投稿種別（approve / comment / request-changes）は「投稿種別の判定」の4分岐で確認なしに機械的に決めろ。** 🔴 必須対応 の指摘が残っている状態で承認するな。分岐が一意に決まる選択を AskUserQuestion で聞くな
- 投稿前に PR 本文と既存のコメントを全部読め
- push が済んでいない修正を「反映しました」と書くな
- 指摘は必ず2分類（🔴 必須対応 / 🟢 任意対応）のどちらかに仕分けてから文章化しろ。禁止語を使うな
- **🟢 任意対応 に入れてよいのは、この PR の中で直らないまま終わってもこちらが困らないものだけだ。** マージ前に直ってほしいなら 🔴 必須対応 に入れろ
- **決まり文句を使い回すな。** 分類・免責・謝意を伝える一文は、その指摘の内容に合わせて毎回書き下ろせ。過去の投稿でもそのまま使えそうな汎用的な一文になっていたら書き直せ
- 複数指摘をまとめるときは分類と1対1の見出し（`## 🔴 必須対応` / `## 🟢 任意対応`）で分けろ。**見出しの文言も絵文字も変えるな**（「複数の指摘をまとめるときの見出し構成」参照）。同じ見出しの下に2件以上あるなら番号を振れ
- **各指摘は結論を示す太字の1行タイトルから始めろ。** 指摘が1件だけで番号を振らないときも付けろ。説明文のベタ書きから始めるな（「各指摘は結論の太字1行タイトルから始めろ」参照）
- **分類を伝えるのは見出し・ラベル・本文のいずれか1箇所だけにしろ。** 見出しやラベルで示したなら、各項目の文末で分類を言い直すな（「分類を伝える場所は1箇所に絞れ」参照）
- **下書きの中身を咎める返信を投稿の許可と読むな。** 直した本文を提示し直し、改めて明示的な投稿許可を得てから投稿しろ（「押し戻されたときの直し方」参照）
- **押し戻されたときに指摘そのものを削除する方向へ倒すな。褒め言葉・謝意の表現を咎められたときも同じで、丸ごと削除するな。** まず表現・分類・見出しを直せ。削除は「その指摘は不要」と明示されたときだけだ。**押し戻された箇所以外を巻き込んで作り替えるな**（「押し戻されたときの直し方」参照）
- 「文章の書き方」節の言い回し規約に従え
- 承認の本文は冒頭に謝意の1文を置け（「文章の書き方」参照）。冒頭に謝意を置いたら締めで謝意を繰り返すな
- **承認の本文には承認する旨を明示する一文を必ず入れろ**（例:「問題ございませんでしたので、承認いたします。」）
- **承認で 🟢 任意対応 の指摘が1件以上残っているときは、見送ってマージしてよいことと、対応して追加でコミットした場合もあらためてのレビューを待たずマージしてよいことの両方を、その指摘内容に即して毎回書き下ろせ**（決まり文句にするな。「文章の書き方」の締めの一文の項目を参照）
- **🟢 任意対応 だけの指摘を「気になった点」のような重い言い回しで切り出すな。** 指摘の重さに合った軽い言い回しで切り出せ（「文章の書き方」参照）
- **メンション直後の1文を投稿種別で機械的に決めるな。** 相手の対応を受けての返信なら謝意から始めろ
- 自分または他のレビュアーの指摘への対応を確認しただけの承認では、確認済み項目を列挙して再掲するな
- 相手の仕事ぶりを採点するような言い回し（「大変丁寧に実装いただきました」「参考になりました」等）を書くな。感謝を1文だけに切り詰めて無愛想にするな。感謝は「自分がどう助かったか」目線で書け（「文章の書き方」参照）
- **冒頭の謝意には、その PR の具体的な良い点を必ず1つ以上含めろ。初回の下書きの時点で含めろ。** 変更点を列挙して「確認させていただきました」で結ぶだけで終わるな。良い点も採点調にせず「自分がどう助かったか」目線で書け（「文章の書き方」参照）
- 下書きは1案に絞って提示しろ。複数案を並べて選ばせるな
- **下書きの提示は必ずこの会話の普通の文章として本文の全文を直接書け。** ファイルに書いて `Read` した結果を「上のファイルの通り」のように参照するだけでは、ユーザーには見えていない
- 文章の分量は状況に応じて変えてよい。固定テンプレートを強制するな
- 指摘内容そのものを探す・生成する作業はこのスキルの対象外。`/code-review` 等に任せろ
- PR へのコメント・レビュー本文は日本語で書け
- 本文はシングルクォートで囲んだ複数行リテラルを `--body` に渡せ。ヒアドキュメントを使うな（「実行」参照）
- 投稿後に誤りが見つかったら、承認の取り消しではなく本文の書き換えで対応しろ。**許可を得ないまま投稿してしまったときも同じ手順で、まず書き換え後の本文を下書きとして提示しろ**（「投稿後の訂正」参照）
- **規範を根拠にする指摘（「このリポジトリの規約では」等）は、必須対応に入れる前に根拠ファイルを実際に Read して実在・出典（対象リポジトリの規約か個人のレビュー方針か）を確認しろ**。確認できない、または個人方針由来と判明した指摘は必須対応に入れるな。**出典の区別は分類のために行うものだ。個人方針である旨を本文に前置きするな**（「規範を根拠にする指摘の裏取り」参照）
- **手戻りの原因がこちら側にあるときは、指摘より先に相手の実装が正しい旨を明示し、詫び（「大変申し訳ございません」）を原因説明の冒頭と締めの両方に入れろ**
- 本文が長くなるときは話題ごとに段落を分けろ。「①〜④」等の番号参照には所属見出しを添えろ（「🔴必須対応の①〜④」等）
