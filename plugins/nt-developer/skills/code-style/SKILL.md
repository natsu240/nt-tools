# コード共通スタイル規約（書く前に読め）

PHP / Vue / TypeScript / SCSS / CDK / CI/CD / シェルスクリプトなど、何か実装するときすべてに適用される、読みやすさ優先のチェックリスト。過去セッションで「読みにくい」「動けばいいやみたいなコード」「コメントが冗長」と指摘されたパターンを抑止するための共通ルール。

**判断軸は `${CLAUDE_SKILL_DIR}/../../references/quality-axes.md` にある。** この skill が持つのは、その軸に沿って書くための規約とコード例だ。

**ここに並んでいる言語名は、続けて読むべき領域別 skill がどれかを示す案内だ。適用対象を限定する一覧ではない。** 名前が挙がっていない言語・ファイル形式でも、この skill の規約は全部適用しろ。

各言語・領域固有の構文やフレームワーク固有のルールは、別 skill で：

- **PHP / Laravel**: `code-style-laravel`
- **Vue / SCSS / Element Plus**: `code-style-vue`
- **素の TypeScript**: `code-style-ts`
- **AWS CDK**: `code-style-cdk`
- **GitHub Actions 等の CI/CD**: `code-style-cicd`
- **シェルスクリプト（.sh / .bash / .zsh）**: 領域別 skill は無い。この skill だけで足りる

## 既存コードを参考にしても、規約違反は模倣するな

新規ファイルを書くときも既存ファイルに追記するときも、参考にした既存コード（同じプロジェクトの別ファイル、同一ファイル内の別メソッド）が `code-style` / `code-style-laravel` / `code-style-vue` / `code-style-ts` / `code-style-cdk` / `code-style-cicd` のいずれかに違反していないか、書く前に確認しろ。

違反していたら、その書き方を模倣するな。各規約が定める書き方を優先しろ。「既存がそうなっているから」を規約違反の言い訳にするな。

対象は docblock やコメントに限らない。命名、エラーハンドリング、null チェックの仕方、構造分割、文字列結合の方法など、コードを書く・直すあらゆる場面に適用しろ。

例外: 各規約が「既存に合わせろ」と明示している箇所（docblock スタイル（1 行 / 複数行）は周囲に合わせろの節の改行形式、`code-style-laravel` の FormRequest / Validation は既存プロジェクトの慣例に揃えろの節が定める (A)(B)(C) パターン選択等）はそのまま既存に従ってよい。それ以外は理想を優先しろ。

## 触る範囲の負債は本命の実装より先に直せ

今回の変更で触る範囲に規約違反の既存コード（負債）があるなら、本命の実装に入る前にそれを直せ。負債の上に新しい実装を積むな。

- **対象範囲**: 今回読み書きするファイル・関数と、そこが直接呼ぶ／そこを直接呼んでいる箇所まで。それより外は今回の対象にするな
- **負債の定義**: その範囲の既存コードが `code-style` / `code-style-laravel` / `code-style-vue` / `code-style-ts` / `code-style-cdk` / `code-style-cicd` のいずれかに違反していること
- **順序**: リファクタを先に終わらせてから本命の実装に入れ。同じ編集の中で混ぜるな
- **承認**: 直す範囲は計画に書いて承認を取れ。承認が返らなかった範囲は触るな

工程ごとにやることは `plan` / `implement` / `commit` の各 skill がこの節を指して持っている。

## 既存の類似実装を統合するときは中身と呼び出し状況を確認しろ

複数箇所にある同名・類似のメソッド/クラスを1つに統合するとき、メソッドシグネチャが一致しているだけで「差分なし」と判断するな。

- 統合対象それぞれの実装の中身を比較し、挙動が本当に同一か確認しろ
- 統合対象それぞれの既存の呼び出し元を全て洗い出し、実際に使われているか（生きているか、デッドコードか）を確認しろ
- どちらか一方が呼ばれていないデッドコードだった場合、統合によってそのデッドコードの実装が初めて使われることになる。生きていた方の実装に合わせて統一しろ

## 恒久的なガイドライン・ルール文書に実装の具体名を書くな

`docs/` 配下等、恒久的に参照され続けるドキュメントに、MUST ルール・禁止事項の「例」として現在の実装クラス名・ファイルパス・チケット番号を書き込むな。実装は将来リネーム・削除・置き換えされるが、ドキュメントの実例はそのまま残り、いずれ実体と乖離した古い依存過多な記述になる。ルールは抽象的な原則（依存の方向性・禁止パターンの構造）だけで説明しろ。

## ドキュメント・コメントを分量で評価するな。読み手が目的を果たせるかで判断しろ

README・`docs/` 配下・コメント・docblock を書くときも、他人が書いたものを評価・レビューするときも、次で判断しろ。

- **行数・記載量の多さそれ自体を評価軸にするな。** 「N 行あって充実している」を加点の理由にするな。分量は、読み手の目的を果たせているかを確かめてから初めて意味を持つ
- **コードを読めば分かる内容の重複説明になっていないか確認しろ。** 関数・クラス単位の処理説明、ディレクトリの全列挙はドキュメントの仕事ではない
- **頻繁に変わる実装詳細に依存させるな。** 実装が変わるたびに書き直しが要る記述は、放置された瞬間に嘘になる
- **読み手と目的に合わせて情報量を削れ。** README なら「初めてこのリポジトリを触る開発者が全体像を素早く掴めること」が目的だ。目的に寄与しない記述は、内容が正しくても減点対象にしろ

コメント・docblock を何行書いてよいかの判定は 1行なら書いてよい。2行目以降だけ「コードの外側にある事実か」を問えの節が持つ。この節が扱うのは、文書・コメント全体の分量を良し悪しの根拠にするなという話だ。

## 三項演算子の長い分岐は早期 return にしろ

❌ NG（PHP の例）:
```php
return $value === null || $value === '' ? '' : $value . '円';
```

⭕ OK:
```php
if ($value === null || $value === '') {
    return '';
}
return $value . '円';
```

理由: 三項演算子は条件・true 分岐・false 分岐が 1 行に潰れて読みづらい。早期 return は視線が左 → 右 → 下に流れて自然。

TS でも同じ：

❌ NG:
```ts
return value === null || value === '' ? '' : `${value}円`
```

⭕ OK:
```ts
if (value === null || value === '') {
  return ''
}
return `${value}円`
```

## 同じ式を繰り返すな。変数化しろ

❌ NG（PHP の例）:
```php
return $typeLabel === null || $typeLabel === ''
    ? $area . '㎡'
    : $area . '㎡（' . $typeLabel . '）';
```

⭕ OK:
```php
if ($area === null) {
    return '';
}
$base = "{$area}㎡";
if ($typeLabel === null || $typeLabel === '') {
    return $base;
}
return "{$base}（{$typeLabel}）";
```

理由: 同じ式を 2 回書くと修正時にズレる、読み手も「同じ式？」と確認する手間。

## 1 関数内に独立 if を 3 つ以上並べるな。helper 関数へ分離しろ

❌ NG（メイン関数に if 連発）:
```php
private function buildSummaryLabel(?MCategory $category, ?int $total, ?int $index): string
{
    $parts = [];
    if ($category?->name !== null) {
        $parts[] = $category->name;
    }
    if ($total !== null) {
        $parts[] = "全{$total}件";
    }
    if ($index !== null) {
        $parts[] = "({$index}件目)";
    }
    return implode('　', $parts);
}
```

⭕ OK（各分岐を helper に分離、メインは組立だけ）:
```php
private function buildSummaryLabel(?MCategory $category, ?int $total, ?int $index): string
{
    $parts = array_filter([
        $category?->name,
        $this->formatTotal($total),
        $this->formatIndex($index),
    ]);
    return implode('　', $parts);
}

private function formatTotal(?int $total): ?string
{
    if ($total === null) {
        return null;
    }
    return "全{$total}件";
}

private function formatIndex(?int $index): ?string
{
    if ($index === null) {
        return null;
    }
    return "({$index}件目)";
}
```

ルール:

- `array_filter` の中に三項演算子を埋め込むな
- helper 内は早期 return
- メイン関数は「何を組み立てるか」だけ見える形にしろ

## enum で表現できるコードは enum を使え

❌ NG（マジックナンバーと private const の散在）:
```php
private const HONORIFIC_CODE_WITH_TITLE = 1;

if ($honorificCode === self::HONORIFIC_CODE_WITH_TITLE) {
    ...
}
```

⭕ OK:
```php
// 別ファイルに enum 定義
enum OwnerHonorificCode: int
{
    case WITH_TITLE = 1;
    case NONE = 2;

    public function pdfSuffix(): string
    {
        return match ($this) {
            self::WITH_TITLE => '　御中',
            self::NONE => '',
        };
    }
}
```

TypeScript でも同じ：マジックナンバーを enum / Union 型 / `as const` で表現しろ。

## class docblock は種類で使い分けろ。メソッド docblock はちゃんと書け

### class docblock の有無

| 種類 | class docblock |
|---|---|
| **機能系**（Action / Service / Composable など、メソッドが本体） | ❌ 不要 |
| **抽象クラス・基底クラス** | ✅ 必要（何の共通基盤か、継承先は何をするか書く） |
| **DTO**（データ構造）| ✅ 必要（用途を書く） |
| **Constants**（定数のみ）| ✅ 必要（何の定数集か書く） |
| **Enum** | ✅ 必要（何のコードか書く） |

「データ構造系（DTO / Constants / Enum）」は class そのものが目的なので class docblock 必要。
「機能系」はメソッドが本体なので class docblock 不要、メソッド docblock に集約。
「抽象クラス」は単体では使われず継承先で意義が出るので、何の共通基盤かを class docblock で書く。

### メソッド docblock は説明1行とタグで書け

**説明文は 1 行が基本だ。** 「何をする関数か」が 1 行で伝わればそれで足りる。入力・出力の詳細は `@param` / `@return` / `@throws` のタグに寄せろ。

⭕ OK（説明 1 行 + タグ）:
```
/**
 * 入力モーダルで入力された全項目を sample_records に upsert する。
 *
 * @param  SampleRecordInput  $input
 * @return SampleRecord
 * @throws ValidationException
 */
public function __invoke(...): ...
```

説明を 2 行以上にしてよいのは、コードから読み取れない技術根拠がある場合だけだ（1行なら書いてよい。2行目以降だけ「コードの外側にある事実か」を問えの節で判定しろ）。

### 例外

関数名が完全に自明な場合（`user(): BelongsTo`、`id(): int` 等の getter / リレーション）は省略可。

### 多数メソッドが並ぶ class では各メソッドに 1 行の docblock を付けろ

5 関数以上が目安。各メソッドの docblock で「何をする関数か」を 1 行で書くと一覧性が大きく上がる。メイン処理メソッドや複雑な関数も同じで、説明は 1 行に収め、型と例外はタグで補え。

## docblock の言語は日本語に揃えろ

❌ NG（英語の docblock がそのまま残る）:
```
/**
 * Staff users whose workplace group is this record.
 */
```

⭕ OK（説明文は日本語、業務用語はそのまま日本語）:
```
/**
 * このグループを所属グループとして登録しているユーザー
 */
```

ルール:

- 読み手が日本語話者のプロジェクトでは日本語に統一
- 業務用語（「担当グループ」「所属グループ」「論理削除済み」等）は英訳すると意味が薄れるので日本語のまま
- `@param` / `@return` / `@throws` / `@var` のタグは書け。行数の判定の対象外なので、説明 1 行と併記して構わない
- メソッドシグネチャだけで型が完全に決まるなら `@param` / `@return` は省いて良い。配列の要素型のようにシグネチャで表せない型は、静的解析（Larastan / tsc 等）のために必ず書け

## docblock スタイル（1 行 / 複数行）は周囲に合わせろ

1 ファイル内で 1 行 docblock と 3 行 docblock を混在させるな。**周囲の既存メソッドのスタイルに揃えろ**。

❌ NG（1 行と 3 行が混在）:
```
/** ユーザーが登録した対象レコード */
public function user(): ...

/**
 * 入力モーダルの入力値
 */
public function sampleRecord(): ...
```

⭕ OK（周囲のスタイルに揃える）:
```
/** ユーザーが登録した対象レコード */
public function user(): ...

/** 入力モーダルの入力値 */
public function sampleRecord(): ...
```

新規ファイルなら一貫して 3 行形式が読みやすいが、既存ファイルに追記する場合は既存パターンを優先しろ。

ただしこれは改行形式（1 行か複数行か）だけの話だ。既存ファイルに docblock の言語は日本語に揃えろの節や docblock / コメントに出典・経緯・チケット番号・他ファイル参照を書くなの節の違反（英語のまま残っている、チケット番号が書いてある等）が前例としてあっても、その内容面の違反まで模倣するな。既存のスタイルより常にそれらの節の禁止事項を優先しろ。

## 薄いラッパー関数（1 行で外部 API を呼ぶだけ）はインライン化しろ

❌ NG（関数名と中身が同じことを言っているだけのラッパー）:
```php
private function findGroup(int $groupId): MGroup
{
    return MGroup::with(['owner', 'category'])->findOrFail($groupId);
}
```

⭕ OK（呼び出し側に直接書く）:
```php
$group = MGroup::with(['owner', 'category'])->findOrFail($input->groupId);
```

ルール:

- 関数名と中身が同じことを言っているだけならインライン化
- 「null チェック」「業務的な前処理」「複数行のクエリ組立」を含むなら関数化のままで OK
- 関数化の存在理由が「null チェックを集約する」だった場合、null チェックを削除したらラッパー自体を再評価しろ（残す意義が消えるケースが多い）

## docblock / コメントに出典・経緯・チケット番号・他ファイル参照を書くな

❌ NG（PR description に書くべき情報をソースに残す）:
```
/**
 * 入力モーダルの入力値（sample_records）
 *
 * 対象レコード単位 1:1（item_id UNIQUE）。DEMO-101 / DEMO-102。
 * owner_name / amount は一覧画面 / ダッシュボードと独立した PDF 専用値として保存する。
 *
 * 削除分類: 設定系（物理削除 / backend-flow.md §1.5）。SoftDeletes 不使用。
 */
class SampleRecord extends Model
```

⭕ OK（docblock 自体を削除。設計意図は spec / PR description に集約）:
```
class SampleRecord extends Model
```

ソースに書くな（`plans/*.md`〈チケット単位の実装計画書〉に集約せよ。plans に書いておけば `/pr` で PR description を書くときにそこから参照できる）:

- チケット番号（`DEMO-101` 等）
- デザインカンプの URL や要素 ID、デザイン仕様への参照
- 他ファイル参照（`plans/進行中/<管理表>/入力モーダル.md §1.5` / `〇〇.php の △△ メソッド` 等）
- **経緯・背景説明**（「過去版保持の業務要請は無いため」「マスタ未整備のため兼用」「以前は X だったが Y に変更」等。1 行でも書くな）。**どこまでが禁止かは純粋な経緯は消せ。実装契約・技術根拠だけ残せの節で判定しろ**
- 分類ラベル（「削除分類: 設定系」等）
- spec / PR description に書ける設計意図（DB 設計の理由、なぜこのテーブル構成か、なぜこの方式を選んだか、コスト・運用上の判断、採らなかった案とのトレードオフ、判断の根拠にした計測値・実測値 等）。**これも同じ節で判定しろ。この項目を「コードから読み取れない理由は全部書くな」の意味に読むな**
- **単一行のコードをそのまま訳しただけの解説**（例: `width: 200px` の直上に「200px に縮小」、`return $a - $b` の直上に「A から B を引く」）。**複数行の処理・条件分岐を 1 行に要約したコメントはこれに当たらない。書いてよい**
- **推測ベースのコメント**（実装者・PR description のどこにも根拠が無い背景説明。「外部提出用のため」型。書きたいなら出典を併記しろ）

後から経緯を知りたい時は **git blame → 該当 PR → PR description / plans** で辿る運用にする。ソースに書くと、参照先（チケット名・他ファイル名）がリネームされた時に rot する。

CLAUDE.md「コメント最小限」の派生ルール。

### 1行なら書いてよい。2行目以降だけ「コードの外側にある事実か」を問え

**1行に収まっているコメント・docblock は、それだけで書いてよい。** 関数名の言い換えでも、if が何を判定しているかの要約でも構わない。コードのすぐ上に1行あるほうが読み手に早く伝わり、コードを消したときコメントだけ取り残されることも起きにくい。

**判定の対象は2行目以降だけだ。** 1つのコメントが2行以上になるなら、2行目から先を1行ずつ「これはコードの外側にある事実か」と問え。答えられない行は消して1行に収めろ。

⭕ コードの外側にある（2行目以降に書いてよい）:

- 使っているツール・言語・ライブラリの仕様（`LC_ALL=C` を外すと日本語でバイト数が狂う、`sed` の置換では入れ子クォートが壊れる、この PostToolUse は成功時だけ走る）
- 実行環境の事実（launchd は最小 PATH で起動する、この環境の `[default]` に認証情報を置いていない）
- そのファイルに現れない別プロセスの存在（deny を ask に変えると無人実行が確認待ちで止まる）

❌ コードの中にある（2行目以降に書くな）:

- 何をするか・対象・動作・範囲・条件の列挙（**関数名と条件分岐がそのまま示している**）
- 「なぜこの処理が必要か」（何をするかが分かれば目的は伝わる）
- 変更したら自明に壊れること（「1回起動して以降ずっと通ると抜け道になる」は説明されるまでもない）

**行数と無関係に、1行でも書くな**: 本節冒頭のリスト（チケット番号・仕様ツールの URL・他ファイル参照・経緯・分類ラベル・spec に書ける設計意図・推測ベースの記述）と、別レイヤー・呼び出し元 / 呼び出し先の事情をコメントに書くなの節が禁じている内容。

❌ NG（1 行で言えることを無理に複数行へ伸ばす）:
```php
// 入力モーダルの送信: 登録済→送信済の初回遷移と同時に実行する。
// 順序は「PDF 生成 → upsert → ApplySampleTransition → 履歴記録」。
// 外側 DB::transaction が包括するため mPDF 例外時は全ロールバックになる。
if ($isSampleRecordFlow) {
```

⭕ OK（要点だけ 1 行に削る。経緯・手順の詳細は PR description に書く）:
```php
// 入力モーダルの送信は登録済→送信済の初回遷移と同時に実行する
if ($isSampleRecordFlow) {
```

⭕ OK（2行目以降が正当化される例。ライブラリの非自明な挙動を書かないと同じバグを踏む）:
```php
/**
 * その他条件本文を PDF 用 HTML に整形する。
 * Blade の {{ }} で出力すると改行が消失するため、HTML エスケープ後に nl2br で <br> 化し、
 * Blade 側は {!! !!} でそのまま流し込む前提とする。
 */
```

ルール:

- if 文の直前・変数宣言・class docblock・関数 docblock など、**書く場所を問わず**同じ判定をしろ
- まず 1 行に削れないか考えろ。「なぜこの分岐・この値が必要か」を 1 行で言えるなら 1 行にしろ
- 2行目以降を許すのは「これを書かないと次に触る人が同じ間違いを踏む可能性が高い」具体的な技術的根拠がある場合だけ。「念のため詳しく書いておく」「背景を残しておきたい」は理由にならない
- 罫線 + タイトルのセクション区切りコメント（`// ------` + 見出し 1 行）と、`@param` / `@return` / `@throws` / `@var` のタグ行はこの原則の対象外

### 純粋な経緯は消せ。実装契約・技術根拠だけ残せ

**コメントが実装とずれて腐るのは、コードが既に語っていることをもう一度書いた行だけだ。** コードを直せば同じ内容が2箇所にあることになり、片方が取り残される。**コードから読み取れない理由（実装契約・技術根拠）はコードのどことも重複していないので、コードを直しても腐らない。禁止の対象に含めるな。**

**この節が消させるのは「どう決まったか」という過去・将来の運用判断であって、「なぜ今この形でなければならないか」ではない。** 後者を消すと、次に触る人が理由を知らないまま形を崩す。

❌ 削除対象（純粋な経緯。過去・将来の運用判断。1 行でも書くな）:
```
// 過去版保持の業務要請は無いため SoftDeletes は使わない
// マスタ未整備のため購入側の固定額を兼用する（将来課題）
// 旧: padding 40px のせいでバーが押し込まれていた
```
→ コードからは「今こうなっている」だけが読めればよい。経緯は plans（実装計画書）/ PR description に書け。

⭕ 残してよい（実装契約・技術根拠。コードからは読み取れない Why）:
```
/**
 * その他条件本文を PDF 用 HTML に整形する。
 * Blade の {{ }} で出力すると改行が消失するため、HTML エスケープ後に nl2br で <br> 化し、
 * Blade 側は {!! !!} でそのまま流し込む前提とする。
 */

// link.click() が例外を投げても URL.revokeObjectURL がスキップされないよう try/finally で保護
```
→ 「ライブラリ X の挙動上 Z しないと Y で困る」「呼び出し側にこう書く契約」型は残せ。

**ただしこの ⭕ の例に写っている 3 行を「複数行でよい」の許可として読むな。** これは残す側に該当する内容の例であって、分量の基準ではない。残すと決めたら必ず1行なら書いてよい。2行目以降だけ「コードの外側にある事実か」を問えの節で行数を判定しろ。

**判定軸**: コメントを消したときに「次に触る人が同じバグを踏むか」を考えろ。踏むなら残せ、踏まないなら消せ。

**この判定軸は「後でレビューする時」に使うものではなく、コメントを書いたその瞬間にその場で自分に適用しろ**。書き終えてから見直すのでは遅い。2 行目以降を 1 行書くたびに次を自問しろ:

- これを削除したら、次にこのコードを読む人が実際に困る具体的なシナリオを 1 つ挙げられるか？ 挙げられないなら消す
- これは「今のコードが何をするか」ではなく「なぜ今の形になったか（経緯）」を説明していないか？
- コメントの内容を、コード自体（変数名・引数・アサーション・テスト名）を読めば導けないか？

❌ NG（テストコード内で「なぜこの payload を送るようになったか」という変更経緯を書いてしまう）:
```php
test('...', function () {
    // REGISTERED→OFFERED の transition_event=next は入力モーダルの送信を伴う契約になったため、
    // 統一 PATCH で入力値一式も同時送信する。
    $response = ...->patchJson(..., ['sample_record' => [...]]);
});
```
→ `sample_record` を payload に含めていることはコード自体で読み取れる。「なぜ必要か」は呼び出し先（Controller の 409 ガード）の話であり、このテストファイルが語る責務ではない。

⭕ OK（コメント無し。テスト名とコードで十分伝わる）:
```php
test('...', function () {
    $response = ...->patchJson(..., ['sample_record' => [...]]);
});
```

### 改行は文（句点）の切れ目でだけ入れろ。1 文を途中で折り返すな

複数行コメントを書くと決めた場合、**1 文（句点「。」で終わる単位）を 1 行に収め、文の途中で折り返すな**。

❌ NG（1 文の途中で改行が入り、目で追いにくい）:
```php
/**
 * `SampleRecordValidation::rules()` を `sample_record.` prefix で展開する
 * （inlineNewVendorTabRules と同じ「キーの有無で判定」パターン）。未送信時はルールを
 * 展開しないため required 違反にならない。未送信時の必須性判定は Controller 側の
 * 状態不整合ガード（409）が別途担う。
 */
```

⭕ OK（句点の位置でだけ改行。1 文が長くても途中で折り返さない）:
```php
/**
 * `SampleRecordValidation::rules()` を `sample_record.` prefix で展開する（inlineNewVendorTabRules と同じ「キーの有無で判定」パターン）。
 * 未送信時はルールを展開しないため required 違反にならない。
 * 未送信時の必須性判定は Controller 側の状態不整合ガード（409）が別途担う。
 */
```

ルール:

- 1 行の見た目の長さより文の意味的なまとまりを優先しろ。1 文が長くなっても、句点以外の位置で折り返すな
- **改行（＝文の数）が増えるほど、そのコメント自体が本当に必要かを docblock / コメントに出典・経緯・チケット番号・他ファイル参照を書くなの節冒頭の判定軸（残すか消すか）に戻って疑え**。文が 3 つ以上に増えるようなら、大抵は書きすぎている

### 別レイヤー・呼び出し元 / 呼び出し先の事情をコメントに書くな

❌ NG（バックエンドのコメントにフロントエンドの表示仕様を書く）:
```php
// FE は SERVER_ERROR の汎用トーストしか出さないため、原因特定をログに寄せる
```

❌ NG（関数の docblock に、呼び出し元の画面・処理ステップの事情を書く）:
```php
/**
 * 統一エンドポイント（ItemApiController）の Step 4 から呼ばれる。
 * トランザクションは呼び出し元が管理する。
 */
```

⭕ OK（そのファイル・その関数自身の責務だけを書く）:
```php
/**
 * item_status_id を更新する。
 */
```

ルール:

- コメントは「そのファイル・その関数が何をするか」だけを書け。呼び出し元がどう使うか、別レイヤー（FE/BE、別サービス）がどう振る舞うかは書くな
- 呼び出し契約（引数の意味、副作用の有無）は書いてよいが、「どの画面のどのボタンから」「フロントはこう表示する」という具体的な利用シーンは書くな
- これは本節冒頭の「他ファイル参照禁止」の延長。ファイル名を出していなくても、別レイヤーの事情を語っている時点で同じ違反

### 似た関数の docblock をコピペしたら中身も見直せ

❌ NG（複数形版を作った時、単数形の docblock をそのままコピペ）:
```ts
/** 一覧レスポンスを表示用に正規化する。 */
function normalizeItem(item) { ... }

/** 一覧レスポンスを表示用に正規化する。 */  // ← 複数形なのに単数形の説明のまま
function normalizeItems(items) {
  return items.map(normalizeItem);
}
```

⭕ OK（実態に合わせて書き分ける）:
```ts
/** レスポンス 1 件を表示用に正規化する。 */
function normalizeItem(item) { ... }

/** レスポンス一覧を表示用に正規化する（各要素は normalizeItem に委譲）。 */
function normalizeItems(items) {
  return items.map(normalizeItem);
}
```

ルール:

- 似た関数を複製・派生させるときは、コピペした docblock が新しい実装の実態と合っているか必ず見直せ
- 単数/複数、成功/失敗、同期/非同期のような対になる関数ペアで特に起きやすい

### 違反コメントを直すとき、全消しにするな

違反コメントを直すとき、**コメント全体を消すのではなく違反該当のフレーズ・節だけ削る**。

❌ NG（短絡的な全削除）:
```diff
- /**
-  * その他条件本文を PDF 用 HTML に整形する。
-  * Blade の {{ }} で出力すると改行が消失するため、HTML エスケープ後に nl2br で <br> 化し、
-  * Blade 側は {!! !!} でそのまま流し込む前提とする。
-  */
+ // （docblock 全削除）
```

⭕ OK（違反該当だけ削る。1 行目の業務意図は残す）:
```diff
  /**
   * その他条件本文を PDF 用 HTML に整形する。
-  * 過去の入力フォーム実装と同じ方針で導入。
   * Blade の {{ }} で出力すると改行が消失するため、HTML エスケープ後に nl2br で <br> 化し、
   * Blade 側は {!! !!} でそのまま流し込む前提とする。
   */
```

ルール:

- docblock の **1 行目（業務意図）は必ず残せ**
- 違反該当部分（経緯 / 他ファイル参照 / 自明な What）だけ削れ
- 違反部分を削った結果コメント全体が無意味化したら、その時だけ行ごと削除する判断もアリ
- 機能系クラス（Action / Service）の class docblock は class docblock は種類で使い分けろ。メソッド docblock はちゃんと書けの節の規約通り不要。data 系（DTO / Constants / Enum）は class docblock を残せ

## ライブラリ提供の定数 / 専用ラッパーメソッドを優先しろ

❌ NG（マジック文字列を直書き）:
```php
$content = $mpdf->Output('', 'S');
```

⭕ OK（ライブラリが用意した専用ラッパーメソッドを使う）:
```php
$content = $mpdf->OutputBinaryData();
```

⭕ OK（ライブラリ提供の定数を使う）:
```php
use Mpdf\Output\Destination;
$content = $mpdf->Output('', Destination::STRING_RETURN);
```

ルール:

- マジック文字列・マジックナンバーをライブラリの API に渡す前に、`vendor/` 配下や `node_modules/` 配下に定数や専用メソッドがないか確認しろ
- 「意味不明な空文字列」（例: `Output('', 'S')` の第1引数）を渡す状況になったら、ライブラリ側にラッパー API がないか調べろ

## 自前実装より先に言語標準 / フレームワーク機能を確認しろ

❌ NG（言語標準・フレームワークにある処理を素の for / preg_replace / 文字列連結で再実装）:
```ts
let total = 0
for (const item of items) {
  total += item.price
}
```

⭕ OK（言語標準の配列メソッドを使う）:
```ts
const total = items.reduce((sum, item) => sum + item.price, 0)
```

ルール:

- 文字列操作・配列操作・日付操作・バリデーション等を新規に書く前に、使用中の言語標準ライブラリやフレームワークに同等の機能がないか先に確認しろ
- 「自前実装 vs 標準機能」で書きやすさが同程度なら標準機能を選べ。標準機能の方が可読性・保守性で勝るケースが大半
- **新規パッケージの追加判断はこのルールに含まない**（依存追加は別途ユーザー確認が必要な操作）
- 各言語固有の具体例は `code-style-laravel`（自前実装より先にLaravel本体機能/導入済みパッケージを確認しろの節）/ `code-style-vue`（自前実装より先にVueUse/Element Plusを確認しろの節）を別途起動して読め

## 送信前に自分の diff を読み直せ

コード書き終わったら自分の diff を読み直して、上記の各項目を全部チェックしろ。特に以下は重点的に確認：

- **class / メソッドに最低限の docblock があるか**
- **チケット番号 / デザイン参照 / 他ファイル参照・設計意図を書いていないか**（docblock / コメントに出典・経緯・チケット番号・他ファイル参照を書くなの節のリスト全項目）
- **残すと決めたコメントも行数を判定したか**（1行なら書いてよい。2行目以降だけ「コードの外側にある事実か」を問えの節）。**2 行以上になっているものは2行目から1行ずつ「消したとき次の人がどう壊すか」を言えるか試し、言えない行を削れ**
- **コメントが別レイヤー・呼び出し元 / 呼び出し先の事情を語っていないか**（同節）
- **既存の docblock をコピペした箇所で、内容が新しい実装の実態と合っているか**（同節）

読みづらい箇所が残っていたら直してから報告しろ。

各言語・領域固有のチェック項目は `code-style-laravel` / `code-style-vue` / `code-style-ts` / `code-style-cdk` / `code-style-cicd` を別途起動して読め。
