PR を作成する、既存 PR の本文・label / assignee / reviewer を編集する、または既存 PR への追加コミットを push するスキル。skill 冒頭で「新規 PR 作成モード」「既存 PR への追加コミット push モード」「既存 PR 編集モード」のどれかを判定して分岐する。`--draft` を付けると新規 PR 作成モードで Draft PR を作る。**ユーザーが「label つけて」「アサインして」「reviewer 追加して」「PR 本文を直して」「ドラフトで作って」「draft PR にして」と言ったとき、生の `gh pr create` / `gh pr edit` を直接叩かずこのスキルを経由しろ**（label / assignee / reviewer の追加と本文の編集は既存 PR 編集モードに、ドラフト作成は新規 PR 作成モードの `--draft` 指定に、それぞれ自動で入る）。既存 PR にレビュー指摘対応・追加修正のコミットを push したいときも、生の `git push` だけで終わらせずこのスキルを経由しろ（既存 PR への追加コミット push モードが担当する）。

**事前確認は原則するな。黙って push / PR 作成 / PR 編集を実行して結果（URL と適用内容）だけ報告しろ。** 例外として確認を取るのは以下のときだけ:

- **カレントブランチに open PR がある / マージ済みで、かつ未 push のコミットが無いとき** → 新規作成と編集の選択肢を提示（モード判定の文脈で必要。未 push のコミットがあるときは「既存 PR への追加コミット push モード」へ確認なしで自動的に入る）
- **`--reviewer` の引数が GitHub login の形になっていない** → 誤通知防止のため AskUserQuestion で login を聞け
- **他人の PR を編集しようとしたとき**（既存 PR 編集モードで author が自分以外） → 編集していいか確認
- **base ブランチ候補が複数あるとき**（default 以外にも `develop` 等の統合ブランチが存在） → プロジェクトごとにブランチ運用が違うため、どの統合ブランチを base にするか毎回選ばせろ
- **新規 PR 作成モードで `--reviewer` も `--draft` も指定されていないとき** → reviewer を指定するか確認しろ（Draft PR は基本 reviewer なしで作る運用のため対象外。既存 PR 編集モードは label/assignee だけ追加したいケースもあるため対象外）。**ただし、現在のプロジェクトの `CLAUDE.md` / `README.md` 等に「レビュー不要」「他者レビューは任意」「self-approve でマージして OK」のような、reviewer を付けない運用が明記されている場合は確認せず reviewer なしで進めろ**（曖昧な記述では判断せず、明記されているときだけ適用しろ）
- **新規 PR 作成モードで、変更ファイルのパスが重なっただけの実装計画書の候補が見つかったとき**（「実装計画の参照」の経路B） → その計画書を今回の PR に紐付けていいか確認しろ。誤って紐付けると他の作業中の計画書を巻き込んで `レビュー中` → `完了` まで動かしてしまう。**ただし、このセッションでユーザー自身がその計画書を指している場合と、その計画書を読んでそれを根拠に実装した場合は確認するな**（条件は「実装計画の参照」参照）
- **新規 PR 作成モードで統合PR（develop ← dev-X.X.X 等）と判定したとき** → 詳細な説明文まで書くか、参照リンクの列挙だけで足りるかを本文を書き始める前に確認しろ（「新規 PR 作成モードの手順」の統合PRの項参照）

上のリストとは別に、**新規 PR 作成モードで reviewer が 1 人以上確定したときは、PR 作成前に本文の下書きをそのまま見せろ**（reviewer なしなら不要）。これは「事前確認は原則するな」と衝突しない。原則が禁じているのは「push / PR 作成 / PR 編集を実行していいか」を聞くことで、ここで聞いているのは実行の可否ではなく**他人に届く文章の中身**だからだ。reviewer を付けて PR を作った瞬間に相手へ通知が飛び、それは取り消せない。作成後に `gh pr edit` で直しても、直す前の文章が既に相手の手元に届いている。

新規 PR 作成モードでは PR 作成前に base ブランチの最新変更を作業ブランチへ `git pull` で取り込め（チーム開発での差分ズレ防止）。コンフリクトが起きたら自動解決せず止めてユーザーに報告しろ。また `.env*` や docker-compose / CI の `env:` 等、env・環境変数の変更を検出したら、PR 本文に変更キー名を明記し、報告時にチームへの共有をテキストで呼びかけろ（詳細は各セクション参照）。

## 引数

- 位置引数: 数字のみなら**既存 PR の番号**として扱う / それ以外は **PR タイトル**（新規 PR 作成モード）。省略時は commit から生成
- `--draft`: 新規 PR 作成モードで指定すると Draft PR として作成する（`gh pr create --draft`）。既存 PR 編集モードでは対象外（無視して警告）
- `--reviewer <login>`: レビュアー指定。GitHub login をそのまま渡せ。複数指定は `--reviewer A --reviewer B`（Draft 作成時は基本 reviewer なしで作るが、明示指定があれば付ける）
- `--label <label>`: label を手動指定（変更ファイル推定を上書き）。複数指定は `--label A --label B`

## モード判定（最初にこれをやる）

以下の分岐条件を**この順番で**確認しろ。最初に当てはまったモードに切り替えろ。どれにも該当しなければ「**新規 PR 作成モード**」（既存挙動）に進め。

### 既存 PR への追加コミット push モードへの分岐条件

- **第1位置引数が数字のみではない**（PR 番号を明示指定していない） かつ **カレントブランチに open PR がある** かつ **未 push のコミットが存在する**（リモートに同名ブランチが存在し、`git log origin/<カレントブランチ>..HEAD --oneline` が1件以上）→ **確認なしで**自動的にこのモードへ入れ。`nt-developer:commit` の「コミット後の自動連鎖」から呼ばれた場合、ほぼ常にこれが目的であり、都度 AskUserQuestion で聞くと「事前確認は原則するな」という方針と逆行する
- リモートに同名ブランチが存在しない（一度も push していない）場合はこのモードの対象外。次の分岐（既存 PR 編集モード）または新規 PR 作成モードの判定に進め

### 既存 PR 編集モードへの分岐条件

- **第1位置引数が数字のみ**（例: `/pr 212`）→ 引数の PR 番号を対象に編集モードへ。確認不要
- **カレントブランチに open PR があり、かつ「既存 PR への追加コミット push モード」の条件に当てはまらない**（未 push のコミットが無い） → `gh pr list --head "$(git symbolic-ref --short HEAD)" --state open --json number,title --jq '.[0]|select(.)|"\(.number)\t\(.title)"'` で取れたら、AskUserQuestion で「既存 PR #N 『<title>』を編集 / 新規 PR 作成 / 中止」を聞いて分岐
- **カレントブランチが既にマージ済み**（`--state merged` で同コマンドがヒット） → 「カレントブランチは既にマージ済みなので新規 PR は作れない。どの open PR を編集？」と説明し、`gh pr list --state open --json number,title,headRefName --jq '.[]|"#\(.number) \(.title) (\(.headRefName))"'` の一覧を AskUserQuestion で選ばせろ。中止選択肢も用意

判定が終わったら:
- 新規 PR 作成モード → 「**新規 PR 作成モードの手順**」へ
- 既存 PR への追加コミット push モード → 「**既存 PR への追加コミット push モードの手順**」へ
- 既存 PR 編集モード → 「**既存 PR 編集モードの手順**」へ

## base ブランチの検出

!`git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null`

上記はリモート origin のデフォルトブランチを `origin/<branch>` 形式で返す（例: `origin/master`）。`origin/` を除いた部分を default ブランチとする。空（origin/HEAD 未設定）ならローカルに実在する `main` / `master` / `develop` のうち1つを default とする。

**プロジェクトごとにブランチ運用が異なる**（例: `develop` から切った作業ブランチは `develop` へ、`master` から切った修正ブランチは `master` へ、といった使い分けをしているリポジトリがある）。default ブランチを機械的に決め打ちするな。以下の手順で毎回判定しろ:

- ユーザーが引数で base を明示した場合はそれを最優先し、以降の判定は不要
- `git branch -r` でリモートブランチ一覧を取得し、default 以外に長期運用されていそうな統合ブランチ（`develop` / `staging` / `release/*` 等、`feature/*` や個人名ブランチのような一時的なものは除く）が存在するか確認しろ
- default 以外の統合ブランチが1つでも見つかったら、**AskUserQuestion で「このPRのbaseはどれか」を必ず確認しろ**（カレントブランチ名から自動推測できそうに見えても、プロジェクトごとの運用差が大きく誤検出のリスクが高いため推測で決めるな）。選択肢には default ブランチと検出した統合ブランチ全部を含めろ
- default 以外に統合ブランチが無ければ確認不要、そのまま default を使え

## reviewer の指定

- `--reviewer` の引数は **GitHub login としてそのまま `gh` に渡せ**（ASCII の英数字とハイフンのみの形なら login と見なす）
- login の形でない引数（日本語の呼び名等）を渡されたら、推測で login を組み立てるな。**AskUserQuestion で GitHub login を聞け**

## label の推定

- リポジトリの label 一覧を `gh label list --json name --jq '.[].name'` で取得しろ（**`--jq` に raw 出力フラグ（`-r`）を付けるな**。`gh` では `unknown command` で失敗する。`gh` の `--jq` は文字列をクォート無しでそのまま出力するので、この指定はそもそも不要だ）
- 変更ファイル一覧を取得しろ:
  - 新規 PR モード: `git diff --name-only <base>...HEAD`
  - 既存 PR モード: `gh pr diff <番号> --name-only`
- 以下のルールで type を推定（複数該当 OK、全部候補に積め）:

| 推定 type | 判定条件 |
|---|---|
| **web** / **frontend** | 拡張子 `.vue` / `.ts` / `.tsx` / `.js` / `.jsx` / `.scss` / `.css` / `.html` を含むファイル、または `resources/assets/` / `frontend/` / `sass/` / `assets/` 配下を1つ以上含む |
| **backend** | 拡張子 `.php` / `.py` / `.rb` / `.go` を含むファイル、または `app/` / `src/` / `database/migrations/` / `api/` 配下を1つ以上含む |
| **docs** | 変更ファイルが `docs/` 配下 or `*.md` **のみ**で構成されている |
| **CI/CD** / **github_actions** | `.github/workflows/` 配下 or `.github/actions/` 配下を1つ以上含む |
| **infra** | `infra/` / `terraform/` / `kubernetes/` / `k8s/` 配下、または `Dockerfile` / `docker-compose*.yml` / `.dockerignore` / `Makefile` のいずれかを含む |
| **dependencies** | ロックファイル（`composer.lock` / `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` / `Gemfile.lock` / `Pipfile.lock` / `poetry.lock` / `go.sum`）を1つ以上含む |
| **php** | `.php` 拡張子のファイル、または `composer.json` / `composer.lock` を含む |
| **javascript** | `.js` / `.ts` / `.tsx` / `.jsx` 拡張子のファイル、または `package.json` / `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` を含む |

- 推定した type をリポジトリの label 一覧と突き合わせ、**実在する label のみ付与しろ**。実在しない type は黙って捨てろ（リポジトリで運用していない label を勝手に作るな）
- `--label` 引数が指定されていれば推定を上書きしろ（手動指定された label が実在しなければ確認の上で中止）
- 推定 type と実在 label の AND の結果が 0 件 → label なしで作成 / 編集して OK
- 同じ意味で別名が複数候補に挙がる場合（例: `web` と `frontend`、`CI/CD` と `github_actions`）、**実在する方を優先**。両方実在する場合は両方付けろ（リポジトリの運用に合わせる）

## env / 環境変数変更の検出

**前提**: `.env` / `.env.local` / `.env.production` 等の実ファイルは通常 `.gitignore` 対象で、そもそも PR の diff に現れない。ファイル名パターンだけでは検出できないので、「gitignore されない箇所での env 変更」と「コード側の新規 env 参照」の2軸で判定しろ。

以下のいずれかに該当したら「env / 環境変数変更あり」と判定しろ:

- `.env.example` / `.env.*.example` / `.env.sample` 等の**テンプレート系 env ファイル**（gitignore 対象外で運用されることが多い）の変更
- 変更ファイルパスに `docker-compose` を含む（`docker-compose.yml` / `docker-compose.*.yml`）
- `.github/workflows/` 配下の変更で、diff 内に `env:` の追加・変更行がある
- `infra/` / `cdk/` / `terraform/` 等のインフラ定義配下の変更で、diff 内に `environment:` / `Environment:` プロパティの追加・変更行がある
- **コード側の diff 追加行**に `env(` / `process.env.` / `getenv(` / `System.getenv(` / `os.environ` 等、新規の環境変数参照パターンが現れる（新しい環境変数キーへの依存が追加された強いシグナル。実ファイルの `.env` 自体が見えなくても、コード側の変更からの間接検出ができる）

判定対象は `git diff <base>...HEAD`（変更ファイル一覧 + diff 本文）。該当したら以下の両方を必ず実施しろ:

- **PR 本文に `## 環境変数・設定変更` セクションを追加**し、変更された環境変数・設定キーの**名前のみ**を列挙しろ。値は機密の可能性があるため本文に絶対書くな
- **PR 作成後の報告メッセージで「このPRは env / 環境変数の変更を含みます。チームに共有してください」とユーザーに明示的にテキストで呼びかけろ**。チャットツール等への実際の送信はこのスキルの対象外（ユーザーに促すだけで、勝手に送信するな）

**限界**: 実ファイルの `.env` は gitignore 対象のため、その値の変更自体は検出できない。この判定はあくまで「gitignore されない設定ファイル」と「コード側の新規参照」からの間接検出であり、見逃しがあり得る前提で運用しろ。検出できなかったからといって env 変更が無いとは限らない。

この判定は**新規 PR 作成モードでのみ**行え（既存 PR 編集モードで本文を編集するときは、依頼された内容だけを反映しろ）。

## 実装計画の参照（plans/*.md または GitHub Issue）

実装計画に書かれた設計意図・背景を PR description に反映しろ。書き込み先は2通りある（どちらに書くかの判定は `nt-developer:plan` が正本）。両方を探し、見つかった方を使え。

### plans/*.md（ローカルの実装計画書）

- チケット単位の実装計画書（`plans/<状態>/<管理表>/<日本語タイトル>-<チケットID>.md`）が対象
- **1つの PR に複数チケットの計画書がまとまることは普通にある**ので、1件見つかった時点で打ち切らず全件集めろ。
   - **変更ファイルの重なりで探せ（要確認）**: `plans/進行中/` 配下の `.md` を `find` で列挙して全部 Read し、各計画書の「触るファイル」節に挙がっているパスが `git diff --name-only <base>...HEAD` の結果と1つ以上重なるものを**候補**として拾え（`plans/レビュー中/` は既に別の PR に紐付いているため対象外）。**経路A で既に見つかっていてもこの経路を省くな**（別チケットの計画書が同じ PR に含まれていることに気づけなくなる）
- **候補をそのまま採用するな。まず内容を照合しろ。** パスの重なりは「同じファイルを触る別の作業」でも成立する。`docs/*.md` や共通コンポーネントのように、複数の計画書が同時に「触るファイル」へ挙げるファイルは実在する:
   - **内容の照合**: 候補の「変更後・対応内容」に書かれている変更が `git diff <base>...HEAD` に実際に含まれているかを読んで確かめろ。含まれていなければ候補から外せ（パスだけ重なった別作業だ）
- **内容の照合を通った候補のうち、次のどちらかに当てはまるものは確認なしで採用しろ。** どちらも「その計画書が今回の作業のものだ」とセッション中の事実で裏が取れているので、改めて聞いても答えは変わらない:
   - このセッションでユーザー自身がその計画書を指している（`nt-developer:plan` でその計画書を書いた / `nt-developer:code-review` の引数としてパスを渡された / 会話でパスを示して「この計画で実装して」と言われた）
   - その計画書を自分で Read し、それを根拠に今回の実装をした
- **どちらにも当てはまらず、「触るファイル」のパスが重なっただけの候補は、AskUserQuestion で「この計画書を今回の PR に紐付けていいか」を確認しろ。承認されたものだけ採用しろ。** 経路A で見つかったものは確認不要でそのまま採用しろ
- **採用が確定した経路B の計画書は、以降の扱いを経路A と同じにしろ**（本文への反映・`レビュー中` への移動・PR 番号の目印の追記すべて）。**採用しなかった候補はこの PR に一切紐付けるな**（本文にも書くな、移動もするな、目印も書くな）。誤って紐付けると、他の作業中の計画書が勝手に `レビュー中` へ移されたうえ、マージ時に hook が `完了` まで動かしてしまう
- **「触るファイル」節からパスを取り出すときの注意**: 1行に複数のパスと日本語の説明が混在していることがある（例: `html/.env / html/.env.example（環境変数を追加）`）ので、1行1パスと決めつけずパスの形をしたものを全部拾え。ファイルのパスでない項目（AWS の SSM パラメータ名等）と、`.env` のように Git 管理外で差分に絶対現れないファイルは重なり判定の材料にならないので無視しろ
- 採用が確定したファイル（経路A の全件 + 経路B で承認された分）は全件 Read で全文読め
- **見つかったファイルのパスは全件、PR 作成後まで保持しろ**（PR 作成後に、同梱 hook が移せなかった分を自分で `レビュー中` へ移すときに使う。「新規 PR 作成モードの手順」参照）

### GitHub Issue の description

- カレントブランチ名（`git symbolic-ref --short HEAD`）と `git log <base>..HEAD` のコミットメッセージから Issue 番号を探せ。`#<数字>` / ブランチ名先頭の `<数字>-` / Issue の URL が対象だ
- 検出した番号が実在するか `gh issue view <番号> --json number,title,body` で確認しろ。取得できなければスキップしろ（ブランチ名の数字が Issue 番号でないことは普通にある）
- **取得した Issue のタイトル・本文が今回の差分と無関係なら使うな**（`fix-2-bugs` のようなブランチ名から拾った数字が、たまたま実在する別の Issue に当たることがある）
- Issues が無効・`gh` が未認証のリポジトリではこの経路はスキップされる

### 反映のしかた（経路共通）

- **計画の内容をそのまま転記するな**。`git diff <base>...HEAD` と突き合わせ、**今回の PR に実際に含まれる差分に対応する内容だけ**を抜き出せ。実装中の紆余曲折・最終的な差分と無関係な将来課題は書くな
- 計画の節と PR 本文セクションの対応は次の表に従え。**差分に関係する節は1つも漏らすな**。表に無い節（実装ステップ・触るファイル 等）は転記対象外だ

| 計画の節 | 転記先の PR 本文セクション |
|---|---|
| 背景 | 変更理由 |
| 現状 | 変更理由 |
| 実装中に確定したこと（節名の揺れを含む） | 変更理由 |
| 決めたこと（表） | 決めたこと（新設） |
| 承認記録 | 決めたこと（新設） |
| 確認テストの「該当した観点」 | 設計判断・スコープ |
| 採らなかった案 / この判断を覆す条件 / 未解決事項 / 今回やらないこと | 設計判断・スコープ |
| 検証・完了条件 | 動作確認内容 |
| 検証・完了条件の「よりどころにする資料からの逸脱」の表 | よりどころにする資料からの逸脱 |
| 参照節の太字ラベルに「チケット」を含む箇条書き | 関連チケット |

- **差分に関係するのに対応表の節が計画に無い、または載せると決めたのに省いた場合は、なぜ載せないかを自分に問え。** 答えられないなら省くな。答えが「今回の差分と無関係だから」であれば、その節ごと省いて構わない
- 「決めたこと」表と承認記録は、対応する `## 決めたこと` セクションへ表・箇条書きのまま転記しろ。今回の差分と無関係な行（別チケット向けの決定等）は含めるな。該当する行が1件も無ければこのセクション自体を省け
- 確認テストの「該当した観点」は、今回の差分に関係するものだけを断定文のまま `## 設計判断・スコープ` に含めろ。「該当なしと判定した観点」は転記対象にしない（レビュアーの判断材料にならない）
- **計画の「検証・完了条件」に「よりどころにする資料からの逸脱」の表があれば、今回の差分に関係する行を `## よりどころにする資料からの逸脱` セクションとして PR 本文へ転記しろ**（`plan` skill の「逸脱の記録は「検証・完了条件」に残せ」）。**各行から次の5つを1つも落とすな**: 対象 / よりどころにする資料の期待値（よりどころにする資料の文言のまま）/ 採用した挙動 / 根拠の出所（誰が・いつ・どの対象について出した根拠か）/ その根拠が及ぶ適用範囲。**根拠の対象を書かずに「実測済み」「確認済み」「承認済み」だけを書くな。** 読み手はそれを対象全体に及ぶ承認済みの設計変更と読む
   - **根拠が一部の対象にしか及んでいない場合、根拠の及ぶ対象と、それを他の対象へ広げた承認の有無を行として分けて書け。** まとめて1行にすると、根拠の範囲が対象全体に及んでいるように読める
   - 逸脱の表が計画に無い、または今回の差分に関係する行が無ければこのセクションごと省け。**逸脱を「採らなかった案」や「設計判断・スコープ」に混ぜて書くな**（レビュアーがよりどころにする資料と照合すべき項目だと気づけない）
- **計画書の「採らなかった案」「この判断を覆す条件」「未解決事項」「今回やらないこと」に書かれた内容も、今回の差分に関係するものに限り抜き出し、`## 設計判断・スコープ` セクションとして PR 本文に反映しろ。** 差分と無関係な項目（別チケット向けの検討事項等）は含めるな。該当する項目が1件も無ければこのセクション自体を省け。レビュアーが「これは意図的に対応していないのか、見落としなのか」を PR 本文だけで判断できるようにするための項目だ
- **採用が確定した `plans/*.md` に書かれたチケットのリンクを、PR 本文に `## 関連チケット` セクションとして全件列挙しろ。** GitHub が自動でリンクしてくれるのは GitHub Issue（`Closes #<番号>`）だけで、それ以外の管理表のチケットは**本文に URL を書かない限り PR から一切追跡できない**。GitHub Issue 経路は `Closes #<番号>` で追跡できるためこのセクションの対象外だ
   - 拾う対象は**太字ラベルに「チケット」を含む箇条書きだけ**に限れ。**Markdown リンクを無条件に全部拾うな。** 同じ節にはチケット以外に「よりどころにする資料」「参考資料（経緯を追うだけで判断の根拠にしない）」「運用ドキュメント」等が同じ箇条書き形式で並んでおり、関係のないリンクまで関連チケットとして載ってしまう
   - 探す範囲はまず `## 参照` 節にしろ。**見出しの表記は計画書によって揺れる**ので、この見出しが無ければ本文全体から同じ条件（太字ラベルに「チケット」を含む箇条書き）で探せ
   - 書くのはリンク（タイトル + URL）だけにしろ。行末に付いている優先度・担当者・ステータス等の内部トリアージ情報は落とせ（レビュアーの判断材料にならず、時間とともに古くなる）
   - `http` / `https` で始まらないリンク（他の計画書への相対リンク等）は書くな。レビュアーが開けない
   - 条件に合うチケットが1件も無ければ `## 関連チケット` セクションごと省け
- **GitHub Issue 経路で見つかった Issue は、PR 本文末尾に確認なしで `Closes #<番号>` を追記しろ。** 「GitHub Issue の description」の手順で既に「今回の差分と無関係なら使うな」という関連性確認を通過している Issue なので、改めてユーザーに書くかどうかを確認する必要は無い。マージ時に GitHub が自動で Issue をクローズする仕組み（[Linking a pull request to an issue](https://docs.github.com/ja/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)）を利用する。複数の関連 Issue が見つかった場合は `Closes #<番号1>` と `Closes #<番号2>` のように行を分けて書け
- **`plans/*.md` 経路は対象外**（GitHub Issue 番号を持たないため紐付けようがない）。この経路で見つかった計画にチケット ID が書かれていても、`Closes #<番号>` はそれに使うな（GitHub Issue 専用のキーワードだ）

計画書・Issue の探索と採用の判定は**新規 PR 作成モードでのみ**行え（既存 PR 編集モードで本文を編集するときは、依頼された内容だけを反映しろ）。**ただし「反映のしかた（経路共通）」の対応表は、既存 PR への追加コミット push モードが本文の食い違いを直すときにも使え**（「既存 PR への追加コミット push モードの手順」参照）。

## 新規 PR 作成モードの手順

- **head ブランチを決定しろ（最初に必ずやれ）**: 通常はカレントブランチがそのまま head になる。**ただし、ユーザーが別ブランチの統合を頼んだときのように、カレントブランチとは別の既存リモートブランチ間の PR 作成を頼んだ場合、そのブランチをチェックアウトするな。** `gh pr create --head <head ブランチ名> --base <base>` は head 引数にブランチ名を渡すだけで PR を作成できる。ローカルでのチェックアウトは不要な操作であり、頼まれていない git 操作をするな。head がカレントブランチと異なる場合、以降の「base ブランチの最新変更を作業ブランチに取り込め」の `git stash` / `git pull` の手順もスキップしろ（既にリモートに存在する確定済みブランチを取り込み直す必要は無い）。変更ファイル一覧・env 検出等の判定も `git diff <base>...<head 参照>`（例: `origin/dev-10.3.7`）で行い、ローカルのブランチ切り替えは発生させるな
- **統合PR（develop ← dev-X.X.X 等、複数の作業ブランチをまとめてデプロイ用ブランチへ取り込む PR）を判定しろ**: `git log <base>..<head 参照> --merges --oneline` に複数のマージコミットが含まれる場合、このPRを統合PRとして扱え。統合PRは通常のfeature PRと性質が違うため、以下を変えろ:
   - **タイトル**: 含まれる元のfeature PRのタイトルを使い回すな。統合PR自体の目的（例:「10.3.7の改修内容を開発環境にデプロイします」）を表す新しいタイトルを作れ。「もっと分かりやすいタイトルに」と言われた文脈は、直前に出したタイトルの言い回しの改善であり、元のfeature PRのタイトルへの差し替えではない
   - **本文**: 標準項目（変更概要・変更理由・動作確認内容・懸念点）を機械的に埋めるな。含まれる各マージコミット・feature PRへの参照を列挙する簡潔な形を基本にしろ。**同一リポジトリ内の PR/Issue 参照はフルURL（`https://github.com/...`）ではなく `#<番号>` 形式で書け**（GitHub が自動でリンクする）。**詳細な説明文まで必要か、参照リンクの列挙だけで足りるかを、本文を書き始める前に一言確認しろ**（統合PRの本文量はプロジェクトごとに運用の幅が大きく機械的に決め打ちできないため。これは「事前確認は原則するな」の新しい例外だ）
- **チーム開発の一貫性のため、base ブランチの最新変更を作業ブランチに取り込め**（head がカレントブランチと異なる場合はこの手順全体をスキップしろ）:
   - `git status` で作業ディレクトリの変更を確認しろ。未コミットの変更（tracked / untracked 問わず）があれば `git stash push -u` で退避しろ
   - `git pull origin <base>` で base ブランチの最新変更を作業ブランチに取り込め
   - コンフリクトが発生したら、そこで止めてユーザーに状況を報告し指示を仰げ（自動解決するな）。直前の `git status` 確認で stash していた場合は pop せず残しておけ（コンフリクト解消後にユーザー自身が pop する）
   - コンフリクトなく取り込めたら、直前の `git status` 確認で stash していた場合は `git stash pop` で戻せ
- 引数を解析しろ: 位置引数 → PR タイトル / `--draft` → Draft フラグ / `--reviewer` → reviewer リスト / `--label` → label リスト
- `git log <base>..HEAD` と `git diff --stat <base>...HEAD` で PR に含まれる変更を確認しろ
- PR タイトル省略時は最新コミットメッセージの第1行（複数コミットなら集約した日本語タイトル）を作成しろ
- 「env / 環境変数変更の検出」の判定を行え
- 「実装計画の参照」の手順を実行しろ（詳細は「実装計画の参照」参照）
- PR 本文を作成しろ:
   - `.github/PULL_REQUEST_TEMPLATE.md`（または `.github/pull_request_template.md`）があればその項目立てに従え
   - 無ければ標準項目（変更概要・変更理由・動作確認内容・懸念点）を含めろ
   - 比較検討・理由等の技術的な深い内容は `<details><summary>` で折りたたんでよい。レビュアーは結論だけ読めば済み、気になる人だけ開いて根拠を追える
   - 「env / 環境変数変更の検出」の判定で変更ありと判定した場合、`## 環境変数・設定変更` セクションを追加し変更キー名を列挙しろ
   - 「実装計画の参照」の手順で抜き出した背景・現状・実装中に確定したことがあれば「変更理由」に反映しろ
   - 計画の「決めたこと」表・承認記録があれば `## 決めたこと` セクションを新設して反映しろ（新設する PR 本文セクションはこの1つだけにしろ）
   - 「実装計画の参照」の手順で抜き出した確認テストの該当した観点・採らなかった案・判断を覆す条件・未解決事項・今回やらないことがあれば `## 設計判断・スコープ` セクションを追加しろ
   - 計画の「検証・完了条件」があれば「動作確認内容」に反映しろ。うち「よりどころにする資料からの逸脱」の表は別に `## よりどころにする資料からの逸脱` セクションへ切り出せ（必須要素と書き方は「反映のしかた（経路共通）」参照）
   - 対応表に載っているのに転記していない節が無いか、書き終える前に「反映のしかた（経路共通）」の対応表と突き合わせろ
   - PR 本文は**レビュアーが読むもの**である。レビュアー視点で意味が通る情報だけを書け。以下は書くな:
     - AIエージェント自身の作業プロセスや使った内部ツールの名前（コードレビュー用スキルの内部判定結果、MCP 経由の取得手段等）
     - 個人的な作業メモ・仕様メモ（プロジェクトがよりどころにするドキュメントでないもの）を、よりどころにする資料であるかのように参照させる書き方
     - git 管理外のファイルパス（レビュアーが clone しても実在せず開けないパス）
     - **自分のローカル固有の事情を、他の開発者にも当てはまる前提にした注意書き**（例: git 管理外の個人用 migration を自分が置いていたためにテストが落ちた話を「同じものを持っている方は同様の対応が必要です」と書く。他の人がそれを持っているかは確認できず、そもそもプロジェクトの規約に無い運用なら他人はやっていない。自分の環境で起きたことは、その原因が変更内容そのものにあるときだけ書け）
   - git 操作の専門用語（「develop 未マージ」等）をそのまま書くな。何が起きているかを平易な言葉に言い換えろ（例:「別の作業のコミットがまだ共通ブランチに取り込まれていないため、このPRにも一緒に含まれています」のように、レビュアーが実際に何を確認すればいいかが伝わる書き方にしろ）
   - 「元々」「以前から」「もともと」「これまで」等、**過去の状態や経緯を断定する記述**を書く前に、実際の裏付け（base ブランチ側の該当ファイルの実際の内容、git 履歴、過去のコミット等）を確認しろ。確認していない・確認できないなら、その断定表現を使うな（推測で経緯を語るな）
   - 特に「このPRで新しく追加した方針・ルール」と「以前から存在していた方針・ルール」は混同しやすい。両者を書き分けるときは、必ず該当の base ブランチ（例: `develop`）側の実際のファイル内容を確認してから書け
   - 本文を書き終えたら、レビュアー本人になったつもりで読み返し、意味が通らない語やレビュアーが確認できない参照が残っていないか確認しろ
- reviewer を決定しろ:
   - `--reviewer` が1つ以上指定されていれば、そのまま login のリストとして扱え。**login の形になっていない引数があるときだけ** AskUserQuestion で確認しろ
   - `--reviewer` が未指定 かつ `--draft` も未指定なら、まず現在のプロジェクトの `CLAUDE.md` / `README.md` 等に「レビュー不要」「他者レビューは任意」「self-approve でマージして OK」のような、reviewer を付けない運用が明記されているか確認しろ。明記されていれば確認せず reviewer なしで進めろ。明記が無ければ AskUserQuestion で reviewer を確認しろ。選択肢は「指定しない」＋ Other の自由入力で聞き、Other には GitHub login を入力させろ。「指定しない」を選んだら reviewer なしで進めろ
   - `--reviewer` が未指定 かつ `--draft` 指定時は確認せず reviewer なしで進めろ（Draft はまだレビュー段階でないため）
- **reviewer が 1 人以上確定したら、PR 作成前に本文の下書きをそのままユーザーに提示しろ**。他者が読む前提の文章になっているか確認してもらう機会を挟め。修正指示があれば反映し、承認を得てから次に進め。reviewer が居ない場合（「指定しない」を選んだ・Draft 作成時）はこの確認は不要。これは実行の可否を聞いているのではなく、相手に通知が飛んだあとでは取り消せない文章の中身を確認しているので、「事前確認は原則するな」の対象外だ（skill 冒頭参照）
- **本文に追記の見込みが残っている場合**（実装計画の参照で紐付け候補がまだ確定していない、後から追記が要ると分かっている等）は、reviewer を付けずに先に `gh pr create` し、本文を完全に固めてから `gh pr edit --add-reviewer` でレビュアーを追加しろ。**reviewer 付きで作成した本文を、作成後に追記・修正するな**
- **本文・タイトルの修正指示を受けたら、まず指示の範囲を確認しろ**。「〇〇でいいのでは」「〇〇だけで良くない？」のような疑問形の発言は、その通りに全部書き換えろという実行指示だと決めつけるな。範囲が読み取れないときは、見出し構造ごと本文を削除する等、指示された範囲を超えた変更を先にするな。修正後は指示された範囲だけが変わったことを自分で確認しろ
- **ユーザーが強い言葉で修正を一度指示した直後の反映は、再度「これでいいか」を確認するな。** そのまま実行して結果を報告しろ。直前の項目の「reviewer 確定時の下書き確認」は最初の下書きを提示する場面の話で、その後の明示的な修正指示への対応にまで適用するな（確認を毎回挟むと、既に強く指示した内容の実行が遅れるだけで意味が無い）
- label を変更ファイルから推定 + リポジトリの label 一覧で存在チェック
- **事前確認なしで** リモートへ push しろ（push 済みなら省略可）
- **事前確認なしで** PR を作成しろ: `gh pr create --base <base>` に以下を渡せ
   - `--title <title>` / `--body <body>`
   - `--draft`: `--draft` 指定時のみ付与（Draft PR として作成）
   - 自己 assign: 常に `--assignee @me` を付けろ。省略するな（同梱 hook が `--assignee` 無しの `gh pr create` を検知して deny する）
   - reviewer: 解決済み login ごとに `--reviewer <login>` を繰り返し
   - label: 存在チェック OK の label ごとに `--label <name>` を繰り返し
- **`plans/*.md` の `レビュー中` への移動は、同梱 hook が `gh pr create` の成功を受けて自動で行う。** hook は `plans/進行中/` の計画書のうち**ファイル名のチケット ID がブランチ名・PR タイトル・コミットメッセージのどれかに現れるもの**を、管理表のディレクトリを保ったまま `plans/レビュー中/` へ移し、1行目に `<!-- PR: #<番号> -->` を書く。この目印がマージ時に `plans/完了/` へ移すための紐付けになる。**自分で同じことをするな**（PR 作成前は番号が分からず、作成後は hook が既に済ませている）
- **hook が移せなかった計画書だけ自分で移せ。** ファイル名にチケット ID を持たない計画書（`チームキー-数字` 形式でない管理表のチケット、`plans/other/` 配下）は、今回の PR のものかを機械的に判定できないため hook は移さない。代わりに hook が「今回の差分で変更したファイルに触れている計画書」を PR 番号付きで挙げて通知する。その中に「実装計画の参照」で採用が確定したものがあれば、管理表のディレクトリを保ったまま `plans/レビュー中/` へ `mv` し、1行目に `<!-- PR: #<番号> -->` を書け（既に同じ形式の行があれば番号を書き換えろ。1行目でない位置に書くな）。**採用が確定した分は1件も漏らすな。漏らしたファイルだけマージ時の自動移動から取り残される。** 採用していない候補には手を触れるな。GitHub Issue 経路（渡せるファイルが無い）ではこの処理は不要
- 作成した PR の URL と適用内容（タイトル / Draft か否か / reviewer / assignee / label）を簡潔に報告しろ。plans 経路の計画書を `レビュー中` へ移した場合は移動先パスも報告に含めろ。「env / 環境変数変更の検出」の判定で変更ありと判定していれば、報告の最後に「このPRは env / 環境変数の変更を含みます。チームに共有してください」と明示的に添えろ

## 既存 PR への追加コミット push モードの手順

レビュー指摘対応の修正コミット・追加修正コミットを既存 PR に push するケースを担当する。`nt-developer:commit` の「コミット後の自動連鎖」から起動されたときの主要な経路になる。

- **push 前に `gh pr view <番号> --json state` でその PR の state を個別確認しろ。** ブランチが使い回されている場合、`gh pr list --state open` の検索結果だけで「継続」と判断せず、push する前に一度 AskUserQuestion で方針を確認しろ
- state が open だと確認できたら、**事前確認なしで** `git push` しろ
- push が終わったら、**必ず一度「この修正はレビュー指摘に対応したものか」を自分に問え**。判定を自動化するな。以下のような手がかりから自分で判断しろ:
  - このセッション内で対象 PR のレビューコメント・変更依頼を読んでいたか
  - 対象 PR に既存のレビュー（approve / 変更依頼 / コメント）が付いているか
  - 今回のコミットメッセージ・会話の依頼内容が「指摘対応」「修正」を意図しているか
- **レビュー指摘対応だと判断したら、push の報告だけで終わらせるな。** `nt-developer:pr-comment` skill を起動し、レビュアーへの対応完了コメントを投稿するところまで検討しろ（実際に投稿するかどうか・誰宛かの判断は pr-comment skill 自身の作法に従え。このスキルが保証するのは「検討するところまで」だ）
- レビュー指摘対応でないと判断したら、通常どおり push 結果（対象 PR 番号・push したコミット数）のみ報告しろ
- **push のたびに、対象 PR に紐付く計画（`plans/*.md` または GitHub Issue の description）を読み直し、PR 本文と食い違っている箇所が無いか確認しろ。** レビュー対応で計画側だけ更新され、PR 本文が作成時のまま古くなっている状態を放置するな
   - 食い違いを見つけたら、**確認なしで** `gh pr view <番号> --json body` で現在の本文を取得し、「反映のしかた（経路共通）」の対応表の転記先に従って直した本文をファイルに書き出し、`gh pr edit <番号> --body-file <書き出したファイル>` で反映しろ
   - 食い違いが無ければ本文の編集は不要
   - 本文を直した場合は、直した内容を push の報告に含めろ

## 既存 PR 編集モードの手順

- 対象 PR 番号を確定（モード判定で取得済み）
- PR の現状を取得: `gh pr view <number> --json title,labels,assignees,reviewRequests,headRefName,baseRefName,state,author`
- 引数を解析: `--reviewer` / `--label`
- 本文の編集（追記・修正・全面書き換え）を依頼されている場合、`gh pr view <number> --json body` で現在の本文を取得して全文読め。依頼された変更だけを反映した本文をファイルに書き出せ。本文の書き方は「新規 PR 作成モードの手順」の PR 本文作成の項に従え
- label 推定（`--label` 引数が無いとき）:
   - `gh pr diff <number> --name-only` で変更ファイル一覧を取得
   - 「label の推定」セクションのルールで type 候補を推定
   - リポジトリの実在 label と AND
   - PR に既に付いている label は除外（重複追加は不要）
- assignee:
   - PR に既に自分が assignee として入っていれば省略
   - そうでなければ `@me` を追加対象に
- reviewer:
   - `--reviewer` で指定された login をそのまま使え
   - 既に reviewRequests に入っている人は除外
- **PR author が自分以外なら** AskUserQuestion で「他人の PR ですが本当に編集しますか？」と確認。author が自分なら確認不要
- **事前確認なしで** 適用: `gh pr edit <number>` に以下を渡せ
   - 追加 label ごとに `--add-label <name>` を繰り返し
   - assignee: `--add-assignee @me`
   - reviewer ごとに `--add-reviewer <login>` を繰り返し
   - 本文を編集した場合は `--body-file <書き出したファイル>` を渡せ
- 適用後の PR URL と適用内容（label / assignee / reviewer / 本文編集の有無）を簡潔に報告しろ

注: このモードでは label / assignee / reviewer の**追加**と**本文の編集**を扱え。削除・タイトル変更はこのスキルの対象外で、必要な場合はユーザーに `gh pr edit --remove-label <name>` / `--title` の案内をして中止しろ。

## ルール

- **事前確認は原則するな**。事前にタイトル・本文・reviewer・label の表を提示して「これで作成 / 編集していい？」と聞くな。黙って実行して結果報告のみ
- カレントブランチに open PR があり未 push のコミットが存在するときは、確認なしで「既存 PR への追加コミット push モード」に入れ。**push 前に `gh pr view <番号> --json state` で state を個別確認しろ**（検索結果だけで「継続」と判断するな）。push 後は「レビュー指摘対応かどうか」を必ず自分に問い、対応だと判断したら `nt-developer:pr-comment` skill の起動を検討しろ（判定の自動化はしない。「既存 PR への追加コミット push モードの手順」参照）。あわせて対象 PR に紐付く計画と PR 本文の食い違いを確認し、食い違いがあれば確認なしで直せ（「既存 PR への追加コミット push モードの手順」参照）
- 確認を取るのは以下の例外のときだけ:
  - カレントブランチに open PR / マージ済み PR があり、かつ未 push のコミットが無くてモード分岐が必要なとき
  - `--reviewer` の引数が GitHub login の形になっていないとき（誤通知防止）
  - 既存 PR 編集モードで PR author が自分以外のとき（他人の PR への勝手な編集防止）
  - base ブランチ候補（default 以外の統合ブランチ）が複数あるとき（「base ブランチの検出」参照）
  - 新規 PR 作成モードで `--reviewer` も `--draft` も指定されていないとき（reviewer を指定するか確認しろ。Draft PR と既存 PR 編集モードは対象外。プロジェクトの `CLAUDE.md` / `README.md` 等に reviewer を付けない運用が明記されている場合は確認せず reviewer なしで進めろ）
  - 新規 PR 作成モードで、「触るファイル」のパスが重なっただけの計画書の候補が出たとき（紐付けていいか確認しろ。ユーザー自身がその計画書を指している場合と、それを根拠に実装した場合は確認するな。「実装計画の参照」参照）
- 上の例外リストとは別に、新規 PR 作成モードで reviewer が 1 人以上確定したら、PR 作成前に本文の下書きを見せろ（reviewer なしなら不要）。これは実行の可否の確認ではなく、相手への通知が飛んだあとでは取り消せない文章の中身の確認なので、「事前確認は原則するな」の対象外だ
- **head ブランチがカレントブランチと異なる（統合PR等で、既にリモートに存在する別ブランチ間の PR を頼まれた）場合、そのブランチをチェックアウトするな。** `gh pr create --head <branch>` はブランチ名の指定だけで済む。base 取り込みの `git stash` / `git pull` もこの場合はスキップしろ（「新規 PR 作成モードの手順」参照）
- **統合PR（`git log <base>..<head> --merges` に複数のマージコミットを含む PR）では、元のfeature PRのタイトルを使い回すな。標準項目（変更概要・変更理由・動作確認内容・懸念点）も機械的に埋めるな。** 含まれるマージコミット・feature PR への参照を `#<番号>` 形式（フルURLは書くな）で列挙する簡潔な本文を基本にし、詳細な説明文まで要るかは本文を書く前に確認しろ（「新規 PR 作成モードの手順」参照）
- **本文・タイトルの修正指示は疑問形（「〜でいいのでは」等）でも実行指示として受け取れ**。ただし指示の範囲を超えて見出し構造ごと削除する等の広範囲な変更は、明示的な同意なしに行うな。**ユーザーが強い言葉で修正を指示した直後の反映は、再度「これでいいか」を確認せずそのまま実行しろ**（「新規 PR 作成モードの手順」の reviewer 確定時の下書き確認の項参照）
- 新規 PR 作成モードで base ブランチの `git pull` 中にコンフリクトが発生したときは、事前確認の例外ではなく単純に**そこで処理を止めてユーザーに報告し指示を仰げ**（自動解決するな）
- env / 環境変数変更を検出した PR では、報告の最後に必ずチーム共有を促すテキストを添えろ（「env / 環境変数変更の検出」参照）。チャットツール等への自動送信はするな
- 実装計画（`plans/*.md` または GitHub Issue の description）が見つかれば、差分に関係する節を「反映のしかた（経路共通）」の対応表に従って PR description に反映しろ（「実装計画の参照」参照）。計画全体の転記・紆余曲折は書くな。**背景・現状・実装中に確定したことは「変更理由」へ、決めたこと表・承認記録は新設する `## 決めたこと` へ、確認テストの該当した観点・採らなかった案・この判断を覆す条件・未解決事項・今回やらないことは `## 設計判断・スコープ` へ、検証・完了条件は「動作確認内容」へ反映しろ**（差分と無関係な項目は含めるな。新設する PR 本文セクションは `## 決めたこと` の1つだけだ）。**計画の「検証・完了条件」に「よりどころにする資料からの逸脱」の表があれば `## よりどころにする資料からの逸脱` として別セクションに転記し、対象・よりどころにする資料の期待値・採用した挙動・根拠の出所・その根拠が及ぶ適用範囲を1つも落とさず書け**（根拠の対象を書かずに「実測済み」「確認済み」だけを書くな。「反映のしかた（経路共通）」参照）。GitHub Issue 経路で見つかった Issue は確認なしで `Closes #<番号>` を本文末尾に追記しろ（複数見つかれば行を分けて全部書け）。`plans/*.md` 経路は Issue 番号を持たないため対象外
- `plans/*.md` の発見はチケット ID 一致（経路A）だけに頼るな。変更ファイルの重なり（経路B）も必ず併走させろ。**経路B の候補は内容の照合を通ったものだけ採用しろ。** ユーザー自身がその計画書を指している場合とそれを根拠に実装した場合は確認なしで採用し、パスが重なっただけの候補はユーザーに確認しろ（「実装計画の参照」参照）
- 採用が確定した `plans/*.md` にチケットのリンクがあれば `## 関連チケット` として PR 本文に列挙しろ。拾うのは**太字ラベルに「チケット」を含む箇条書きだけ**で、よりどころにする資料・参考資料・運用ドキュメントのリンクを混ぜるな（「反映のしかた（経路共通）」参照）
- `plans/*.md` の `レビュー中` への移動と1行目の `<!-- PR: #<番号> -->` は、同梱 hook（`move-plan-to-review-on-pr-create.sh`）がファイル名にチケット ID を持つ分を自動で処理する。**自分で同じことをするな。** hook が移せない分（ファイル名に ID を持たない計画書）は番号付きで通知されるので、採用が確定したものだけ自分で移せ（「新規 PR 作成モードの手順」参照）。既存 PR 編集モードは対象外
- PR タイトル・PR 本文はすべて日本語で書け
- $ARGUMENTS の第1位置引数が**数字のみ**なら PR 番号として扱い既存 PR 編集モードへ。それ以外は `--draft` / `--reviewer ` / `--label ` 以外の文字列を PR タイトルとして使え（新規 PR 作成モード）
- `--draft` は新規 PR 作成モードでのみ有効。既存 PR 編集モードで指定された場合は無視し、「既存 PR を Draft 化する機能はこのスキルの対象外（`gh pr ready --undo` で手動対応を）」と伝えろ
- assignee の自分自身は `@me` で渡せ（gh の特殊指定。明示的に login を取得する必要なし）
- 既存 PR 編集モードは label / assignee / reviewer の追加と本文の編集が対象。削除・タイトル変更は対象外（生の `gh pr edit --remove-label` 等の案内をして中止）
