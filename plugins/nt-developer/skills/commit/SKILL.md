変更をコミットするスキル。**ステージングが完了したら、`git commit` を実行する前に必ず一度止まり、ユーザーに確認を取れ**（「コミット実行前の最終確認」参照。セッション内での使い回しは無く、コミットのたびに毎回必要）。diff の全文はターミナルに出すな（ユーザーは VSCode 等のエディタでステージ済みの変更を確認する前提のため）。この最終確認とは別に、以下の4つでも個別に確認を取れ:

**この skill を起動する前に、別途「この内容でコミットしていいですか」を聞くな。** コミットの確認はこの skill の中の「コミット実行前の最終確認」で1回だけ取る。起動前と起動後の2回になると、同じことを二度聞かれることになる。実装が終わったら黙ってこの skill を起動しろ。

- **シークレットを含み得るファイルを検出したとき**（「手順」参照）
- **base ブランチ候補が複数あるとき**（「base ブランチの取り込み（コミット前）」参照。そのセッションで最初の1回のみ）
- **今回の作業と無関係な変更（差分の hunk 単位）を検出したとき**（「無関係な変更の検出（ステージング前）」参照）
- **範囲内の変更が複数の独立した目的に分かれているとき**（「独立した複数目的の変更の検出（コミット分割の提案）」参照）

**コミットが完了したら、確認なしで続けて `/pr` スキルを起動しろ**（push → PR 作成まで一気通貫で進める。「コミット後の自動連鎖」参照）。

## base ブランチの取り込み（コミット前）

コミットする前に base ブランチの最新変更を作業ブランチへ取り込め。base より遅れたままコミットを積むと、`/pr` を叩く段階まで差分ズレ・コンフリクトに気づけない。

### base の検出

`git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null` がリモート origin のデフォルトブランチを `origin/<branch>` 形式で返す（例: `origin/main`）。`origin/` を除いた部分を default ブランチとして使え。空（origin/HEAD 未設定）ならローカルに実在する `main` / `master` / `develop` のうち1つを default にしろ。

`git branch -r` に default 以外の統合ブランチ（`develop` / `staging` / `release/*` 等。`feature/*` や個人名ブランチのような一時的なものは除く）が存在する場合だけ、AskUserQuestion でどれを base にするか聞け。**聞くのはそのセッションで最初の1回だけにして、以降のコミットでは同じ回答を使い回せ**（コミットのたびに聞くな。`/pr` が毎回聞くのは PR 1本につき1回しか走らないからで、コミットは頻度が違う）。default 以外の統合ブランチが無ければ確認不要、そのまま default を使え。

### 遅れの判定

以下に1つでも該当したら取り込みは丸ごとスキップし、通常のコミット手順へ進め:

- `git remote` に `origin` が無い（リモート未設定のリポジトリ）
- `git fetch origin <base>` が失敗する（オフライン・認証エラー等）。この場合は取り込みを試せなかった旨をコミット結果の報告に1行添えろ
- `git rev-list --count HEAD..origin/<base>` が `0`（base より遅れていない）

`git rev-list --count HEAD..origin/<base>` が1以上のときだけ、次の取り込みを実行しろ。**遅れていないのに `git pull` を叩くな**（無駄なマージ処理と stash 往復が毎コミット発生する）。

### 取り込み

- 未コミットの変更（tracked / untracked 問わず）があれば `git stash push -u` で退避しろ。**未コミットの変更を抱えたまま素の `git pull` を叩くな**（同梱 hook が deny する）
- `git pull --no-ff origin <base>` で base の最新変更を取り込め
- **コンフリクトが起きたらそこで止めてユーザーに報告し、指示を仰げ**（自動解決するな）。退避していた場合も `git stash pop` せずそのまま残せ（コンフリクト解消後にユーザー自身が pop する）
- コンフリクトなく取り込めたら、退避していた場合は `git stash pop` で戻せ。この pop 自体がコンフリクトした場合も、そこで止めてユーザーに報告しろ
- 取り込みが起きたら `git status --porcelain` を取り直せ。**退避前に取得したパス一覧をそのままステージングに使うな**（pull と pop でファイルの状態が変わっている）

## 無関係な変更の検出（ステージング前）

シークレット検出を通過したら、ステージングの前に「今回の作業と無関係な変更が混ざっていないか」を hunk（差分の1かたまり）単位でチェックしろ。**判定の単位はファイルではなく hunk だ。** 同じファイルの中に範囲内の変更と範囲外の変更が混在していても、範囲外の部分だけを検出しろ。

### 判定基準

`git diff` で対象ファイルの差分を hunk 単位で確認し、各 hunk について以下のどちらかに合致すれば「範囲内」と判定しろ。新規ファイル・削除・リネームは hunk に分割せず、1ファイル1単位として扱え。

- **実装計画を参照している場合**（会話中に GitHub Issue の description または `plans/*.md` を参照した実装作業）: 実装計画の「変更後・対応内容」「触るファイル」の記載と内容が一致する
- **実装計画を参照していない場合**: このセッション中に自分（Claude）が `Edit` / `Write` で書いた内容と一致する

**実装を別のセッションで行い、このセッションではコミットするだけの場合も、計画を参照しているなら1つ目の基準を使え。** `plan` は計画・実装・レビューをそれぞれ別のセッションで行う運用を基本にしているため、コミットするセッションで自分が `Edit` / `Write` を1度も呼んでいないことは普通に起きる。実装がこのセッションでないという理由で2つ目の基準に落とすな（落とすと実装セッションで書いた変更が全部「範囲外候補」になり、コミットのたびに確認が飛ぶ）。

どちらの根拠も無い hunk は「範囲外候補」にしろ。**以前のセッションや手作業での変更は、計画にも今セッションの Edit/Write 履歴にも無い限り自動的に範囲外候補になる**（意図した挙動だ。誤検知だと思っても判定基準を緩めるな）。計画に書いてあるなら「以前のセッションの変更」でも範囲内だ。

### 計画書とのズレの確認（実装計画を参照している場合のみ）

上の hunk 単位の照合は「差分が計画の記載内容と一致するか」の確認だが、それとは別に**計画書自体が実装後も正しい状態を保っているか**を確認しろ。差分と計画書の「実装ステップ」「触るファイル」を突き合わせ、以下を確認しろ:

- 実装ステップのチェックボックスが実際の完了状態と一致しているか
- 計画に無いファイルを実際には変更している、または計画にあるのに触っていないファイルがないか
- 計画時点の前提が実装中に変わったのに、古い記述が計画書側に残っていないか

ズレを見つけたら、コミット前にその場で計画書側を更新しろ（Issue 経路の更新のしかたは `nt-developer:plan` の `references/issue-route.md`「反映のしかた」に従え。plans 経路は計画書を直接編集しろ）。実装計画を参照していない場合はこの確認は不要。

### 確認の出し方

範囲外候補が1件でもあれば、ステージングの前に一覧（ファイルパス + 該当行の抜粋）をまとめて提示し、AskUserQuestion **1回**で以下を決めろ。**hunk ごとに個別に聞くな。**

- 全部除外してコミット（範囲内のみ。デフォルト）
- 一部を含める（Other で対象を指定してもらう）
- 全部含める（実は全部関連している）
- 中止する

範囲外候補が無ければ確認せず、次のステージング手順にそのまま進め。

### 部分ステージングの手順

- ファイル全体が範囲内なら通常どおり `git add <path>` でステージしろ
- ファイルの一部の hunk だけが範囲内の場合、そのファイルの `git diff` から範囲内 hunk だけを抜き出したパッチを作り、`git apply --cached <patch>` で部分ステージしろ
- パッチの作成・適用が失敗したら、そのファイルの全 hunk を「範囲外候補」に繰り込め（**安全側に倒せ。無理に部分ステージを続けるな**）
- 除外した hunk はステージせず作業ツリーに残せ。コミット結果の報告に、除外した内容を一言添えろ（例:「`Foo.vue` の◯◯行目は今回のコミットから除外しました」）

## 独立した複数目的の変更の検出（コミット分割の提案）

「無関係な変更の検出」を通過した範囲内の変更（hunk）を、コミットする前に**目的単位でグルーピング**しろ。1コミットに無関係な複数の目的が混在する事故（例: インフラのコスト削減と開発ルール整備の hook 追加が同一コミットに入っている、無関係な2つのバグ修正が同一コミットに入っている）を防ぐためだ。

### 判定基準

- 会話中でユーザーから独立した複数の依頼（別々のバグ修正・別々の機能追加・関連の無い雑務等）が来ていて、それぞれに対応する変更ファイル・hunk が重ならずに分かれる
- 実装計画を参照している場合、計画の「変更後・対応内容」に独立した複数の項目が並んでおり、対応する変更ファイルが重ならずに分かれる

**同じ目的に付随する関連変更（例: 1つのバグ修正に伴うテスト追加・型定義の調整・呼び出し元の追従修正）は同じグループにまとめろ。** 過剰に分割するな。目的が独立しているかどうかで判定しろ、ファイルが違うというだけで分けるな。

**ただし触る範囲の負債を直したリファクタの hunk は、本命の実装と別のグループにしろ**（`code-style` の「触る範囲の負債は本命の実装より先に直せ」節）。「同じ目的に付随する関連変更」に含めるな。

**hunk 単位の判定と言いつつファイル単位の印象で済ませるな。** 同一ファイル内でも、変更理由が異なる複数の hunk が混在していないか、個々の hunk 本文を実際に読んで確認しろ。

### 確認の出し方

グルーピングの結果、独立したグループが2つ以上検出されたら、**分割するかどうかの確認と各グループの中身の確認を1回にまとめて出せ**。グループが判明した時点で全グループの内容は揃っているので、グループごとに何度も往復するな。

- 各グループについて「予定コミットメッセージ」と「ファイル単位の変更内容」（「コミット実行前の最終確認」と同じ2段構成）を、**全グループぶんまとめて**一覧で提示しろ
- AskUserQuestion は使うな。「コミット実行前の最終確認」と同じ会話文スタイルで「この内容で全部コミットしてよければ教えてください」と**1回だけ**聞け
- 修正・中止の意向が示されたら、そこで止めてユーザーの指示を待て。**グループごとに個別に確認を挟むな**

グループが1つ（または独立した目的に分けられなかった）場合は、この一括確認は不要で通常どおり「コミット実行前の最終確認」を1回だけ行え。

### 分割時の手順

- 一括確認で承認を得たら、グループごとに確認を挟まず連続で実行しろ: 対象ファイル・hunk を「無関係な変更の検出（ステージング前）」の「部分ステージングの手順」（`git add` または `git apply --cached`）でステージ → その場でコミット
- 1グループぶんのコミットが終わるまで次のグループのステージングに進むな（他グループの変更を作業ツリーに残したまま混入させないため）
- 全グループのコミットが終わったら、コミット結果をグループごとに（commit hash + メッセージ第1行）まとめて報告しろ
- 報告の後、初めて「コミット後の自動連鎖」に進み、`/pr` を**1回だけ**起動しろ（グループごとに毎回起動すると `/pr` のモード判定確認が繰り返し発生する）

## コミット実行前の最終確認

ステージングが完了したら `git commit` を実行する前に必ず一度止まれ。**このセッションで初めてかどうかに関わらず、コミットのたびに毎回聞け**（「base ブランチ候補」の確認と違い、使い回しは無い）。

- diff の全文をターミナルに出力するな。ユーザーは VSCode 等のエディタでステージ済みの変更を確認する前提なので、テキストとして貼り直す必要は無い
- 確認を求める前に、変更内容の要点を次の2段構成で示せ。**複数文をつなげた作文調の説明文で書くな**
  1. これから使う予定のコミットメッセージをそのまま示す（別に要約文を作るな。コミットメッセージ自体が要点になる）
  2. ファイル単位の変更内容を「ファイル / 変更内容」の2列テーブルで示す（1ファイル1行、1行あたり1文程度に収める）
- **AskUserQuestion ツールは使うな**。要点を示したあと「コミットしてよければ教えてください」と会話文で聞き、ユーザーの自然文の返答を待て（曖昧な選択肢から選ばせる場面ではなく、単純な yes/no のゲートなので選択肢UIは不要）
- コミットしてよい旨の返答が来るまで `git commit` を実行するな。修正・中止の意向が示されたら、そこで止めてユーザーの指示を待て

## 手順

- `git status --porcelain` で変更ファイルのパス一覧を取得し、`git diff` で中身を確認しろ
- **「base ブランチの取り込み（コミット前）」を実施しろ**。取り込みが起きた場合は `git status --porcelain` を取り直してから次に進め
- **シークレット検出**: ステージング対象に `.env*`（`.env.example` 除く）/ `credentials*` / `*.pem` / `*.key` / `*_rsa` / `id_rsa*` / `service-account*.json` / `.npmrc` / `.pypirc` のような秘密情報を含み得るファイルが入っていないかチェックしろ。1件でも該当したら AskUserQuestion で「コミットしていいか / 除外するか / 中止するか」を必ず聞け（git 履歴に残ると完全削除が困難なため）
- シークレット検出に該当しなければ、**「無関係な変更の検出（ステージング前）」を実施しろ**。範囲外候補が無ければ確認なしで、あれば確認を経てから、次に進め
- **「独立した複数目的の変更の検出（コミット分割の提案）」を実施しろ**。範囲内の変更を目的単位のグループに分けろ
   - グループが1つなら、以下のステージング〜「コミット実行前の最終確認」を通常どおり1回行え
   - グループが2つ以上なら、「独立した複数目的の変更の検出」の「確認の出し方」に従い**全グループぶんまとめた一括確認を1回**行え。承認を得たら、以降はグループごとに確認を挟まず連続で以下のステージング〜コミットを実行しろ
   - **ステージングは `git add -A` / `git add .` / `git add *` を使わず、パスを明示しろ**。ファイル全体をステージする場合は `git status --porcelain` で見たパスを `git add <path1> <path2> …` の形で渡せ。hunk 単位の部分ステージが必要な場合は「無関係な変更の検出（ステージング前）」の「部分ステージングの手順」に従え。同梱 hook がパス無指定の `-A` / `.` / `*` を deny するため、パス無指定では実行できない
   - 改名（`R  old -> new`）は old と new の両方のパスを渡せ。削除されたファイルもパス指定でそのまま staging できる（`-A` に戻す必要はない）
   - 空白・日本語・記号を含むパスはシングルクォートで囲め
   - パスが多くて1コマンドに収まらないときは `git add` を複数回に分けろ。`-A` に戻すな
   - コミットメッセージは「コミットメッセージの type prefix」に従って作成（説明文は日本語、type キーワードのみ英語）。第1行の下に書く理由は「コミットメッセージの本文」に従え
   - `Co-Authored-By` 等の署名はスキルで強制しない（付与の要否は各自の設定 / CLAUDE.md に従う）
   - **ステージ後、`git diff --cached` の内容と意図した変更（計画書・会話で確定した対象）を突き合わせ、コマンドの部分的失敗等で漏れが無いか確認してからコミットしろ**
   - グループが1つのときだけ、ステージング後に「コミット実行前の最終確認」を実施しろ。「コミットする」が返るまで `git commit` を実行するな（グループが2つ以上のときは既に一括確認済みなので、ここでは聞き直すな）
   - コミット結果（commit hash + メッセージ第1行 + 変更ファイル数）を1〜2行で報告しろ。base ブランチからの取り込みが発生した場合は「base から N コミット取り込み」を、`git fetch` に失敗して取り込みを試せなかった場合はその旨を、同じ報告に1行添えろ（遅れが無くスキップしたときは何も書くな）。グループに分けてコミットした場合は、全グループのコミットが終わってからグループごとに commit hash + メッセージ第1行をまとめて報告しろ
- **全グループのコミットが終わったら、続けて「コミット後の自動連鎖」を実施しろ**。ユーザーが「コミットだけ」「PRはまだ」等でこのコミットの範囲を明示的に絞っていた場合はスキップしろ

## コミット後の自動連鎖（push → PR 作成）

**「コミット実行前の最終確認」でユーザーが承認しコミットが完了したら、確認なしで続けて `/pr` スキルを起動しろ。** コミットだけで作業を終わらせず、push と PR 作成まで一気通貫で進める運用にしている。

- 起動した `/pr` は自身のモード判定（新規 PR 作成 / 既存 PR への追加コミット push / 既存 PR 編集 / 中止の分岐、reviewer 未指定確認、reviewer 確定時の下書き確認等）をそのまま行え。**カレントブランチに既に open PR がある場合も含め、分岐の判断は `/pr` 側に委ねろ**（commit 側で「open PR があるから push だけにしよう」のように先回りして判定するな）。既存 PR への追加コミットを push するケース（レビュー指摘対応の修正コミット等）では、`/pr` が push 後に「レビュー指摘対応かどうか」を自問し、対応だと判断すれば `pr-comment` skill の起動を検討する。push だけで完了と報告するな
- **例外**: ユーザーが「コミットだけ」「PR はまだ」「push しないで」等でこのコミットの範囲を明示的に絞った場合は、`/pr` を起動せずコミット完了で終われ
- 「独立した複数目的の変更の検出（コミット分割の提案）」でコミットを複数回に分割した場合は、**全グループのコミットが終わってから最後に1回だけ** `/pr` を起動しろ（コミットのたびに毎回起動すると `/pr` のモード判定確認が繰り返し発生する）

## コミットメッセージの type prefix

**すべてのコミットメッセージ先頭に Conventional Commits 形式の type prefix を必ず付けろ。** 形式は `type(scope): 日本語の説明` または（scope を省略する場合）`type: 日本語の説明`。type キーワードは英語、説明は日本語で書け。

### type 一覧

Conventional Commits 仕様が MUST で定義する type は `feat`（新機能）と `fix`（バグ修正）の2つのみで、それ以外は仕様上「使ってよい」例示にすぎない。以下は実務で最も広く採用されている `@commitlint/config-conventional` の11種（lint ツール・CI テンプレートのデフォルトとして事実上の標準になっている）で、このリポジトリでもこれを使う。

| type | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更（README / CLAUDE.md 等） |
| `style` | 動作に影響しないフォーマット・空白・命名等の変更 |
| `refactor` | バグ修正でも機能追加でもないコードの整理 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルドシステムや外部依存関係の変更 |
| `ci` | CI 設定ファイル・スクリプトの変更 |
| `chore` | 上記いずれにも当てはまらない雑務（バージョン更新のみ等） |
| `revert` | 過去のコミットの取り消し |

変更内容から最も当てはまる type を1つ選べ。複数の性質が混在する場合は最も主要な変更（例: バグ修正のついでの軽微な整理なら `fix`）を優先しろ。

- **CI と CD（デプロイ）を分けるな**: GitHub Actions 等のパイプライン変更は、CI 目的でも CD 目的でも一律 `ci` を使え（標準11種にも広く確立された慣習にも CI/CD 分離は存在しない）
- **インフラ定義（Terraform / CDK / Dockerfile / K8s マニフェスト等）専用の type は無い**: `build` に寄せろ（ビルド・デプロイ対象を変更するという解釈）。純粋な運用上の雑務なら `chore` でもよい

### コミットメッセージの本文

第1行（type prefix + 説明）の下に、そのコミットで変えた内容の**理由**を書け。何を変えたかは diff から読めるので繰り返すな。

- 実装計画（`plans/*.md` または GitHub Issue の description）を参照している場合、「決めたこと」表のうちそのコミットに関係する行と、選ばなかった案を捨てた理由を根拠にしろ
- 分量は数行に収めろ。PR 本文に書く詳細をコミットメッセージへ写し直すな
- 理由が第1行で言い切れる変更（誤字修正・`plugin.json` の version パッチ更新等）では本文を省いてよい

### scope の決め方

**判定基準はファイルの置き場所ではなく、変更内容がどのモジュールの話かだ。** ファイルパスだけで機械的に判定するな。

- 変更内容が単一のモジュールの話に閉じている場合、そのモジュール名を scope にしろ（他プロジェクトなら該当パッケージ名やアプリ名）
- 複数モジュールの話にまたがる変更・リポジトリ全体に関わる話（インストール手順全体の更新等）は scope を省略しろ（`type: 説明` の形）
- scope に迷う・存在しないプロジェクトでは省略して構わない

### 例

- `feat(nt-developer): /pr に reviewer 自動解決を追加`
- `fix(nt-setup): OTELログの保持日数指定が反映されない不具合を修正`
- `docs: READMEのインストール手順を更新`
- `chore: 依存パッケージを更新`

## ルール

- **ステージング完了後、`git commit` を実行する前に必ず「コミット実行前の最終確認」で止まれ**。diff の全文をターミナルに貼り直すな（エディタで確認する前提）。「無関係な変更の検出（ステージング前）」で範囲外候補が見つかったときはそれより先に別途1回まとめて聞け（hunk ごとの個別確認はしない）
- コミットメッセージは「コミットメッセージの type prefix」の形式を必ず守れ。type キーワードは英語、それ以外はすべて日本語で書け。第1行の下には変更の理由を書け（「コミットメッセージの本文」参照）
- .env やシークレットファイルは絶対にコミットするな。検出時のみ確認を取れ
- 今回の作業と無関係な変更（hunk 単位）を計画・Edit/Write 履歴と照合せずに黙ってステージするな（「無関係な変更の検出（ステージング前）」参照）
- 範囲内の変更が複数の独立した目的に分かれる場合、確認せず黙って1コミットにまとめるな（「独立した複数目的の変更の検出（コミット分割の提案）」参照）
- コミット前に base ブランチの最新変更を取り込め（「base ブランチの取り込み（コミット前）」参照）。**未コミットの変更を抱えたまま素の `git pull` を叩くな**。`git stash push -u` を先に踏め
- base より遅れていないときは `git fetch` だけで終われ。毎コミット無条件に `git pull` を走らせるな
- 取り込みで起きたコンフリクトを自動解決するな。そこで止めてユーザーに報告し指示を仰げ（stash していたら pop せず残せ）
- ステージングでパスを省略するな（`git add -A` / `git add .` / `git add *` は禁止）。`git status --porcelain` で見たパスをそのまま明示しろ
- **コミットが完了したら確認なしで続けて `/pr` スキルを起動しろ**（「コミット後の自動連鎖」参照）。ユーザーが「コミットだけ」等で範囲を明示的に絞った場合のみスキップしろ
